# Proposal: Vault/Campaign Separation and the Campaign Map Experience

## Why

MekHQ — the domain reference — has no personal storage concept: everything lives inside one campaign save. MekStation's differentiator is a clear separation of function: an account-level personal vault of immutable, versioned templates (custom mech designs, pilots, player cards/progression) and campaigns that draw on the vault by taking **instance copies** — "the template created by the user, put in context where it becomes real." The original audit found inconsistent separation (thin live references and a stale snapshot spec). Live `CreateCampaignPage.submit.ts` no longer uses the former `UNIT_TEMPLATES` name/tonnage match; root-force membership uses minted instance ids (bounded D3 prerequisite; regression still required). Custom-unit SQLite `current_version`/`unit_versions` plus `VersionRepository`, route preview/commit (`starmapTravelPreview` / `useCampaignStore.dayActions`), and SVG 2.5D projection (`HexMapDisplay`) exist in source. Source presence is not runtime or production authority: campaign journal authority remains disabled, and travel/opportunity/isometric acceptance remain open. Remaining work is template provenance plus a future compatible migration rung after schema v2, campaign opportunities and their authority rules, and the missing map/interface acceptance contracts. The 2026-08-06 council decision (`openspec/council-decisions/2026-08-06-player-vault-vs-campaign-state.md`, judge-VERIFIED) settled the state architecture; this change turns that decision plus the map experience into specs.

## What Changes

- Establish the **vault/campaign boundary** as a first-class capability: immutable versioned vault templates; campaign roster entries as instance copies carrying `unitRef`/`pilotId` + `unitSource` + `sourceVersion` provenance; campaign-local divergence (damage, refits, XP, wounds, death) owned entirely by the instance; explicit screen/menu ownership (personal context: My Units, Pilots, player cards, customizer; campaign context: mech bay, roster, contract market, missions, starmap).
- **Reconcile `campaign-instances`** to the current-tree reference+provenance model per the council decision: the pilot half maps onto `ICampaignRosterEntry` (present in source), the unit half becomes reference+provenance per D1 (`add-saved-custom-unit-campaign-roster/design.md:41-43`) — construction-payload snapshots are removed from the spec. **BREAKING (spec-level):** `CampaignUnitInstance`/`vaultUnitVersion` as specified are retired; no code change is breaking (those types were never implemented).
- Extend the current-tree **starmap travel economy**: preserve existing route preview/commit, elapsed-time, fee, daily-processing, and arrival calculations while adding **dynamic opportunities** — GM-authored or randomly generated — as time-bound map affordances that resolve into contracts/missions. Preview/commit exist in source; they still need acceptance coverage and authoritative travel/opportunity events. Do not add a second clock.
- Reconcile and extend the current-tree **starmap-interface** display contract with opportunity markers and travel-state rendering; route time/cost preview exists in source and needs current acceptance coverage where required.
- Complete the **isometric battlefield view** contract over the existing SVG 2.5D tactical projection: elevation-aware tiles, unit tokens, facing, occlusion, and shared tactical overlays remain layered over — and do not replace — the current 2D tactical map. A new 3D engine, renderer, or per-unit model-asset acquisition is outside this change.
- Sequencing: implementation of all of the above begins **after CAMP-01F/G/H land** (frozen contract digests pin today's roster shape; council/Momus precondition).

## Capabilities

### New Capabilities
- `vault-campaign-boundary`: the personal-vault vs campaign-context separation — immutable versioned templates, instance-copy semantics with provenance, context ownership of screens/menus, and the template→instance flow ("becomes real").
- `starmap-travel-economy`: travel simulation on the campaign starmap — time advancement, jump/transit/daily costs against campaign finances, arrival effects, and dynamic opportunity generation (GM-authored and random) resolving into contracts.
- `isometric-battlefield-view`: isometric 3D presentation of ground combat over the existing hex tactical model — projection, elevation, tokens, selection/hover parity with the 2D map.

### Modified Capabilities
- `campaign-instances`: reconciled to the reference+provenance instance model (council decision); pilot instances named onto the current-tree roster-entry shape; unit construction snapshots removed; `unitSource`/`sourceVersion` added.
- `starmap-interface`: display contract gains route/time/cost preview, opportunity markers, and travel-in-progress rendering.

## Impact

- **Types/state**: `IRosterUnitProjection` (+`unitSource`, `sourceVersion`), `ICampaignRosterEntry` (naming/spec reconciliation only), and the next `SerializedCampaign` migration rung after the existing v2 authority envelope (`campaignMigration.ts` ladder; the implementation wave must admit v3 for provenance unless an explicitly reviewed alternative is chosen). Existing custom-unit UnitRepository create/update path produces the SQLite current_version/unit_versions rows, while VersionRepository provides history/revert operations; pilot version authority remains an unresolved admission decision.
- **Screens**: personal context (My Units, Pilots, Customizer, player cards) vs campaign context (dashboard, mech bay, contract market, missions, starmap) — navigation/IA ownership declared per context; campaigns index gains the create/draw-from-vault flow.
- **Campaign systems**: `campaign-finances` (travel fees/daily costs post), `day-progression` (travel time), `mission-contracts` (opportunities resolve into contracts; no requirement change expected — integration via design), GM tooling (opportunity authoring).
- **Combat UI**: current-tree tactical map stack includes an additive SVG 2.5D isometric renderer consuming the same hex/terrain/unit state (`tactical-map-interface` untouched at requirement level); this change completes its acceptance gaps rather than introducing a separate 3D engine. Renderer presence is not measured 4v4 or production-authority proof.
- **Frozen constraints honored**: D1 (no construction-payload duplication; preserve the explicit source references and minted roster-instance IDs already used by `src/components/gameplay/pages/campaigns/create/CreateCampaignPage.submit.ts`; the old name/tonnage match is absent), CAMP-01 contract digests (implementation sequenced post-F/G/H), replay determinism (instances resolve stats by pinned version).
