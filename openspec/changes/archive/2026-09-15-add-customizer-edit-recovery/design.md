## Decisions

1. Undo is session-local and limited to the latest 50 user operations for each BattleMech-family store. A store action, including all its synchronous cascades, is one transaction. Armor auto-allocation and bulk equipment placement each undo once. No-op actions do not consume history. Editing after undo clears redo. Reload and closing the draft clear session history.
2. Snapshots contain complete editable UnitState fields, including optional fields and equipment instance IDs, but exclude store methods, draft identity, timestamps, source provenance, and library receipts. Undo/redo applies the fields changed by each transaction, preserving identity fields changed independently by a later library save. It preserves the store identity and functions and runs through the existing persistence path. Derivations continue to use the restored store.
3. Browser status is visible text based on actual write receipts. Initial/read-only states do not assert a successful write. A persisted library receipt records the server-returned ID/version, a serialized-construction fingerprint for library status, and a complete editable-draft fingerprint for dirty-state protection. Both save comparisons normalize temporary equipment IDs; undo snapshots and stale-request guards retain exact IDs. Status describes the last saved/loaded version, never claims it is the server's latest version, and reports whether the draft matches that receipt without an invented change count.
4. Saved history is bound to the draft and library ID captured when opening. Restoring fetches and normalizes the selected immutable version before applying it as one undoable draft transaction. It does not call the library revert API or mutate a library version. Saving the restored draft uses the existing save flow. Late responses must not overwrite another unit, a closed/replaced store, or intervening edits. Loading/restore failures remain visible and preserve the draft.
5. Undo/redo controls show the next operation, support Ctrl/Cmd+Z, Shift+Ctrl/Cmd+Z and Ctrl+Y, and leave native text-editing undo and modal interaction alone. At 390px the controls and status remain readable without page overflow. Unsupported unit families retain draft-status visibility and do not show misleading enabled history controls.

## Ownership and verification

Parent owns store history, snapshot/receipt contracts, undo UI, specification, integration and final verification. One bounded Cursor Grok 4.6 high worker may own visible status, saved-history integration, and save/load receipt callers. Verification includes store serialization and derived values, independent tabs, no-op/branch/cap behavior, save races, failed writes, stale historical fetches, and real server-backed save/history/restore/reload in a disposable browser and database. Required type/lint/format/build checks apply; pre-existing failures are recorded separately.
