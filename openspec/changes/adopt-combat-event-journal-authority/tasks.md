IDENTITY covers command id, actor, starting revision, and every event id AND type - a retry reproduces all of them, a different command reusing the id does not, which is what makes `integrity-conflict` a distinct answer from `duplicate-command` rather than a silent overwrite that would attribute one player's command to another. CONTIGUITY names the offending revision rather than failing vaguely, and rejects a REPEATED revision the same way as a skipped one (two events claiming one place in history are equally unreadable). ATOMICITY is one SQLite transaction covering the identity lookup, revision check, every INSERT, the receipt, and the `updated_at` bump; identity is checked FIRST because a retry arriving after the stream moved is still a retry, and calling it a revision conflict would send the caller to rebuild state it already holds. **A VACUOUS TEST WAS CAUGHT HERE:** the original atomicity row offered an out-of-order batch and asserted nothing was written - it passed WITH THE TRANSACTION REMOVED, because the pure contiguity guard rejects that batch before the insert loop runs. It proved the guard, not the rollback.
