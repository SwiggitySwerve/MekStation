# Proposal: Campaign Authority and Synchronization

## Why

The 2026-08-07 live visual audit produced hard evidence of the boundary this change fixes: a campaign created in one browser context returns "Campaign not found" on every deep link from any other context. Campaign runtime state lives in the browser (Zustand `persist` → client storage), so the source device is the only place the campaign exists, deep links and cross-device continuity fail, and co-op is structurally constrained. The 2026-07-07 live playtest's multiplayer socket failures (dual in-memory match stores) and the silent `/api/campaigns` 500 are the same root cause surfacing elsewhere.

The direction is confirmed: campaign state must be kept on the server — never authoritative in the browser — so it can be shared with peer players through a share function, synchronized constantly, and never lost on the source device. The source broadcasts events to every downstream consuming device (each of which runs its own local server and keeps its own durable copy). One source campaign can create many shared instances; shared instances know they are not the source; they see the actions taken over the campaign's whole history from their less-permissive perspective. The Game Master retains full view of everything; other participants must not even receive the events outside their access.

The substrate largely exists and is reused, not reinvented: the SQLite event journal (`src/lib/events/journal/`) already provides hash-chained events (`previous_stream_event_digest` → `event_digest`), stream/branch identity, canonical command identity, and actor/authority columns; `CampaignPersistenceService` already provides server-side campaign summaries/bodies; the WebSocket upgrade path and vault-identity token minting already exist for multiplayer. This change binds the campaign domain to that substrate and adds the authority, replication, and access-projection contracts on top.

## What Changes

- **NEW capability `campaign-authority`** — server-authoritative campaign state: every campaign is owned by exactly one source instance on a server; all mutations are commands validated at the source and appended durably to the campaign event stream before any acknowledgement or broadcast; browser storage is demoted to a cache; deep links resolve from the server.
- **NEW capability `campaign-replication`** — the share function issues grants; downstream devices instantiate replica instances that carry source identity and grant provenance (a replica always knows it is not the source); replicas receive the event stream over a persistent connection with cursor-resumable catch-up, persist their own durable local copy on their own local server, and route mutation intents back to the source.
- **NEW capability `campaign-access-projection`** — every campaign event carries an access scope at emission; the source projects a per-grant filtered stream; consumers never receive events outside their grant; the GM grant receives the full stream; filtered streams remain causally ordered, per-scope contiguous, and per-scope digest-chained so a replica can verify integrity without learning anything about withheld events.
- **MODIFIED capability `campaign-persistence`** — the server-side persistence contract is promoted from an optional save path to the authoritative home of every server-owned campaign: creation lands in the server store immediately, deep links resolve without client-side handoff, and a deleted server record cannot be resurrected from a client cache.
- **MODIFIED capability `coop-campaign-sync`** — the guest's read-only mirror is upgraded to a durable replica instance (persisted by the guest's own server, carrying replica authority metadata, surviving restart with offline reads), and guest hydration becomes scope-filtered at the host with per-grant cursor resume. The existing intent → validate → commit → broadcast loop, host-as-GM authority model, and player-safe projections are preserved and generalized, not replaced.

## Impact

- Affected specs: `campaign-authority` (new), `campaign-replication` (new), `campaign-access-projection` (new), `campaign-persistence` (modified), `coop-campaign-sync` (modified).
- Affected code (at implementation time, not in this change): campaign Zustand stores and persistence wiring (`src/stores/campaign/`), `CampaignPersistenceService` and `/api/campaigns/*` routes, the event journal consumers (`src/lib/events/journal/` — reused as-is), the WebSocket server surface (`server.js` upgrade path + a campaign sync channel), vault-identity token minting for grant authentication.
- **BREAKING (spec-level):** browser-local storage ceases to be an authoritative home for campaign state. Existing browser-persisted campaigns require a one-time adoption migration into the server store (design D8); after adoption the client cache is derived state only.
- Relationship to `design-vault-campaign-separation-and-maps`: composes, does not overlap. The vault change governs what enters a campaign (immutable personal templates → instance copies with provenance); this change governs where campaign state lives and how it reaches other players. The vault remains personal and unsynchronized; campaign event streams are the shared unit.
- Sequencing: implementation starts only after CAMP-01F/G/H complete (same frozen-contract gate as the vault change). Spec-level work (this change) lands now.
