# Design: Campaign Authority and Synchronization

## Context

> Reconciliation note (2026-08-20): this change is the single surviving home for campaign journal work. `adopt-campaign-event-journal-authority` (the campaign-journal slice of `harden-gm-two-player-campaign-sessions`) is archived as SUPERSEDED; its D2/D3 machinery is imported intact as D10 below, its cursor doctrine is adopted into the rewritten D4, and its spec deltas are absorbed into this change's `specs/`. Council decision: `openspec/council-decisions/2026-08-20-campaign-journal-reconciliation-and-next-work.md`.

Live evidence (2026-08-07 visual audit, historical motivation): campaigns were browser-local — a fresh browser context got "Campaign not found" on every campaign deep link. At that date the runtime store was Zustand `persist` (`src/stores/campaign/useCampaignStore.ts` → `clientSafeStorage`); the server-side `CampaignPersistenceService` + `/api/campaigns/*` existed but acted as an optional save path, not the home. As of 2026-09-12 that deep-link failure is not current route behavior: `CampaignPersistenceService` owns server read/save (`src/services/campaignPersistence/CampaignPersistenceService.ts`); GET `/api/campaigns/:id` reads the server record and returns 404 only for a missing row (`src/pages/api/campaigns/[id].ts`); the persistence store loads through that API (`src/stores/campaign/useCampaignPersistenceStore.ts`); and the campaign route shell loads the route campaign through that store (`src/pages-modules/gameplay/campaigns/campaignPageShell.tsx`). Browser storage remains cache/legacy-adoption input until D8 migration. Production journal authority remains a separate still-disabled cutover boundary (`CAMPAIGN_JOURNAL_AUTHORITY_ENABLED` is false; `src/lib/campaign/sync/campaignJournalAuthorityEnabled.ts`). Meanwhile the repo already contains the three hard pieces this design needs: a canonical, hash-chained SQLite event journal (`src/lib/events/journal/` — stream type/id, branch id, stream revision, commit position, canonical command identity, actor/authority columns, `previous_stream_event_digest` → `event_digest` chaining, fsync semantics, recovery), a server-authoritative co-op sync spec (`coop-campaign-sync`: intent → validate → commit → broadcast, host-as-GM, player-safe projections, snapshot hydration), and a WebSocket upgrade path plus vault-identity token minting on the multiplayer surface. The user direction: campaign state lives on the server; a share function creates many shared instances from one source; shared instances know they are not the source; they see the whole history from a less-permissive perspective; the GM sees everything; out-of-scope events are never even delivered.

## Goals / Non-Goals

- Goals: one authoritative home per campaign (source instance on a server); durable append-before-acknowledge so the source never loses state; durable replicas on consuming devices ("each downstream device has its own kind of server"); grants with scope-filtered event delivery (filtering at the source, never client-side hiding); GM full view; late-join backfill of the full in-scope history; tamper-evident streams end to end.
- Non-Goals: CRDT/peer-merge state (explicitly forbidden by `coop-campaign-sync`); multi-master writes; cross-server campaign migration protocols (a future change; the identity model leaves room); vault synchronization (the vault stays personal — `design-vault-campaign-separation-and-maps` governs vault→campaign copies); combat-session transport (the match/mission layer keeps its existing socket protocol).

## Decisions

### D1 — The campaign stream lives in the existing SQLite event journal; no new log technology
Campaign mutations append to the canonical journal with `streamType: 'campaign'`, `streamId: <campaignId>`, `branchId: 'main'` (branching reserved for future what-if forks, matching the journal's existing column). The journal's canonicalizer, command identity, digest chaining, fsync and recovery semantics are reused as-is. Rationale: the journal already implements exactly the "git-tree of tracked changes over time" model (hash-chained, branch-capable, replayable) and is battle-tested by its own suites; a second log would violate simplest-solution and single-source-of-truth. Alternative rejected: bespoke campaign log tables (duplicate infrastructure, no chain verification).

### D2 — Authority metadata on the instance record: `source` or `replica`, never silent
The campaign record gains `authority: { role: 'source' } | { role: 'replica', sourceInstanceId, grantId, scopes, revokedAt? }` plus a stable `instanceId` for every hosting server. Commands execute only where `role === 'source'`; replicas hard-guard local mutation (reusing the mirror append guard) and forward intents. Rationale: the user's requirement that shared instances "know they are not the direct source" must be a stored, surfaced fact, not an inference from connection state.

### D3 — Scope is stamped on every event at emission and is part of the canonical bytes
Event payload envelope gains `scope: 'gm' | 'campaign' | 'team:<id>' | 'player:<participantId>'`, chosen by the emitting domain action (day advance → `campaign`; GM-authored hidden opportunity → `gm`; a lance's private orders → `team:`/`player:`). Because scope is inside the canonicalized payload it is digest-protected; reclassification is a new revelation event referencing the original, never an edit. Rationale: filtering can only be trustworthy if the classification is immutable and the GM can audit it. Alternative rejected: scope lookup tables outside the event (mutable, unauditable, race-prone).

### D4 — Per-grant projection at the source: filter, renumber, deliver through the privacy-owned cursor authority (REWRITTEN 2026-08-20, council reconciliation)
For each grant the source maintains a projection cursor over the campaign stream. Delivery = events whose scope ∈ grant.scopes, assigned a contiguous per-grant sequence. Out-of-scope events are simply absent — no stubs, no gaps in the per-grant numbering, no global positions on the wire — so a consumer cannot count or time withheld activity, yet can verify completeness/integrity of its own stream. GM grants carry the all-scopes set and receive the raw stream (global revisions + original chain).

AMENDED per the council reconciliation with the superseded `adopt-campaign-event-journal-authority` (decision: `openspec/council-decisions/2026-08-20-campaign-journal-reconciliation-and-next-work.md`): this design SHALL NOT mint a campaign-specific epoch, sequence allocator, or raw-journal cursor. The per-grant sequence and delivery acknowledgement are carried by the privacy-owned `(deliveryEpochId, deliverySequence)` mapping defined by `add-authority-audit-and-privacy-proof` (its design derives `deliveryEpochId` from authorized-viewer + stream and fails closed on foreign epochs) — a grant maps to a delivery epoch; `deliverySequence` IS the per-grant sequence. The earlier per-grant digest chain (`prevGrantDigest` → `grantDigest`) is replaced by the epoch mapping's fail-closed identity guarantees plus the journal's own chain on the underlying events; if implementation shows scoped-stream tamper-evidence needs a digest chain the epoch mapping cannot supply, that gap re-opens this decision (recorded revisit trigger). Consequence accepted: THIS change now owns the delivery-cursor privacy/leak proofs for campaign delivery (tasks 3.3/4.3), consuming the audit-privacy schema as a narrow dependency rather than waiting on that change wholesale. Rationale: per-scope contiguity satisfies "verifiable" and "no leakage" simultaneously, and a single delivery-cursor authority repo-wide beats a campaign-local exception (uniformity; the adopt-side doctrine "do not mint a campaign-specific epoch" is adopted, not overridden).

### D5 — Transport: a campaign sync channel on the existing WS upgrade path, authenticated by grant token
The share function mints a grant token (signed with the existing vault-identity machinery already used by multiplayer). A replica connects to the source's `/api/multiplayer/socket` (campaign channel) presenting `{campaignId, grantId, token, cursor}`; the source streams backfill from the per-grant sequence after `cursor`, then live events. Heartbeat + reconnect follow the existing socket conventions. Rationale: one socket surface, one identity system; the `coop-campaign-sync` transport requirements already bind to this path. Alternative rejected: HTTP polling (loses ordering/latency), new port (packaging complexity).

### D6 — Replica durability: the consuming device's own server persists the scoped stream
The replica device's server process stores received events in its local journal under `streamType: 'campaign-replica'`, `streamId: <campaignId>#<grantId>`, preserving the per-grant chain, and projects UI state from it. Offline: reads work from the local store; mutation intents are disabled (not queued in v1 — a queued-intent inbox is a future extension listed in Open Questions). Browser Zustand persistence remains only as a render cache keyed by `(instanceId, revision)` per campaign-authority. Rationale: this is the user's "each downstream device has its own kind of server," and it makes late-join backfill a one-time cost.

### D7 — Ordering, idempotence, and loss: durable-append-then-broadcast, apply-by-sequence
Source ordering: journal append (fsync) → acknowledge submitter → fan out to grant projections. Replica apply is idempotent by per-grant sequence; duplicates are dropped; out-of-order delivery triggers cursor re-request. A downstream failure can never affect the source stream (one-way data flow). Snapshots (`CampaignSnapshotPublished`, scope-filtered per D4) are an optimization baseline every N events so late joiners avoid unbounded replay; the spec requires them to be equivalent to replaying the scoped stream.

### D8 — Legacy adoption: one-time import of browser-persisted campaigns
On first load after cutover, browser-persisted campaigns are offered for adoption: the client uploads the serialized campaign; the server creates the source instance with a synthetic `campaign-adopted` genesis event (carrying the imported projection digest), and the browser copy is demoted to cache. Unadopted copies remain readable but clearly labeled unshareable/legacy. Rationale: the audit found real campaigns already live in browsers; stranding them would destroy user state — the same "never lose state" principle applied backward. AMENDED 2026-08-20: D8 is the browser-copy entry point into D10's migration-state machinery — an adopted browser campaign records its imported baseline in the D10 cutover marker and enters `journal` (or `shadowing`, where a server snapshot also exists) rather than bypassing migration state; D8 and D10 are one adoption surface, not two.

### D10 — Migration states, atomic batch commit, and cutover law (IMPORTED INTACT 2026-08-20 from superseded `adopt-campaign-event-journal-authority` D2/D3)
Cutover is per campaign and persists one durable migration state, `CampaignAuthorityMigrationState = 'legacy' | 'shadowing' | 'journal' | 'blocked'`, with a cutover marker recording the imported source snapshot revision/digest, root branch, baseline event/revision, projector version, deterministic schema/upcaster-pipeline fingerprint, and first journal-authority command if one exists. There is never dual authority. Snapshots are materialized projections of committed journal history; every materialized snapshot binds the schema-pipeline fingerprint, and recovery MUST discard and rebuild a snapshot whose fingerprint differs from the registered replay pipeline even when projector version and digest match. Commands commit as atomic batches: the source validates a stable command identity and expected campaign revision, derives the whole event batch plus expected post-state digest, atomically appends both, applies the committed batch, verifies the applied digest, and only then fans out; on divergence it publishes no success, quarantines the process-local projection, and rebuilds from the journal without deleting the committed batch. Snapshot-authority rollback is permitted only while the journal head equals the imported baseline and no journal-authority command has committed; afterwards the campaign uses a compatible journal reader or enters `blocked`, never a silent legacy fallback. Rationale for import-intact: the D2 machinery solves legacy-cutover safety, which D8's one-shot genesis alone does not; folding would have lost the shadow-comparison and rollback laws.

### D9 — GM view is a grant property, not a hosting property
The GM's full view comes from holding the all-scopes grant. Usually the GM hosts the source, but a GM connecting from another device gets a full-scope replica — same mechanism, no special path. Host-as-GM arbitration from `coop-campaign-sync` is unchanged: commands still commit at the source.

## Risks / Trade-offs

- **Scope misclassification leaks**: a domain action stamping too-wide a scope leaks information permanently (streams are immutable). Mitigation: scope vocabulary is closed; emission sites are enumerated at implementation time with a QC sweep asserting every campaign event constructor names a scope; GM audit surface shows scope per event.
- **Per-grant chains add storage/compute at the source**: one cursor + rolling digest per grant is O(grants) and trivial at tabletop scale (units of grants, not thousands). Accepted.
- **Snapshot/stream equivalence drift**: mitigated by requiring snapshot content to be derived by replaying the scoped stream (the projection function is shared), plus a verification task.
- **Offline replicas cannot act**: accepted for v1 (matches "replicas are source-bound"); queued intents deferred.
- **Adoption imports state without event history**: adopted campaigns begin their chain at the genesis event; pre-adoption history is a single opaque baseline. Accepted and labeled in UI.

## Migration Plan

1. Server-authoritative cutover for new campaigns (creation writes the source instance + genesis event; deep links resolve server-side).
2. Adoption flow for legacy browser campaigns (D8).
3. Grants + share function + replica instantiation (durable replica store, replica identity surfaces).
4. Scoped projection + per-grant chains + scoped snapshot hydration (upgrading the co-op mirror path in place).
5. Cache demotion: Zustand persist keyed by instance/revision, validated against stream head.

## Open Questions

- Queued offline intents from replicas (an inbox the source drains on reconnect) — deferred; requires conflict UX.
- Cross-server source migration (moving a source to another device) — identity model reserves `instanceId` lineage; protocol deferred.
- Whether team scopes need hierarchical containment (`team ⊂ campaign`) or stay flat — flat in v1.
- Branching (`branchId ≠ main`) for GM what-if forks of campaign state — the journal supports it; product design deferred.

## Preparation freeze (2026-09-12)

### D11 — Prepared synchronous append-with-extension (P0a; 2026-09-12 freeze)

P0a is a concrete journal-writer preparation API. It is not a campaign producer, not private-envelope replay, and not cutover. Production `CAMPAIGN_JOURNAL_AUTHORITY_ENABLED` stays false. This decision does not claim the method exists, is reviewed, or is runtime-accepted.

Current `appendWithExtension` cannot capture an immutable private baseline: it parses and canonicalizes `raw` before `this.db.transaction(...).immediate()` (`SQLiteEventJournalWriter.ts:54-68`). `IEventJournal` stays unchanged (`EventJournalContract.ts:140-158`). Existing `append` / `appendWithExtension` callers, including `campaignCombatOutcomeInbox.ts:80`, keep today's contracts.

Add only on `SQLiteEventJournalWriter`:

```ts
appendPreparedWithExtension<TContext, TResult>(
  prepare: (db: Database.Database) =>
    | { readonly kind: 'ready'; readonly context: TContext;
        readonly raw: IAppendEventBatch<TPayload> }
    | { readonly kind: 'refused'; readonly result: TResult },
  extend: (
    db: Database.Database,
    context: TContext,
    append: () => EventJournalAppendResult<TPayload>,
  ) => TResult,
): Promise<TResult>
```

One `this.db.transaction(...).immediate()` body, in this order: (1) contractually read-only `prepare(this.db)` — source/head reads only; no SQL writes, external side effects, or retained statements/handles; P0a does not add a runtime read-only database proxy or SQL parser (trusted internal callbacks plus real tests suffice); (2) `{ kind: 'refused' }` returns `result` with no parse, canonicalize, append, or extension write and leaves every relevant table unchanged; (3) `AppendEventBatchSchema.parse(prepared.raw)` then `canonicalizeCommandIdentityV1` so prepared baseline bytes are inside command/event digests; (4) duplicate `eventId` throws `Duplicate eventId` as today (lines 56-61); (5) `extend(this.db, prepared.context, () => appendInTransaction(identity.command, identity.digest))`. Typed `revision-conflict` / `command-identity-conflict` from `append()` itself MAY return from `extend` because `appendInTransaction` writes nothing in those branches (`SQLiteEventJournalWriter.ts:107-130`). Both `prepare` and `extend` SHALL complete synchronously entirely during the transaction: no `await`, returned thenables, timers, microtasks, deferred work, external I/O, or retaining `db`/`context`/`append` for later use. For the `TResult` contract, the `result` field of a refused `prepare` return and the direct `extend` return SHALL be synchronous; the defensive guard SHALL inspect the direct `prepare` return before its discriminator, `prepared.result` when it is refused, and the direct `extend` return, rejecting any Promise or thenable before commit and rolling back. Scheduling remains prohibited. Nested `saveCampaign` remains forbidden (`CampaignPersistenceService.ts:110-158`). The thenable guard is defensive only and cannot guarantee rollback of arbitrary scheduled or external side effects; P0a does not promise a general runtime sandbox or detection of arbitrary scheduled closures. A source-command layer defines its dedicated rollback error; after a successful `append()`, `extend` SHALL throw that error on source-write failure; `appendPreparedWithExtension` SHALL let it escape the immediate transaction unchanged. Only the source-command caller catches AFTER rollback and maps a typed refusal. The writer MUST NOT catch and return that refusal inside the transaction. Thrown prepare/parse/canonicalize/append/extension failure rolls back receipt, events, head, and extension rows together.

Required tests (P0a characterizations, not claimed present): actual SQLite commit then reopen; snapshot read of the passed `db` during prepare; rollback after append when the extension throws a dedicated fixture rollback error; refused prepare leaving every relevant table unchanged; malformed batch and in-batch duplicate IDs; returned-thenable rejection/rollback; a caller-side catch outside the writer mapping the fixture error after rollback. Callback contract and review cover the scheduling prohibition; tests SHALL NOT claim automatic scheduled-work detection. The writer SHALL NOT add campaign producer or campaign error taxonomy. Home for those rows is the existing writer suite (`src/lib/events/journal/__tests__/SQLiteEventJournalWriter.test.ts`), which already proves `Duplicate eventId` and rollback on throw.

Local planning-input provenance (ignored raw; not canonical published proof and not runtime acceptance): `.sisyphus/roadmap-completion-20260912/r2-source-contract-private-replay-20260913/` with immutable `report.json` sha256 `835380dfb33bd14a3ee437e5ba86a762ce4691586db7573c055e70a840e33912`. Executable source anchors in this decision remain the support for current writer behavior. The post-append throw-and-propagate rule is the admitted freeze and supersedes any planning-input wording that would return a source-write failure object after append.

### D12 -- Full contract and market are SOURCE-ONLY; `envelopeOf` is the enforcing boundary (2026-09-15; resolves the P0b/P1 audience prerequisite)

This decision discharges the recorded prerequisite "resolve source-only or explicit guest field projection before P0 implementation". It admits an audience contract. It does not admit an implementation, a flag flip, or a cutover; `CAMPAIGN_JOURNAL_AUTHORITY_ENABLED` stays false.

**The problem.** Every campaign-scope recipient today receives an unredacted payload. `ContractAccepted` defaults to `campaign` scope (`campaignEventScope.ts:35`); grant projection copies the payload and strips only `sequence` (`projectCampaignStreamForGrant.ts:140-174`); `applyCampaignEvent` folds the accepted contract into the shared `ICampaignAuthoritativeState` (`applyCampaignEvent.ts:91-97`) and replaces that state wholesale for a snapshot (`:75`); and room-code guest hydration takes the genesis `CampaignSnapshotPublished.payload.state` wholesale (`roomCodeGuestHydration.ts:46-55`), folds in-scope items onto it (`:73-84`), and republishes the composed state as another `campaign`-scope snapshot (`:126-158`). Therefore any field added to `ICampaignAuthoritativeState` or to a `campaignEvent` payload is, by construction, a restricted-guest-visible fact. Full `IContract` (`Mission.ts:135-186`: employer, target, payment terms, salvage rights, morale, AtB type) and `ICampaignContractMarket.offers` (`CampaignCommandExtensions.ts:38-44`) are materially broader than the compact `ICampaignAcceptedContract` (`CampaignSync.ts:66-73`) the wire carries today.

**The decision: source-only.** Full accepted `IContract` and the remaining `contractMarket` are source-local facts with an audience of exactly one -- the source instance's own server process and its persisted `SerializedCampaign` record. They are carried on a journal-private field of `ICampaignJournalEnvelope` (`JournalCampaignEventStore.ts:91-96`), a sibling of `campaignEvent`, never inside it. No grant scope -- not `campaign`, not `team:`, not `player:`, and not the GM all-scopes grant -- entitles a recipient to them over the wire, because no wire-bearing type names them.

**The enforcing boundary is `envelopeOf`, which already exists.** `envelopeOf` (`JournalCampaignEventStore.ts:177-181`) is the single narrowing from a stored journal row to a wire campaign event, and every read path goes through it (`:270`, `:397`). Keeping `envelopeOf` returning `stored.payload.campaignEvent` and nothing else makes the boundary structural rather than procedural: a private field on the envelope cannot reach grant projection, room-code hydration, the co-op mirror, or an HTTP response without someone deleting the narrowing, which is a single reviewable line and a single test. This is D4's "filter at the source, never client-side hiding" applied at the type level.

**Alternative rejected: explicit guest field projection.** The alternative was to classify each full-contract and market field, then add a redacting projector that emits a whitelisted subset to campaign-scope recipients. Rejected on four grounds. (1) It creates a second projection path that must stay correct at three independent emission surfaces -- grant projection (`projectCampaignStreamForGrant.ts:153-174`), room-code hydration's recomposed snapshot (`roomCodeGuestHydration.ts:126-158`), and the client snapshot schema -- and a redactor that any one surface bypasses leaks permanently, because streams are immutable and reclassification is a new event, never an edit (D3). (2) It requires editing `roomCodeGuestHydration.ts` and a client schema, paths the recorded R2 implementation ceiling does not cover, so it would silently exceed the admitted prefix. (3) No product requirement names a guest-visible full-contract field; the compact projection already satisfies every current guest surface, so the whitelist would be empty on the day it shipped -- an abstraction with no caller (simplest-solution). (4) Should a guest-visible contract detail ever be required, the correct shape under D3 is a NEW event type stamped with the scope that fact actually deserves, carrying exactly that fact -- not a field-level redactor draped over a payload whose default audience is already too wide.

**Legacy and digest consequences (binding on any implementation).** The private field SHALL be conditionally constructed and absent when there is no admitted private payload. It SHALL NOT be written as `{}` or as an enumerable `undefined` property: `canonicalizeJsonV1` fails on `undefined` (`EventJournalCanonicalizer.ts:75-77`) and hashes exactly the enumerable own keys (`:104-117`), and `computeCampaignStateDigest` hashes the canonical state (`JournalCampaignEventStore.ts:128-132`), so either shape changes the digest of history that has not changed.

**What this decision does NOT admit.** It does not admit a full private HTTP readback: that surface has no defined caller, no authentication story beyond the existing active-seat gate (`src/pages/api/campaigns/[id]/commands.ts`), and remains blocked exactly as the P1 requirement states. It does not widen the `/commands` response, guest hydration, or the co-op mirror. It does not claim authoritative materialization or replay of unrelated non-contract missions.
