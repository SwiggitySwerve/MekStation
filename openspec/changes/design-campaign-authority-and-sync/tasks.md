## 2. Grants and Share Function (campaign-replication)

- [x] 2.1 Grant model at the source: issue/list/revoke grants `{grantId, campaignId, participantIdentity, scopes, issuedAt, revokedAt?}`; persist in the server store; sign grant tokens with the existing vault-identity machinery.
  - Receipt (2026-08-22): SQLite migration v14 `campaign_grants_schema` + `src/lib/campaign/grants/` (contract, guards, borrowed-handle store, token mint/verify). A grant is `{grantId, campaignId, participantId, issuerPublicKey, scopes, issuedAt, expiresAt, revokedAt?}` with an opaque 32-hex server-minted id; triggers forbid delete (a revoked grant is an audit fact) and admit only the one-way active-to-revoked UPDATE with every identity column pinned. Scope canonicalization (sort + dedupe, one byte form per logical set) is load-bearing because the SAME serialization is both the stored column and the signed bytes; an empty set is typed-rejected. **THE TRUST ANCHOR, corrected in orchestrator review:** the worker verified the signature against the public key CARRIED BY THE TOKEN, which would have reduced the whole grant to a bearer secret - anyone who learned a grantId could sign with their own keypair and pass, making the signature decorative. Fixed by pinning the ISSUING identity key on the grant row at issue time (immutable, trigger-enforced) and verifying against THAT stored key; a token naming a different key is refused outright. Proven by test: an attacker re-signing widened scopes with their own keypair is now stopped at `bad-signature` and never reaches the claims comparison (the test states that a regression to `scope-mismatch` means the anchor is gone), while a token signed by the REAL issuer key with widened scopes still fails `scope-mismatch` - defence in depth catching a row edited around the trigger. Scopes are inside the signed payload, so a holder cannot widen them. Revocation is checked against the STORE on every verification because a signature cannot be un-signed: a cryptographically valid token for a revoked grant fails `revoked`. Verification order is structural, expiry (injected clock), store lookup, then anchored signature; a store throw maps to `store-unavailable` and NEVER to an authorization verdict. `grantAllowsScope` is exact-string membership (gm does not imply campaign; `team:alpha` does not match `team:alpha-2`) - no prefix wildcards.
