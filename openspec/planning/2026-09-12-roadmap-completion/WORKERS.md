## Assignments

Every worker receives:

- One concrete behavior or read-only question, bounded to a small module or explicit file list.
- The baseline head and exact task/requirement IDs, allowed paths, prohibited mutations, and dependency assumptions to verify.
- A reminder that the workspace is shared, other edits must be preserved, and no nested agents may be spawned.
- The expected failing/passing check and an artifact destination outside another worker's ownership.
- A stopping condition: complete the bounded task and hand back evidence, or report one reproduced blocker with the smallest next action.

Workers do not stage, commit, push, merge, edit unrelated specs/checklists, start competing servers/builds, or delete anything unless explicitly assigned that responsibility. Parent verification remains required after a worker reports success. An agent's confidence is not acceptance evidence.

## Review lanes and ciClass (2026-09-16)

Every unit in `units.json` is reviewed in two lanes, as DELIVERY.md step 5 defines them. Lane A is a cross-model agent review: the reviewer worker runs on a different model from the implementer worker and shares no context with it, receives only the diff, the evidence paths and the unit behavior, reproduces at least two mutants itself (the reviewer minimum of the 2026-09-15 section above), and returns a receipt recording `reviewerModel`, `implementerModel`, effort, the reviewed head and a sha256 of its output. A Lane A review is engineering evidence and is never recorded as a GitHub approval. Lane B is the owner ruling required for the authority, privacy, migration, replay, idempotency and concurrency classes and for any owner-gated unit; it arrives as a PR comment beginning `OWNER-RULING <40-hex head>` with the `owner-ruled` label, and it is void as soon as the head moves.

A unit carries a `ciClass` derived from its `ownershipPaths`. A `docs`-class unit owns only paths under `openspec/planning/**` or `docs/**`; docs-class units are combined into one PR and merged with the administrative merge the documentation lane already uses, because no product check can observe them. A `product`-class unit owns any other path and ships as its own PR with the full required check set on the exact proposed head. Combining a docs-class unit with a product-class unit is not allowed - the combined PR is product class and runs the full checks.

## Routing, install guard and restore rules — 2026-09-22

Implementation lanes run on Opus (Agent model opus); Lane A reviews run on Sonnet (Agent model sonnet), so the reviewer and the implementer are always different models. This supersedes the earlier dated routing preferences above; the latest dated routing instruction wins. On a lane's exhaustion or failure (rule added 2026-09-22): change one variable (model, scope or budget) before relaunching and never repeat an identical launch; re-run the local stage from the unit's existing red receipt rather than re-deriving red; and re-run Lane A on the resulting head, because a new head voids the earlier review.

Before any npm or npx command in a worktree except `npm run <script>` and `npm test` (so before every command that can change node_modules, among them install/i/add, ci, uninstall/remove, update, prune, dedupe, link, rebuild and exec/npx; the list is not exhaustive), run `npm run --silent qc:guard-node-modules-link` (or `node scripts/qc/guard-node-modules-link.mjs`) from the worktree root. Without `--silent`, npm prints its own banner lines to stdout before the guard's line, so never read only the first output line. Proceed only when the command exits 0 and prints a line that is exactly `INSTALL_ALLOWED`. Any non-zero exit, or any line starting `INSTALL_REFUSED`, stops the lane; the guard exits 1 on every refusal. A refusal line is `INSTALL_REFUSED`, then the reason word, then diagnostics only (a JSON object, or an error message for inspection-error). This convention is the guard's only caller today: no npm lifecycle script or other code invokes it; its only package.json entry is package.json:154 (the pin test scripts/__tests__/guard-node-modules-link.test.ts:256 asserts that entry). U12b shipped it as a CLI because npm runs a root preinstall after reify.

Never pipe `npm run build` through `tail` or any other filter; record the build's own exit code. In a junctioned worktree the hydration guard exits 1 by design (release-build-system spec.md:59-68), and a pipe reports the filter's status instead.

Restore a mutant with `git checkout HEAD -- <path>` and confirm the file's sha256 equals the pre-mutant hash before recording the mutant as restored. Under core.autocrlf a text-mode rewrite changes the file's bytes and breaks the sha256 match.
