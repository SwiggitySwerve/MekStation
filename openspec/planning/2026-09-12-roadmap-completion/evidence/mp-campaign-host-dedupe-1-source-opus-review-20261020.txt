## 2. Correctness

src/lib/multiplayer/server/CampaignHostRegistry.ts:422-440

- Check-then-set is atomic: getOrCreate is no longer async; get -> inFlight.get -> createEntry(...) -> .finally(...)
  -> inFlight.set all run synchronously in one turn. createEntry is an async arrow, so it runs synchronously only up
  to its first await (getMatchMeta) and cannot re-enter getOrCreate before the set; any synchronous throw inside it
  (including getDefaultMatchStore()) becomes a rejection, and is in fact caught to null by the existing try/catch.
- Cleanup: the stored promise is the finally-derived one, so every waiter observes settlement only after eviction;
  a caller that awaits a null/rejection and retries always starts a fresh attempt. Success, null and rejection all
  evict (mutants M3/M4/M6 caught).
- Identity guard (line 435): defensive. No code path can install a newer in-flight promise for a key while an older
  one is pending (set only happens when the key is absent, delete only in the owner's finally), so the guard is
  currently unreachable; mutant M5 (unguarded delete) is equivalent and survives by construction. Keep it: it matches
  MatchHostRegistry and protects any future clear/generation logic.
- Error propagation: one rejection is shared with every concurrent waiter (probe P5: identical error object to 3
  waiters, then a clean retry). The internal createEntry promise has a handler (.finally), and every production caller
  awaits the returned promise (bindCampaignSyncConnection.ts:283, ServerMatchHost.ts:1065, coopMissionCreate.ts:234),
  so no new unhandled-rejection path.
- Existing-entry reuse: unchanged (get() before inFlight). Durable recovery/journal: createEntry -> register(rebuilt:
  true) unchanged; concurrent first joins now share one paused rebuilt host and one durable journal instead of two
  hosts appending to the same campaign log (RED shows 2 registrations; head shows 1 for memory and durable stores).
- Returning GM / member join: new test drives noteGmConnected + joinMember on the shared entry; existing "lets the
  returning GM clear a rebuild pause" still passes.
- Deadlock check: nothing inside register() awaits getOrCreate for the same key (registerActiveCoopHost is synchronous
  and register does not await listeners), so sharing cannot self-deadlock.
