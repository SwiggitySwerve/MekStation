## 7. PRIV-1 / R-PRIV-1 evaluation

The parent analysis (admission receipt privacy.*; R-PRIV-1; merged #2245) is **correct**:

- Co-op campaign lobbies are listed with roomCode by GET /api/multiplayer/lobbies to any verified bearer (lobbies.ts:65; joinableLobbies.ts IJoinableLobby exposes matchId, roomCode, layout, hostDisplayName, occupancy, fogOfWar, createdAt). The room code is therefore not a secret for them. Confirmed by reading the code at head.
- verifyPlayerToken derives playerId from the embedded public key and consults no registry (auth.ts:178-193); a throwaway Ed25519 key passes. The test suite itself demonstrates this with generateKeyPairSync. Unscoped tokens are accepted because the scopeless branch is a transition residual (auth.ts:233-248) and token.ts:157 mints unscoped tokens. Requiring a scope would not add authorization, since the signer chooses its own scope; it only prevents reusing a *legitimately issued* token across sessions (confused deputy), which is vacuous for the server-minted unscoped tokens today.
- The gate is therefore "possession of a live code + ability to sign anything", i.e. no stronger than the anonymous summary in access terms; what G2A adds is the matchId -> campaignId correlation without a seat. That is exactly how the ruling describes it.
- v2.2.0 is loopback-only: server.js:72-79 refuses any HOSTNAME other than localhost/127.0.0.1 (standalone pins 127.0.0.1). Under that topology PRIV-1 is not a release blocker; the B15 hold is the right place.

Completeness additions (none changes the ruling):

1. **Co-op-ness bit.** With a live code and any self-signed bearer, 200 vs 404 reveals whether the lobby is a co-op campaign lobby. The lobbies listing does not expose a co-op flag, so this is a new bit — but strictly subsumed by the campaignId disclosure PRIV-1 already records.
2. **status/layout as oracles.** status is always 'lobby' (store filter) and layout is already in the anonymous summary and the lobbies listing. Zero new information.
3. **Timing/enumeration.** Crypto runs only after a live-code hit, so response time (and 404-vs-401) tells an unauthenticated caller whether a code is live. The anonymous summary already discloses liveness to anyone; code enumeration cost is unchanged from base (no limiter before or after). Not new.
4. **Cache.** private, no-store is set on every identity-mode outcome including 400/401/404 and 200 (18 of my mutant rows and 11 probe rows confirm); the only identity-mode response without it is the pre-mode 405, which carries no identity.
5. **Accountability.** The route does not log the verified playerId, so the "identity" gate currently yields neither authorization nor an audit trail. Worth considering alongside the B15 fix (CF-G2A-6).
6. **Bearer lifetime.** Up to 6h (token.ts:55); a revoked member keeps the correlation for the token lifetime. Already an accepted residual in the design doc.

**Does G2A make PRIV-1 worse than described? No.** Output beyond campaignId is already public; refusal bodies are constant strings with a single 'error' key; cache headers are on every identity outcome; HTTP writes nothing (afterEach store-equality invariant, verified in RED/GREEN runs and all mutant runs).

## 8. Five-class analysis

- **Authority — PASS.** HTTP claims no seat, membership, receipt or grant; the store is read once via getMatchByRoomCode and never written (afterEach equality on getMatchMeta plus createMatch/closeMatch never called). The expected scope is derived server-side from meta.matchId (:83-86), exactly as auth.ts:305-309 prescribes; the request cannot name its own scope. WS membership/revocation/seat authority is untouched (no WS/binder file changed).
- **Privacy — PASS with notes.** Allowlist built field by field (:96-101), never spreads meta (coopCampaign.state with full campaign state, seats, unitBootstrap, hostPlayerId all stay server-side; SECRET regex in tests, MR11 caught). Refusals disclose nothing (MR10 caught). PRIV-1 recorded as B15 hold; completeness additions in section 7.
- **Replay — N/A with reason.** The route is a pure GET read with no event stream, so event replay does not apply. Bearer replay within TTL yields the identical read-only answer; no nonce is needed because there is no effect to replay.
- **Idempotency — PASS.** Repeated identical requests produce identical responses and no state change; proven by the afterEach invariant across 30 rows and 12 mutant runs.
- **Concurrency — PASS.** Single store read with snapshot semantics; a lobby -> active transition between the read and the response yields at worst a stale 200 for a code the anonymous route would equally have resolved a moment earlier. No shared mutable state, no locks required.
- **State — N/A.** No durable state is written; the only state read is the existing room-code index/meta lookup that the anonymous route already performs.
