## 3. Code review of the change (src/lib/multiplayer/server/MatchHostRegistry.ts)

Shape: getOrCreate keeps the existing-open-host and quarantine checks, then consults inFlight (Map<matchId, Promise<ServerMatchHost|null>>). A miss publishes creation = createHost(...).finally(evict-if-still-mine) synchronously before any await, so every caller in the same tick and every caller until settlement joins the same promise. createHost is the previous body (getMatchMeta -> coop recoverActiveMatches(matchId) + get, or buildMatchHostBootstrapFromMeta -> ServerMatchHost.create -> hosts.set) with generation guards; recoverActiveMatches captures generation and refuses to register after _reset; closeMatch awaits a pending creation; _reset bumps generation and clears inFlight.

Properties checked against the brief:

- **N concurrent first connections -> one host, one adaptation, no store conflict.** Publication precedes the first await, so check-and-set is atomic per tick (mutant M4 shows the test catches a one-tick delay). Joiners receive the same promise and therefore the same host identity; adaptUnit runs once per unit (PR test asserts 2 for 1v1; my P1 asserts 2 with 8 joiners and 1 getMatchMeta read). Only one ServerMatchHost constructor runs, so only one persistInitialEvents, so no sequence collision and no stale lastBroadcastSeq=-1 drain -> no revision-conflict. Confirmed on the production image (section 6).
- **Failure clears the entry; no rejected promise cached.** The .finally callback runs before creation settles for any awaiter, so by the time a joiner resumes with null or a rejection the entry is already gone and the next call retries (M1, M3 killed; PR rows "missing metadata", "evicts a failed bootstrap", coop null/reject; my P2). The identity check (=== creation) means a late settle cannot evict a newer attempt (M7 survives, see 4).
- **No unhandled rejection.** createHost can reject only via the coop recoverActiveMatches path (getMatchMeta and bootstrap failures are caught and return null). The first caller always receives and awaits creation; every joiner awaits the same promise; closeMatch attaches .catch(() => null). My P2 registered process.on('unhandledRejection') around 6 joiners of a rejecting recovery: zero events, all 6 rejected, second call re-ran recovery. Rejection propagates to all joiners exactly as it propagated to the single caller before (bind does not catch; server.js does) - unchanged contract.
- **Durable recovery semantics intact.** bootstrapMultiplayerServer -> registry.recoverActiveMatches() is unchanged apart from the generation guard, which is a no-op unless _reset ran during the sweep (generation starts at 0 and only _reset increments it; production never calls _reset or _resetMatchHostRegistry). The sweep's hosts.set still honours an existing open host (idempotent). My P6 on a DurableMatchStore with one active match: first sweep recovered 1, second sweep recovered 1 and size stayed 1, two concurrent getOrCreate afterwards returned the recovered instance with zero ServerMatchHost.create calls - **recovered hosts are registered once and never re-created**. The MP-RECOVERY-UNITS-1 path (disk catalog in recoverServerInteractiveSession) is not touched; MatchRecovery.ts and matchUnitBootstrap.ts hashes are the merged #2296 bytes.
- **No cross-match blocking.** The map is keyed by matchId; PR row "does not block another match" and M2 (shared key) both exercise it (M2 fails that row by timeout plus the closeMatch row).
- **Eviction/close during creation.** closeMatch awaits the pending creation, then closes and deletes the landed host (PR row; M6 killed; my P3). Two pre-existing shapes remain and are not widened by this PR: (a) P3 - host.closeMatch marks the store completed, and a later getOrCreate on that completed match builds a fresh host (pre-existing: getOrCreate never looked at meta.status); (b) P4 - a retry that starts after a failed attempt but before closeMatch's continuation lands a host that survives the close (close-vs-create ordering, pre-existing). Both are recorded as carry-forwards, not in-PR.
- **MatchRecovery and the #2296 path vs a new connection.** Inside getOrCreate, the coop branch (meta.coopMission -> recoverActiveMatches(matchId)) is now covered by the same in-flight entry, so a socket and the coopMissionCreate REST call racing on the same coop match share one recovery (PR coop rows; my P2). The boot sweep itself is outside the map (as the admission review noted): if a non-coop getOrCreate for an active match ran concurrently with recoverActiveMatches(), my P5 shows the fresh host wins (createHost's hosts.set is unconditional; the sweep's set defers to it), the recovered host is dropped unclosed, and the fresh host's initial persist would collide. This is **unreachable on the delivered server**: server.js awaits runtime.bootstrapMultiplayerServer() (line 537) before createServer and before server.on('upgrade') (line 839) and server.listen (882), so no socket or REST getOrCreate exists during the sweep; recoverActiveMatches has no other production caller. It is a registry-level invariant gap, not a behaviour defect; optional fix in section 8, CF-MPHD-1.
- **First caller's options win.** Joiners' diceSeed is ignored (comment says so). server.js strips the seed in production, so no authority consequence; the PR test asserts the reuse case explicitly (seed 2 joins seed 1's host).
- **Generation guards.** They exist only for the test-only _reset seam the admission review required ("pending creation may resurrect a host after _reset"). The guard before ServerMatchHost.create means a stale attempt never constructs (so never persists) a host - the right fix. In the sweep arm, a stale result's hosts are discarded without closeMatch (they hold a campaign-pause binding and have resumed publications); closing them would mark the store completed, so dropping is the lesser evil, but it is a leak on a test-only path (CF-MPHD-2).
- **Authority/privacy.** No change to admission, viewer projection, fog, intents or wire frames; the registry still only hands back a host after the same quarantine and meta checks. Nothing a client sends influences the dedupe except the matchId it already supplies.

## 7. Findings by severity

### High / Medium
None.

### Low
- **L1 (invariant gap, not reachable in production): the boot sweep is outside the in-flight map and createHost's hosts.set is unconditional.** P5 shows a fresh host overwriting a just-recovered one if the two ever overlap. Guarded today solely by server.js ordering (bootstrap awaited before createServer/upgrade/listen). Optional 3-line fix in section 8 (A1); otherwise CF-MPHD-1.
- **L2 (test-only leak): a sweep that observes a stale generation discards recovered hosts without releasing them** (campaign pause binding, resumed publications). Only after _reset during a sweep. CF-MPHD-2.
- **L3 (proof gap, _reset seam only): M5b, M5c and M7 survive.** Optional rows in section 8 (A2).

### Informational / pre-existing (not introduced here)
- I1: getOrCreate ignores meta.status; a completed match (P3) or an active match whose recovery failed-but-not-quarantined (e.g. partial-history) gets a fresh host whose initial persist collides with the durable log - the same failure class as this finding but on a different trigger. CF-MPHD-3.
- I2: closeMatch now waits for an in-flight creation; DELETE /matches/:id latency is bound to bootstrap latency (previously it returned immediately with no host). Acceptable; noted so A2's restart/reconnect rows are not surprised.
- I3: CampaignHostRegistry.getOrCreate (bindCampaignSyncConnection, coopMissionCreate) has the same check-then-set shape (await getMatchMeta, then register); register() returns an existing open entry but two concurrent misses both build. Different registry, outside this unit's manifest. CF-MPHD-4.
- I4: The PR is three commits on f73bfe7d7 and is not rebased on current origin/main (9c2a8a088); no path overlap, three-dot diff is the merge; exact-main proof must run on the merge commit as usual.

## 8. Precise in-PR fixes (all optional; none required for the ruling)

**A1 (optional, source, ~3 counted lines, well inside 85/500):** in createHost, immediately before `host = ServerMatchHost.create(matchId, this.store, bootstrap);` add
```ts
      const landed = this.hosts.get(matchId);
      if (landed && !landed.isClosed()) return landed;
```
so a host registered by any other path while this attempt awaited (today only the boot sweep) is preferred and no second constructor (and no second initial persist) runs. Closing the window entirely would need the sweep's per-match registration to go through the same map; that is CF-MPHD-1 scope, not this PR.

**A2 (optional, test leaf, line-exempt):** three rows for the survivors: (i) coop meta + gate inside the mocked recoverActiveMatches, _reset while pending, expect the stale call to resolve null and registry.get to be null (M5b); (ii) gate the store's listActiveMatches, call registry.recoverActiveMatches(), _reset during it, expect recovered 0 and size 0 (M5c); (iii) _reset while A is pending, start B, resolve A, then a third getOrCreate must join B's promise rather than start C (assert create spy count 1 after B lands) (M7).
