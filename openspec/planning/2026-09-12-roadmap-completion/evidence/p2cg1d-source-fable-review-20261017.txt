## 5. Per-class findings

- **Authority.** No defect. The host-only check precedes the host door and the GM-only check precedes the decision door, both unchanged in position. The only activation switch is a server-side typed object installed by code (`installApplicationReceipts`), once, on an empty registry, with no setter and no uninstall; no envelope field, header or boolean reaches it. An approval is tied to the exact pending entry object by identity (`pending.get(proposalId) === entry`), so a timed-out, vetoed or closed proposal cannot be committed by an in-flight approval, and an approval cannot authorise a fresh attempt after an uncertain commit. The late refusal is recognised by exact shape, not by class or name, so a foreign-graph or spoofed object cannot be mistaken for one. The crossGraph case shows a graph that reaches the shared registry cannot substitute its own handle or preparation.
- **Privacy.** No defect; strictly less exposure than legacy. Every new wire reason is a kebab-case code from a closed set: the P2CB verdict union (`fresh-request`, `participants-behind`, `correction-pending`, `replacement-artifacts-unverified`, `branch-not-active`, `evidence-unavailable`, `history-integrity`, `context-mismatch`, `gm-required`), B's `append-controls-unsupported`, and D's `proposal-reservation-invalid`, `progression-unsupported`, `progression-reservation-busy`. The `participants-behind` arm's `participantIds` are dropped (RM7 caught); the legacy string sent `participants-behind p1:5,p2:7; requiredRevision 8`. Error frames keep the legacy shape (`code`, `reason`, correlation in the `intentId` field). The shipped client keys on `refusal.code` only (`campaignLifecycleState.ts:494, 588`), so code-only reasons change no client behaviour. The arbiter path's reason is regex-checked on the way out; the host-intent path forwards `outcome.refusal.reason` (typed `string`) unchecked, all of whose sources are constants today (N3).
- **Replay.** No defect. No new event type, reducer or journal field; refusals write nothing on C, on `campaign_public_applied_view` or on M (census over the real files is byte-equal before and after each refusal, including the drift refusal that rolls back inside the IMMEDIATE transaction); the committed path is B's unchanged verify-after-apply pipeline; a replayed duplicate answers its committed receipt and appends nothing (two cases).
- **Idempotency.** No defect. Duplicates replay before the guard at two layers (section 4, RM4); `release` and `consume` are idempotent and `afterRelease` re-running after `onCommitted` is a no-op; coalesced approvals produce exactly one guarded attempt (`commit` called once); a late-refused approval leaves the entry pending and a retry starts a fresh attempt without re-arming the timer (RM5 caught); the busy refusal is retryable on the same socket.
- **Concurrency.** One accepted residual, no active defect. Lock order is C IMMEDIATE (the writer) then M (the reservation inside the guard) on every new door (RM3 caught); M is held across C's COMMIT and released in the commit span (RM2 caught; author's commit-release mutant caught); the span from `reserve()` to either release contains no `await` (the guard, append, COMMIT and `onCommitted` run inside the writer's synchronous `.immediate()`); a throw from `reserve()` is a typed refusal (author's busy mutant caught) and `onCommitted` is always requested, so a borrowed transaction on C is refused by the writer (CF-D7). The host single-writer lock serialises the doors; two concurrent AdvanceDay intents with different ids prepare in parallel and the second's revalidate refuses `fresh-request`; the arbiter's `approving` entry is set before the attempt's first `await`, so a second approve cannot slip between. The residual is decision point 1.
## 6. Judgments on the author's decision points

1. **Post-admit append failure relies on C's microtask release.** Confirmed in code: `appendControlledCampaignBatch`'s extend runs the guard, then `append()`; a `revision-conflict` is a result (not a throw), so the transaction function returns, the writer COMMITs an empty transaction and calls the notification wrapper, which returns without calling D's `onCommitted` because `committed === null`; a throw from `append()` rolls C back and propagates to `commit-uncertain`. In both cases M stays in `BEGIN IMMEDIATE` past the end of the synchronous span until `holdMatchConnection`'s `queueMicrotask` release runs; `afterRelease` runs later (after `runExclusive` settles) and is a no-op by then. The hazard CF-D1 named is real in principle: any `db.transaction()` write on M that runs in that gap nests as a SAVEPOINT, reports success and is discarded by the ROLLBACK. **Ruling: an accepted residual on this head, not an active defect, with a named owner and a hard condition for activation.** Reasons: (a) the unit is dormant (no production installer; `server.js` untouched), so no production path can hold M at all; (b) the gap is bounded by the microtask queue and opens only on a post-admit append failure, which under the host lock means a second writer process or an I/O error; (c) for a foreign M write to land in the gap it must already be queued as a microtask between the span's enqueue and the C release microtask, which requires a chain started in the same macrotask, and the only same-macrotask companions of a campaign-sync frame are other campaign-sync frames (ws emits same-chunk frames synchronously; finding #78 relies on this), none of which writes M; match sockets, HTTP routes and timers are separate macrotasks. The fix cannot be made in D's leaves: B's extend owns the span. Register, before P2CG1H installs the port, an in-span hook `onNotCommitted?: () => void` on `ICampaignAppendControls` (B leaf `ICampaignEventStore.ts`), invoked synchronously by `appendControlledCampaignBatch` when `appended.kind !== 'committed'` and in a catch around `append()` (B leaf `JournalCampaignEventStore.ts`), passed through `ICampaignCommitControls` unchanged, and wired `onNotCommitted: release` in the binder (D leaf `bindCampaignSyncConnection.ts`, next owners I3 and P2CG2), with a trail case `[BEGIN, guard, ROLLBACK, tick]` for the admit-then-conflict path (RM9 today). P2CG1E's leaves do not include any of these files, so this is either a narrow new registration ahead of H or an explicit Root acceptance recorded at H's admission with this analysis. (CF-E1)
2. **Duplicate replay before refusal.** Correct and the right precedence: an intent already committed must answer its committed receipt regardless of present readiness, because authority was evaluated when it committed; re-gating a replay would turn an idempotent retry into a spurious refusal. Holds at two layers (doors and store); D's first case pins the observable.
3. **Port only in an empty registry.** Correct fail-closed design: it makes "an entry built without a launch view beside a flowing receipt port" impossible, which is the invariant the receipt mode needs. Consequence for the activation unit (P2CG1H): `ServerMatchHost.bindCampaignPause` calls `getCampaignHostRegistry().getOrCreate(sessionId)`, so durable active-match recovery in `runtime.bootstrapMultiplayerServer()` (`server.js:537`) can register campaign entries at boot; the install must precede that call, and the campaign SQLite service must be initialised before either, because `register` under an installed port throws when `journalDbOrNull()` is null. Loud failure, correct, but a boot-order trap. (CF-E5)
4. **C test 1 ms flake.** Reproduced: my run 1 failed `coopMissionCreate.test.ts:1158` (`saga.acquiredAt` 1792271877825 < `times.matchCommit` 1792271877826), runs 2 and 3 passed; the author saw the same 1-in-3. Cause: the parent samples `Date.now()` after `exec('COMMIT')` returns while the child, polling `BEGIN IMMEDIATE` every 2 ms, can acquire and sample within the same millisecond tick, so the two samples can differ by one tick in the wrong direction although the order is real. Not a D concern (the file and the code under test are unchanged by D) but a live CI risk: the case is in the `unit` project that the six CI shards run. Fix in E (owner of the file): sample the parent's `matchCommit` and `campaignRelease` in `traceExec`'s `before` hook instead of `after`, which makes `child.acquiredAt >= parentSample` hold for any monotone shared clock; two lines. (CF-E2)
5. **Reason-code-only refusals.** Correct; see Privacy. The legacy socket string carried participant ids and acknowledged cursors to the GM; D's carries a code; the client never parsed the string. One hardening left (N3).
6. **Registry restating the port type.** Acceptable with a note.
