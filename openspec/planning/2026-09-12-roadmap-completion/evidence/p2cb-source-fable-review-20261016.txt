## (2) Sensitive classes

**Authority / principal binding.** A preparation is bound by a module-private `WeakMap` (`:339-346`) to the view's handle, the captured `{campaignId, sessionId}` and the serialized inputs. `revalidate` never accepts a key from the caller; it re-reads the captured key. An object not produced by `prepare` (or a refused preparation, which is never captured, `:516-522`) yields `context-mismatch`. A preparation from graph B handed to graph A's view, or A's preparation on B's handle, is refused (two real graphs, `crossGraph.test.ts:386-388`). Reuse across campaigns is impossible because the key is captured, not supplied. A `refused` verdict short-circuits before any context check (`:534`) and is never credit. The viewer identity is derived server-side from the durable seat (`isGm: member.seat === 'gm'`, `:424-427`) and bound through `campaignViewerAuthorityFingerprint(member, viewer)` (`:447-448`), so a row minted under an older membership incarnation (different `boundAt`) earns nothing (test `:752-760`).

**Privacy / withholding.** Each participant's hydration state is `projectCampaignForViewer` over the full verified history with `campaignScopeAdmits` for that seat, so withheld facts never enter the fold and the baseline latch (`campaignViewerVisibleEvents`) applies; mission launches are selected from the visible set only, ceiling = the visible set's own max `sequence`, never a journal revision (`:456-460`; test `:567-602` proves a replayed child whose sequences are not revisions). The public preparation has exactly two keys (`verdict`, `hydration`), carries no revision, digest, receipt or fingerprint, and `verdict.participantIds` names only retained session members. Refusal reasons are closed enums; the only error text that can escape is a rethrown non-branch driver error (N3). No new `console` output in product code.

**Replay / determinism.** `grep` over the three product leaves finds no `Date.now`, `Math.random` or `new Date` in the new code; the single `new Date().toISOString()` at `campaignPublicAppliedView.ts:272` is P2CA's pre-existing `appliedAt` stamp in `accept`, not a P2CB decision path. The verdict is a pure function of captured inputs and verified history; `JSON.stringify` key order is stable because every object comes from fixed SELECT aliases or literal object shapes, and the roster SELECT is ordered (`seat, bound_at, participant_id`).

**Idempotency.** Repeated `prepare` creates independent captures (GC'd with the preparation). Repeated `revalidate` on unchanged inputs returns the same verdict with no write; after inputs change it returns `fresh-request` every time, never a stale `ready`. `accept` (P2CA) is untouched; P2CB never calls it.

**Concurrency.** The TOCTOU window between `prepare` and `revalidate` is closed by full input re-read inside the caller's transaction (hidden append, seat revocation, branch/generation change, a competing ack and a rolled-back ack are each tested). The post-await `currentDb` re-check (`:509`) catches a service reset during the await; a reset after capture is caught in `revalidate` (`:537-538`) because the new service handle is not `this.db`. The saga probe and SELECT in the strict reader are two statements outside a transaction; benign, as the table is never dropped and a table created in between only makes the SELECT succeed (registration review N4, still true at head).

**Saga change trace (`CoordinatedOutcomeCorrectionSaga.ts:378-415`).** Strict reader: `sqlite_master` probe -> absent table returns `null` (known absence) without migrating; otherwise the same SELECT; every other failure throws. Legacy `readCoordinatedCorrectionSagaByOutcomeId` now wraps strict in the same `try { } catch { return null }` (`:381-386`), so for every input class (no row, absent table, closed handle, busy) it returns exactly what it did at base; its sole production caller `readDurableSagaForCampaign` (`durable.ts:189-199`) and the legacy inbox reader (`:201-209`, now a `try/catch` over the shared strict core) are behaviour-identical to base. `createDurableCampaignProgressionReaders` (consumed by `CampaignHostRegistry.ts:296` and `campaignLaunchAuthorityRoute.ts:263`) returns the same null-on-uninitialized answers; the `readManifestVerdict` null check merely moved from the helper into the closure (`:75-83`). The lazy-table invariant is documented in the strict reader's docblock and verified at head: `migrateCoordinatedCorrectionSaga` is called only from the saga operations (`:226, :309, :365, :422`) and `CoordinatedOutcomeCorrectionTarget.steps.ts:143`; `DurableMatchStore`'s constructor runs only `migrateMatchStoreSupersession` (`DurableMatchStore.ts:675`). Strict precedence: zero inbox rows -> `clear`; inbox outcome but non-durable match store -> `unavailable` (fail closed, `durable.ts:146-148`); absent saga table -> `clear`; open saga -> `blocked/correction-pending`; closed store or dropped inbox table -> `unavailable` (`crossGraph.test.ts:165-205`).

## Findings

1. **N1 - minor - `src/lib/campaign/sync/campaignPublicAppliedView.ts:555` exceeds the 400-line soft max (488 counted, 555 physical).** Two responsibility clusters now share the file. Accept in this PR as a registered-owner exception (closed six-leaf restriction; single typed owner is the contract); Root should register a facade-preserving split (`campaignLaunchView.ts` or similar, re-exported from the owner) as an ordinary successor before P2CE/Task 14 add callers. Rationale and spec citations in section (3).

2. **N2 - minor - strict precedence maps a manifest read failure to `blocked/replacement-unverified`, not `unavailable`.** `readDurableManifestVerdict` (`durable.ts:231-249`) catches everything as `unverified`, and the strict port reuses it (`:127-128`). Only reachable when a saga is `completed` with a `candidateBranchId`; the launch is refused either way, so this is fail-closed with a less precise reason. No change required for P2CB; worth a one-line note when Task 14 maps reasons to user-facing text.

3. **N3 - minor - a non-branch driver error during the awaited materialization escapes `prepare` as a thrown error rather than a typed verdict.** `integrityRefusal` (`:369-373`) rethrows anything that is not an `EventHistoryBranchError`, so a handle closed mid-await (service reset while materializing) rejects the promise instead of returning `context-mismatch`. The post-await `currentDb` check (`:509`) covers the reset case once the read completes. Still fail-closed; the caller (Task 14) must treat a rejected `prepare` as not-ready. Documenting this in the class docblock would be enough.

4. **N4 - info - campaign-level removal is permanent for the participant id across every session of that campaign.** `removed` is keyed by `payload.participantId` only (`:411-416`), while seat rows are per session. This matches the system: `bindCampaignSessionParticipant` refuses to readmit a revoked participant (`CampaignSessionParticipantStore.ts:100-105`) and no readmission event exists in the vocabulary, so there is no path by which a removed id legitimately returns. If a readmission event is ever added, this set must be made order-aware.

5. **N5 - info - `listRoster` ignores the handle argument.** The port is `listActiveCampaignSessionParticipants`, which reads `getSQLiteService().getDatabase()` directly. Correct today because both `prepare` (`:487`) and `revalidate` (`:539`) first prove `currentDb() === this.db`, and the read is synchronous, so the service handle is the checked handle. The owner's `readLaunchInputs(db, ...)` signature suggests the roster is read on `db`; it is, but by equivalence rather than by argument. A one-line comment on the port would prevent a future port from silently reading another handle.

6. **N6 - info - stable-suite log timing.** Run 2 (`round2-test-stable.exit.txt`) ended 2026-10-15 19:09:56 -0600 with exit 0, 2795/2795 suites, 37067 passed, 50 skipped; the commit `fcf0261a` is timestamped 19:10:40. Run 1 is correctly marked invalid: 468 `ROADMAP VALIDATION FAILED` lines, 120 failures, caused by a receipt path registered before the receipt existed; run 2 has none.
