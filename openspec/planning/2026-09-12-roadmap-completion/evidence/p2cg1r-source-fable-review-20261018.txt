## Source review (five classes)

Key sites: `src/lib/campaign/sync/JournalCampaignEventStore.ts:323-329` (`signalNotCommitted`), `:363-370` (capability detection), `:379-413` (extension body), `src/lib/multiplayer/server/CampaignMatchHost.ts:627-648` (forwarding), `src/lib/multiplayer/server/bindCampaignSyncConnection.ts:849-888` (binder `release` / controls), `src/lib/events/journal/SQLiteEventJournalWriter.ts:63-84` (unchanged writer; `db.transaction(...).immediate()`), `src/lib/multiplayer/server/DurableMatchStore.ts:1822-1851` (unchanged `holdMatchConnection` with its microtask safety net).

### Release exactly once, never early, never on success

- **Never before guard admission.** The hook is reachable only after `recorded` is false and `guard(db)` returned `null` (`JournalCampaignEventStore.ts:385-390` return before the `try` at `:393`). A guard refusal releases inside the guard itself (`bindCampaignSyncConnection.ts:872`); a throwing `revalidate` releases and rethrows (`:875-876`); a throwing `reserve()` never set `held` (`:865-867`). A thenable guard result throws from `rejectPreparedThenable` outside the `try`: the hook does not fire there (pre-existing B behaviour; the binder guard never returns a thenable). Mutant RM12 (author) and RV7 (mine) confirm early/success firing is pinned.
- **Never on success.** The committed path returns at `:409` without signalling; the `onCommitted` notification (consume then release, `bindCampaignSyncConnection.ts:879-885`) fires only after the writer's real COMMIT. RV7 (signal after a committed append) is caught by 4 rows.
- **Never on a recorded retry.** `if (recorded) return append();` (`:385`) short-circuits before guard, hook, `afterCommit` and `committed`; semantically identical to the pre-R `!recorded` conditions. See RM9/RV3 below for the reachability caveat.
- **Exactly once.** One signal per non-commit: either the `kind !== 'committed'` branch (`:395-397`) or the `catch` (`:410-412`), never both (the branch returns before the catch can see anything). Adapter test asserts `signals() === 1`; RV1 (double signal) is caught by 3 rows. The binder's `release` is idempotent (`held = null` before `hold?.release()`), and `holdMatchConnection`'s own `release` is idempotent on its `held` flag, so the later `afterRelease` and the reservation microtask are harmless no-ops after an explicit release.

### Hook ordering vs transaction state

- Conflict: `append()` returns `revision-conflict` with no rows written; hook fires while C is still open (trail `M:ROLLBACK:C-open=true`); better-sqlite3 then COMMITs an empty C. Releasing M before the empty COMMIT is safe: M protects revalidate-plus-commit of a batch that will not exist.
- Throw (native abort or throwing `afterCommit`): hook fires in the `catch`, then the original error is rethrown unchanged (RV11, swallowing it, is caught by 8 rows; RM13 by the author), and better-sqlite3 ROLLBACKs C. A throwing `afterCommit` after `append()` wrote rows is correctly treated as not committed because the rethrow rolls C back.
- A throwing hook never replaces the outcome (`signalNotCommitted` swallows; RM10 caught). See N2 for the missing diagnostic.

### Interaction with the later fallback release

Three releases can target the same hold: the synchronous hook, `afterRelease` (after the host lock is released, `CampaignMatchHost.ts:455-460`) and `holdMatchConnection`'s microtask queued at `BEGIN IMMEDIATE`. With R the first wins and the other two are no-ops; the receipt's "retain idempotent onCommitted/afterRelease cleanup and the reservation microtask fallback" is accurate. The only path on which the fallback still does real work is the outer-COMMIT failure (below).

### Foreign-writer interleaving at BEGIN IMMEDIATE

The hazard (H-OPEN-1): a foreign write on the match connection issued after the guard's `BEGIN IMMEDIATE` but before the late release nests as a SAVEPOINT under M and is discarded by the microtask ROLLBACK. The tests reproduce it faithfully: the `exec` spy queues its tick microtask **before** `holdMatchConnection` queues its own release microtask, so at RED the foreign row is written under M and discarded (`foreignRows() === 0`); at GREEN the release precedes the tick and the row commits on its own. Because JS is single-threaded and the whole extension is synchronous, no foreign write can interleave between `BEGIN IMMEDIATE`, the guard and the hook; a foreign writer that already holds the connection makes `holdMatchConnection` throw and the guard answers `progression-reservation-busy` (unchanged, pinned by the P2CG1D row "answers a busy match connection as a typed refusal").

### Error classification preserved

Conflict -> `sequence-conflict` -> `lost-race` -> `CAMPAIGN_STALE_HEAD` (binder rows assert the frame and no close); throw -> rethrown -> commit-uncertain -> socket closes `1008 dispatch-failed`; neither becomes a refusal (`CAMPAIGN_NOT_CONVERGED` asserted absent). Binder `consumed()` is 0 on every non-commit (RM8 caught).

### Outer-COMMIT-failure residual (honestly bounded)

If the extension returns `committed` and the writer's COMMIT then fails, `.immediate()` throws after the extension: neither `onCommitted` (correct - nothing committed) nor `onNotCommitted` (not observable from inside the extension) fires; M is released by the reservation microtask (before `afterRelease`, which runs after the host lock). The hazard window therefore survives only on this path, which on this WAL database with a write lock already held is reachable via deferred-FK failure, `SQLITE_FULL`/`IOERR`, or `BUSY` on checkpoint - exactly the receipt's boundary. Closing it needs a writer-level change (a commit-failure callback around `.immediate()`), which R correctly did not make; see CF-R-4.

### Authority / privacy / replay / idempotency summary

- **Authority:** the hook is a server-only control on `ICampaignAppendControls`; it is never on the wire, never client-suppliable, and reaches the store only through `applyHostIntentWithControls` from the binder's three AdvanceDay doors. A hook-only control on a journal/store without the capability fails closed before any write (adapter + pipeline rows; RM4/RM6 caught).
- **Privacy:** `() => void` carries no data; no new frame, log or payload field. The abort-path close reason is the pre-existing `dispatch-failed`.
- **Replay:** command identity, batch, payload and digest are untouched (controls are not part of `toJournalBatch`); a recorded command replays its stored batch before guard/hook; census/day/head unchanged after every failure; the same host intent then commits exactly once.
- **Idempotency:** release idempotent at two layers; `consumed()` only on a known commit; duplicate-first order preserved.
- **Concurrency:** covered above; the hook runs inside the host single-writer lock and inside C, before any await.

### RM9 / CF-R-2 assessment

The author's survivor RM9 (drop `if (recorded) return append();`) is **not an equivalent mutant**. So one row closes the class. Reachability in production is confined to a concurrent writer on the same campaign journal outside the host's single-writer lock, which today does not exist; severity Low.
