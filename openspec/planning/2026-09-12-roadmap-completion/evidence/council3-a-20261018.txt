## B. Co-op campaign lobby discoverability (PRIV-1)

Players perceive a co-op campaign as a private table; the room code *is* the invitation. A public browser row with "Join" and the code makes the invite meaningless and lets an ordinary 1v1 joiner take the human seat meant for the campaign guest (experience hazard, not just privacy). `isJoinable` checks only lobby status, code, layout and an empty human seat; co-op vessels pass because `CampaignCoopEntryPanel` creates them as `1v1` with `hostSeatKind 'spectator'`.
- "List without code" fails: `defaultCoopCampaignName(roomCode)` returns `Co-op Campaign <roomCode>`, so the name leaks the code, and existence of a private game is still advertised.
- The fix is one predicate: `meta.coopCampaign` is set at creation (`matches/index.ts:247`), so `getJoinableLobbies`/`getSpectatableMatches` can exclude `coopCampaign`/`coopMission` vessels. Invite-code joining is a direct lookup and unaffected.

This is a small privacy-class unit, not routine B15-6 (its admission note says so): `joinableLobbies.ts`, its test, a `securityBoundary.test.ts` row for an authenticated stranger without a campaign seat, units.json, evidence slots; about 6/15 files, well under 100 lines. Not an L1 blocker under same-host topology, but the highest privacy value per line in the backlog. Separately (routine): stop embedding the code in the default name.

Recommendation: hide co-op campaign vessels and co-op mission matches entirely (invite-only); register a 6-file "PRIV-1" unit after U38, before B15-0; B15-6 keeps only the documentation sentence.
Owner question (if any): None; this follows from "room code is the invite".

## C. Fog design: incremental reveal effects from GM state to player state

Reading of the direction: the server/GM state is the only full state; each player holds a *knowledge state* that changes only through explicit reveal/lose effects the server emits when something happens (movement, LOS, sensors, GM grant). The client never computes fog from data it should not hold. Today is the inverse: `GameCreated` ships every unit to every viewer, the client rebuilds full state, then the token layer hides some of it (`fogStatus 'hidden'|'lastKnown'`, `unitStateToToken.ts`). Observer-visible filtering is sound but cannot say "you now see X at hex H" because the player never legitimately had X. Tabletop double-blind (Tactical Operations) works exactly as the owner describes: the referee holds the map, players are told contacts as they appear, a lost contact becomes a last-known marker.

Shape:
1. **Viewer knowledge fold** (pure, `src/utils/gameplay/`): `foldViewerKnowledge(events, viewerId, policy)` folds canonical events through the existing `canPlayerSeeUnit` and yields a deterministic effect stream: `ContactRevealed {unitId, side, snapshot per intel policy}`, `ContactUpdated`, `ContactLost {lastKnownPosition}`, `IntelGranted` (GM allowance). Effects are derived, never appended to the canonical journal; replay, rejoin and rewind re-derive them, so one authority remains and per-viewer rewind digests (U26/P5) are simply digests of folded knowledge.
2. **Own-side opening**: fog-on `GameCreated` to a player carries own/team units plus public config/terrain; enemies arrive only via `ContactRevealed`. This also fixes the metadata route by construction (B14-HEAD stays as interim guard).
3. **Server emission** in `ServerMatchHostEvents`/`Replay`: after each canonical event, diff per-viewer knowledge and send effects through the existing per-viewer delivery numbering; the spec's Opponent Intel Policy (open/rough) decides snapshot content.
4. **Client partial state**: the reducer accepts contact records (minimal `IUnitGameState` tagged by fog status); the existing token layer renders them unchanged; ghosts come from `ContactLost`, not local inference.
5. **Team/GM/spectator**: trusted per-unit owner map (U38) with team-shared sightings; GM sees all; fog-on spectators get the GM view only on the host/GM seat, otherwise stay refused (S/B10 preserved).

Mapping: B14-0 and B14-HEAD remain the interim fail-closed guard; U26 becomes "fold at both heads and digest" instead of a bespoke probe; P5 2.5 "Rewind Preserves Viewer-Specific Hidden State" and tasks 34-40 consume the same fold; U2 E2E-19..30 become the chain's acceptance; `fog-of-war/spec.md` gains a "Viewer Knowledge Effects" requirement.

Implement the refusal as a capability predicate in the new leaf `fogMatchAdmission.ts` ("no reveal projection for this match") rather than `config.fogOfWar === true` checks in six leaves, and phrase the spec delta "until a per-viewer reveal projection exists". Delete nothing in `fogOfWar.ts`/`visibility.ts`; the chain reuses them.

Units (15/500 plausible each): **FOG-1** fold + effect types + tests (pure utils, 6-8 files). **FOG-2** own-side `GameCreated` and metadata projection, lifting the refusal for players only (about 12 files). **FOG-3** live/replay/rejoin emission + client partial-state reducer and token wiring (split client/server if over cap). **FOG-4** team ownership, GM view, `IntelGranted`, spectator policy. **FOG-5** U2 E2E-19..30 fog rows and spec sync.
