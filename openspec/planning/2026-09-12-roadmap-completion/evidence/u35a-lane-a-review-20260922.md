## Safety of swallowing F-1

The try/catch in `recordFirstCommandOnMarker` (campaignCommandPipeline.ts:347-360) wraps only the marker `.read`, the pure `recordFirstJournalAuthorityCommand` transition, and the marker `.write` — three synchronous, already-in-memory operations. It does **not** wrap the append: `acknowledgeCommit` is called only after `store.getEvents`/`appendCampaignCommandBatch` (or `appendDurableAcceptContract`) have already resolved to a committed batch; a pre-commit failure (validation, conflict, the append itself failing) returns from `executeCampaignCommand` through entirely separate branches (`rejected`/`conflict`/`blocked`/`duplicate`) before `acknowledgeCommit` is ever reached, so none of those paths pass through this catch. A swallowed failure leaves exactly one thing null: `firstJournalAuthorityCommandId` on that campaign's marker (confirmed by row (b): `storedMarker(id).firstJournalAuthorityCommandId` is `null` after the injected failure). I grepped every reader of `firstJournalAuthorityCommandId` in `src/`: the only reader besides the writer itself is `rollbackToSnapshotAuthority` (campaignAuthorityMigration.ts:328-351), used from `campaignAuthorityCutoverOps.ts` (an operator tool). Its first guard returns `rollback-prohibited` if the stamp is non-null; a null stamp (from either "no command has committed yet" or "a command committed but the stamp write failed") falls through to a *second*, independent guard: `journalHighestSequence !== baselineHead`, where `baselineHead` is `-1` for any marker with `importedBaseline === null` (journal-native or adopted). For a journal-native or adopted campaign, the genesis event already occupies sequence 0, so `journalHighestSequence >= 0 !== -1` the moment any event exists, and rollback is refused by the second guard regardless of the first. So a null stamp caused by a swallowed marker-io failure does **not** let a rollback through for a journal-native or adopted campaign — the second guard's own semantics (journal head must still equal the recorded baseline) independently blocks it. I did not find a reader that treats a null stamp as "no command has committed" in a way that would authorize an action a real committed command should have blocked.
