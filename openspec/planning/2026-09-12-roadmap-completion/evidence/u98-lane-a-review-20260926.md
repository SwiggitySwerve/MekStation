1. **[PASS] Q1a — one projection at a time per session, proven by the guard, not by assumption.** `campaignGrantChannelSession.ts:96` `private position`; `:100` `private draining = false`; `:191-192` `if (this.draining) return; this.draining = true;`; `:202` `const result = await this.projectCurrentCursor();` is the only call site inside the loop and is `await`ed sequentially (no `Promise.all`/fire-and-forget); `:133` is the only other call site, run once in `start()` before `pendingWake`/`liveReleased` let any wake reach `drainLive`. Node's single-threaded event loop plus the `draining` re-entrancy guard means a second `drainLive()` invocation returns immediately at `:191` and the flag it set (`pendingWake`) is picked up by the loop already running — no two `projectCurrentCursor()` calls (the only place that reads `this.position` at `:314` and writes it at `:333`) are ever in flight for one session.

2. **[PASS] Q1b — page boundary cannot skip or repeat a row.** `projectCampaignStreamForGrant.ts` `readCampaignJournal` (`:132-159`, confirmed via `git show 61ae10ea8...:...` after the cwd mistake in Setup) starts `afterRevision = fromRevision` (the kept position, or 0) and re-issues `journal.readStream({ afterRevision, limit: EVENT_JOURNAL_MAX_PAGE_SIZE })` each turn, continuing from `last.streamRevision` (the true last row actually read, not a computed count) until a short/empty page. `SQLiteEventJournal.readStream` (`src/lib/events/journal/SQLiteEventJournal.ts:20`) is `WHERE ... stream_revision > ? ORDER BY stream_revision LIMIT ?` — strictly exclusive, ascending, so successive pages can neither skip nor repeat a row. `hostCampaignEventJournal.ts:93` passes `query.afterRevision` straight through as `fromSequence`; verified the semantics line up by reading `ICampaignEventStore.ts:21-22` (`getEvents` returns `sequence >= fromSeq`) and `InMemoryCampaignEventStore.ts:137-146` (`fromSeq <= 0` -> full slice, else `sequence >= fromSeq`): since `streamRevision = sequence + 1`, `sequence >= afterRevision` is exactly `revision > afterRevision`. No off-by-one. I independently reproduced an off-by-one at this style of boundary (see Q6/Finding 8 below) and it was killed by the equivalence test.

4. **[PASS] Q1d — the withheld latch's meaning is unchanged and correctly carried.** `projectCampaignStreamForGrant.ts:288-290` `let withheld = from?.withheld ?? false;` then `:298-299` (`if (!admits(event.scope)) { withheld = true; continue; }`) and `:307-312` (`campaignBaselineReachesViewer(event, admits, withheld)`). The latch is monotonic *within an epoch*: once an out-of-scope fact is seen, every later `CampaignSnapshotPublished` baseline is withheld too (a restricted grant "receives any other baseline only while nothing withheld precedes it" — comment at `:302-306`, matches the code exactly), but ordinary later in-scope events are still delivered. 5. **[PASS] Q1e — the opaque token cannot be forged or replayed to leak a position.** `campaignDeliveryTypes.ts:76,84-85` brands `CampaignGrantProjectionPosition` as an unconstructible unique-symbol type with no runtime-visible fields; `projectCampaignStreamForGrant.ts:100-113` keys the `WeakMap` on the frozen empty object identity (`:357` `Object.freeze({})`), not on any string/number a caller could mint. The position is never placed on `IProjectCampaignStreamPage`'s wire-adjacent siblings and never crosses the socket (confirmed the delivery boundary test, `campaignDelivery.boundary.test.ts`, scans public result types for journal-position-shaped fields and passed in the full jest run below). A caller handing in an object not in the map just gets `kept = undefined` -> full read from 0 (`:275-276`) — a safe fallback, not an info leak. Because each `CampaignGrantChannelSession` only ever re-passes its own private field back for its own fixed `grantId` (`:88-96,314`), cross-grant mixing does not occur in the one caller that exists.

6. **[PASS] Q2 — the replica store's kept head is a true lower bound; no concurrent writer can be missed.** `SQLiteCampaignReplicaStore.ts:92-96` `heads` is a per-instance `Map<streamId, {revision, durable}>`; `readDurable` (`:245-259`) reads rows after `head.revision` (default 0 for a new instance/new stream id — "a second instance starts from a full read" holds because `heads` is instance-scoped and there is no persistence), folds them (`foldReplicaEnvelopes`), and sets `heads.set(streamId, {revision: last.streamRevision, durable})` from the *actual last row read*, never a computed/assumed count. Since the append path uses `expectedRevision` optimistic concurrency and the underlying table is append-only (root-branch, no update/delete triggers per the admission receipt's `journalSinceRead`/`hostLogSinceRead` seam notes), any writer's new rows land at revisions strictly greater than what was last read, so the next `readStoredEvents(streamId, head.revision)` call (`:269-289`) picks them up; nothing between 0 and `head.revision` can have been missed because `head.revision` was itself set from a row this instance actually saw. No stream reset exists in the product code (`Nothing resets it: the stream is append-only, and a new instance starts with a full read`, `:88-90`); the only reset (`InMemoryCampaignEventStore.ts:161-164`) is test-only isolation on a different store, not reachable from this path.
