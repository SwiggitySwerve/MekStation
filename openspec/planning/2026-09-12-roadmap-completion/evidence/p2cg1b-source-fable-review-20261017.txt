## 2. Behaviour review (per registered behaviour)

**Writer (`SQLiteEventJournalWriter.ts`).** One private `validatedIdentity` (schema parse, `canonicalizeCommandIdentityV1`, duplicate-eventId throw) is now the single body shared by `append`/`appendWithExtension`, `appendPreparedWithExtension` and the new synchronous `appendInBorrowedTransaction`. The borrowed operation throws `Borrowed append needs an active transaction to join` when `db.inTransaction` is false and otherwise calls `appendInTransaction` directly: no `db.transaction(...)`, no `.immediate()`, no BEGIN/COMMIT/SAVEPOINT, no notification (tests: rows visible inside the caller transaction and gone after the outer throw; durable only after the outer commit and visible after reopen; a released nested savepoint is not durable; duplicate ids throw before writing; revision and identity conflicts stay typed). `appendWithExtension` gains an optional third argument `onCommitted(result)` invoked synchronously after `.immediate()` returns and before the promise settles; the pre-write check `onCommitted !== undefined && this.db.inTransaction` refuses a notification request when the wrapper would be a savepoint. `appendPreparedWithExtension` still owns its own IMMEDIATE transaction and is untouched apart from the shared body; `rejectPreparedThenable` is exported unchanged. Existing 2-argument callers (`campaignCombatOutcomeInbox.ts:87`, the adapter's legacy `afterCommit` path) are behaviour-equivalent: with no notification requested, nesting still degrades to a savepoint exactly as on the baseline (see N1).

**Store contract (`ICampaignEventStore.ts`).** `ICampaignAppendRefusal {kind:'refused', reason}` is a structural result arm; `CAMPAIGN_APPEND_CONTROLS_UNSUPPORTED = 'append-controls-unsupported'`; `ICampaignCommittedBatch` is the plain identity (campaignId, commandId, commandDigest, first/last commit position, eventCount; no payload); `ICampaignAppendControls {guard?, onCommitted?}` is a separate argument; `appendControlledCommandBatch?` is an explicit optional capability. `InMemoryCampaignEventStore` is untouched and therefore not capable (asserted by test). The new `import type Database from 'better-sqlite3'` is type-only and follows the pattern already used by 14 other `src/lib/campaign` modules including the adapter itself; no browser module (`src/components`, `src/pages`, `src/stores`, `src/hooks`, `src/pages-modules`) imports `ICampaignEventStore`.

**Adapter (`JournalCampaignEventStore.ts`).** `appendCampaignCommandBatch` keeps its exported signature as a thin wrapper over the renamed body `appendControlledCampaignBatch(journal, input, afterCommit, controls)`; a `refused` result on the uncontrolled wrapper throws (unreachable with `{}` controls). Order inside the body: `toJournalBatch` (no controls in it) -> capability check (`controlled && !(journal instanceof SQLiteEventJournalWriter)` returns the typed refusal before any write) -> `appendWithExtension` whose extension does: recorded-id check -> `guard(db)` only when unrecorded (thenable rejected, non-null returned as the refusal without calling `append()`) -> `append()` -> legacy `afterCommit` in SQL (still rollback-capable) -> frozen `committed` identity built inside the transaction -> `onCommitted` fired by the writer after COMMIT with a throw captured into `notificationError`. The `committed`/`notificationError` captures are per-call `let`s, so concurrent calls cannot cross-talk. The class keeps branch-before-duplicate and prior-receipt order for both `appendCommandBatch` and `appendControlledCommandBatch`, so an exact retry answers from the receipt without reaching the guard or the notifier (test: guardCalls 1, notified 1 across two calls).

**Host (`campaignHostBatchCommit.ts`, `CampaignMatchHost.doors.ts`, `CampaignMatchHost.ts`).** `CampaignCommitOutcome` gains `refused {refusal}`, `commit-uncertain {commandId, error}` and `committed-unsettled {commandId, events, errors}`. `resultOfCommit` is a `switch` whose `default` hands the failure arms to `throwCommitFailure(outcome): never` (typed `Exclude<..., committed | lost-race>`), so typecheck proves no arm is dropped; `announceMissionLaunched`, `_commitEventsForTests` and `openLocked` go through it; `creditSalvagePoolLocked` and `applyRosterUnitChangeLocked` go through `resultOfCommit`. `applyReconcileEvents` named by the research scope does not exist at this baseline (grep empty), as the admission's B-OPEN-4 recorded; the only outside-leaf consumer (`campaignRetroactiveCorrectionCommit.test.ts:396-411`) narrows with `kind !== 'committed'` and compiles unchanged. In `commitCampaignEventBatch` an append rejection is caught once and returned as `commit-uncertain` with the `commandId` the append was asked to record (projection untouched, nothing published); a known commit drains notification error, divergence, rebuild failure and each publish failure into `errors` in that order and returns `committed-unsettled`; the batch is never compensated, deleted or re-appended. `commitEvents` refuses `guard`/`onCommitted` before the first event whenever `eventStore.appendControlledCommandBatch` is absent, which covers the plain batch store and the per-event `commitCampaignEventsInSequence` fallback (test over both). `applyHostIntentWithControls` runs `applyHostIntentLocked(ctx, intent, controls)` under `runExclusive` with the same isClosed -> replay -> validate -> commit order (the diff only wraps the early returns in `answered`), then runs `afterRelease` exactly once after the lock settles and folds its failure as described in section 6 item 2. `handleIntentLocked` (the guest wire path) accepts no controls. The actual-commit notification is distinct from the legacy in-SQL `afterCommit`/`rewriteRecordAfterCommand` hook, which is preserved as a transactional extension (test: a throwing rewrite rolls back with no notification).

## 6. Judgments on the author's decision points

1. **commit-uncertain leaves the live projection untouched; readback is the owner's.** Correct. The projection was never moved before the append (scratch `expected` only), so leaving it is the baseline behaviour; a speculative re-read inside the door would have changed the existing `campaignHostSerialization` poisoned-store case, as the author found. The arm carries `commandId` and the original error, which is exactly what readback needs; `getCommandReceipt` resolves both directions in the tests. Note that the classification is deliberately conservative: a *known* pre-write throw (guard throw, thenable guard, stale branch, saved-record rewrite throw) is also reported as `commit-uncertain`, so the only "nothing was written" signal with certainty is the typed `refused` arm. That is fail-safe (readback finds nothing and the command may be retried under the same identity), but D's guard should return refusals rather than throw if it wants the precise arm (CF-C2). Accept.
2. **Cleanup failure classification.** Accept. `committed` + cleanup failure -> `committed-unsettled` with the intent's identity (null only when none exists) is the honest reading: the batch is durable, something after it failed. Two sharp edges, neither blocking: (a) a `lost-race`, `refused` or `commit-uncertain` outcome plus a cleanup failure is converted into a thrown `AggregateError` whose `errors` holds only the cleanup error and whose `cause` holds the outcome, so the primary uncertain error lives one level down and an answerable lost race becomes a throw; (b) D must read `cause` to recover the outcome. Record as M3 (documentary) and CF-C4.
3. **Behaviour changes (AggregateError; publish to all; divergence error kept alongside rebuild error; openLocked no longer ignores the outcome).** Accept. The single-failure case throws the identical object, so no existing `instanceof` consumer changes (grep finds no non-test `instanceof CampaignProjectionDivergenceError` or `instanceof AggregateError` anyway); the 340 related suites and 35 predecessor suites pass; delivering to every subscriber before rethrowing is strictly more faithful to "every committed event reaches every subscriber" and the error is still raised. `openLocked`'s new throw on the failure arms is equivalent to the baseline, where the same errors propagated out of `commitCampaignEventBatch` before the outcome was ever built.

Keeping the throw rather than a silent mapping is the right choice.

## 7. Carry-forwards for P2CG1C (exact wording)

1. **CF-C1 (borrowed seam contract).** `SQLiteEventJournalWriter.appendInBorrowedTransaction(raw)` is synchronous, requires `db.inTransaction === true` on the writer's own handle, shares `validatedIdentity` with the owning wrappers, and never begins, commits, releases a savepoint or notifies. C's ordered "campaign C IMMEDIATE then match M IMMEDIATE" must open the C transaction itself on the journal's handle and call this operation inside it; only that outer owner may announce the C commit, after its own COMMIT returns. Do not use `appendWithExtension`/`appendPreparedWithExtension` for the borrowed role: both own an IMMEDIATE transaction and, when nested, silently become a SAVEPOINT (unchanged baseline behaviour when no `onCommitted` is requested; refused before writing when one is).
2. **CF-C2 (refusal versus throw).** The only "nothing written with certainty" signal is the typed `refused` arm; any throw from the append (including a throwing guard, a thenable guard result, a stale branch or a saved-record rewrite failure) is classified `commit-uncertain {commandId, error}` and must be resolved by `getCommandReceipt` readback, never by compensation or a fresh command. A guard that wants the precise arm must return `{kind:'refused', reason}` rather than throw.
3. **CF-C3 (capability fail-closed).** Controls are honoured only by `JournalCampaignEventStore` over a `SQLiteEventJournalWriter`; `InMemoryCampaignEventStore`, a non-SQLite journal, and any store exposing `appendCommandBatch` without `appendControlledCommandBatch` are refused with `append-controls-unsupported` before any write, at both the adapter and the host (`commitEvents`, including the per-event fallback). C and D must not add a second capability flag or a boolean switch; the presence of `appendControlledCommandBatch` is the capability.
4. **CF-C4 (outcome consumption).** `applyHostIntentWithControls` answers `CampaignDoorOutcome = answered | committed | lost-race | refused | commit-uncertain | committed-unsettled`, and throws only for a door-level throw or a cleanup failure on a non-committed outcome, in which case the thrown `AggregateError.cause` is the outcome and `errors[0]` is the cleanup error (an identity conflict is mapped to `answered` inside the door). Consumers must switch exhaustively (typecheck enforces it through `throwCommitFailure`), must treat `committed-unsettled` as durable-plus-unfinished (errors retained in order: notification, divergence, rebuild, publishes, cleanup), and must never map any failure arm to a public success or a zero-append answer.
5. **CF-C5 (cleanup ordering).** `afterRelease` runs once per door after the single-writer lock chain has advanced (lockDepth 0) and after `onCommitted` and publication, but it is a promise continuation: the next queued door may already have started (up to its first await) when it runs. A reservation release placed in `afterRelease` must therefore be idempotent and observable by readback, and the next door's guard must tolerate a not-yet-released prior reservation by refusing (fail closed) rather than assuming order.
6. **CF-C6 (writer-level onCommitted).** At the writer, `appendWithExtension`'s `onCommitted` is called un-wrapped after COMMIT; a throw there rejects the promise although the batch is durable. The adapter wraps it into `notificationError`; any new direct writer caller must either not throw from `onCommitted` or wrap it the same way, and must not read a rejection as "nothing committed".
7. **CF-C7 (trust boundary).** Controls (`guard`, `onCommitted`, `afterRelease`) are server-only operation arguments; `toJournalBatch`, `canonicalizeCommandIdentityV1`, the private envelope and every Protocol/wire type are unchanged and must stay so. The identity-equality fixture (guarded versus plain journal rows and digests) in `JournalCampaignEventStore.test.ts` is the regression the successors should keep green rather than re-derive.
8. **CF-C8 (production inertness, re-verify at C's baseline).** At c0c97c13 no production module calls the new operations, `server.js` composes no guard, and the guest wire door and GM arbiter still use the uncontrolled `applyHostIntent`. C's admission must re-run this grep at its own baseline; the first production caller of a controlled door belongs to D/H, not C.
9. **CF-C9 (lint and cycles).** Head figures: writer 531 physical / 445 counted (warned), adapter 660 / 446 (newly warned), host 699 / under 400, batch commit 309; repo-wide 87 warnings, 0 errors; madge 171 chains from the six leaves, unchanged sets. C adds files, so expect the madge count to move only by C's own modules; record before/after.
