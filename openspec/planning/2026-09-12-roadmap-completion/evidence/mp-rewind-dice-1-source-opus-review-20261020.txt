This closes the "persistence and recovery of the capture across restart" question through the production boot path, not only through \`foldMatchSession\` plus a manual \`ServerMatchHost\` construction.

## Dice-path analysis (post-rewind reachability)

- **Live legacy path** (\`handleIntent\` → \`ServerMatchHostIntent\`): the rebuilt session's \`d6Roller\` is \`() => host.d6()\` → \`this.capture.d6()\` → the current \`RollCapture\` → \`CryptoDiceRoller\`. \`InteractiveSession\` feeds that one roller to initiative, weapon attacks (\`resolveAllAttacks\`), physical attacks, heat including the MaxTech crit-location roller, End-phase PSRs, movement PSR inputs (\`commands.ts:108/127/178\`) and vibro-claw (\`InteractiveSession.ts:680\`, which no longer falls back to \`this.random\`). This is the same coverage the \`ServerMatchHost.create\` and \`recover\` sessions have. Any residual \`defaultD6Roller\` fallback inside individual resolvers is shared with the non-rewind paths and pre-dates this unit.
- **Journal-authority path** (\`ServerMatchHostJournalAuthority.ts:155-161\`, \`decideCommandBatch\`): this path already read \`() => this.capture.d6()\`. Before this PR, \`reseedDice\` replaced that capture with \`SeededDiceRoller(journalDiceSeed)\`, where \`journalDiceSeed\` defaults to \`0\`. Post-rewind journal-mode dice were therefore predictable. The PR's \`installFresh()\` branch fixes that as well, though no test exercises it directly (see finding 2).
- **Double capture / ordering:** in journal mode a die is recorded by both the host \`RollCapture\` and the decide-scoped \`RollCapture\`, but it is drawn once and stamped once, from the decide buffer. The host buffer is discarded at the next \`installFreshCapture\`. In legacy mode, each intent gets \`installFresh\` → engine → \`stampRollsOnNewEvents\` (drain). Hydration consumes nothing, so nothing is stranded between \`reseedDice\` and the first intent. \`replaceSession\` precedes \`reseedDice\`, but the closure resolves lazily, so the order is harmless.
- **Rewind vs in-flight intents:** \`rebuildFromActivatedBranch\` bumps \`opponentEpoch\` and runs inside \`queueCommand\`, so it serializes behind any in-flight intent. The co-op driver re-checks \`session\` identity and the accepted head immediately before DECIDE (\`CoopOpponentDriver.ts:121-129\`). There is no new race.
- **Determinism / replay:** \`foldMatchSession\`, \`fromHydratedSession\` and join replay are event-driven. The owned test forbids entropy during fold, hydrate and \`ReplayChunk\`, and asserts that the stored and broadcast \`rolls\` equal the crypto draws.
- **Fog / authority:** there is no change to the projection, the publication guard or the per-socket replay. Clients still submit intents only. No \`Math.random\`, no \`console\` and no SQLite/browser boundary change was introduced.

## Findings

1. **Low — test gap: debug-seeded post-rewind capture is not asserted** (\`src/lib/multiplayer/server/ServerMatchHost.ts:612-619\`, \`__tests__/ServerMatchHostRewindRebuild.serverUnits.test.ts:256\`).
   - **What happens:** the seeded branch replaces \`this.capture\` with a new object. Mutant R5, which binds the port \`d6\` to the old capture object, survives all 15 rewind tests. \`rewindRebuild.test\` checks only \`d6ForTests()\`, which reads \`this.capture\` directly, not the rebuilt session's draws.
   - **Impact:** a future refactor could leave a debug-seeded rebuilt session drawing from the discarded capture, with its rolls stamped from an empty buffer.
   - **Fix (in-manifest):** pick either of these.
     - (a) Add a seeded variant of test 2: source \`new SeededDiceRoller(new SeededRandom(7))\` with \`diceSeed: 7\`. Assert that the first post-rewind \`InitiativeRolled\` \`rolls\` are non-empty and equal the prefix of a fresh \`SeededDiceRoller(new SeededRandom(7))\` stream.
     - (b) Avoid object replacement altogether. Give \`ServerMatchHostCapture\` a \`resetSource(roller)\` method and call it from \`reseedDice\`. This keeps one capture identity for the lifetime of the host.
   - **Not a blocker:** the debug-seed path is gated out of production by \`readDebugDiceSeed\` (\`MatchHostRegistry.ts:118-127\`).

2. **Low — journal-compatible post-rewind dice are fixed but not directly tested** (\`ServerMatchHost.ts:619-622\`; \`ServerMatchHostJournalAuthority.ts:155-161\`).
   - **What happens:** the owned test forces \`rollbackReader: legacy-compatible\`, so R1 is killed only through the legacy session path. The behavioural change for journal-authority matches is untested: post-rewind decide draws were \`SeededDiceRoller(journalDiceSeed=0)\` and are now crypto.
   - **Fix:** after the fixture issue in the probe notes above is resolved (a recorded journal head for the opening batch), add a journal-compatible variant that asserts \`CryptoDiceRoller.prototype.d6\` draws equal the stamped \`rolls\` of the first post-rewind decided command.
   - **Disposition:** acceptable as a carry-forward if the fixture work does not fit this PR.

3. **Info — stale comments describe dice as seeded** (\`src/lib/multiplayer/server/ServerMatchHostRewindRebuild.ts:172-174\` "then reseed the dice"; \`:195-197\` "fromSessionAsync reseeds from config.seed … same provenance … never Math.random").
   - **Why it matters:** \`config.seed\` now seeds only the AI \`SeededRandom\`. Dice come from the host capture, and in production \`reseedDice\` resets the capture buffer rather than reseeding.
   - **Fix:** reword both comments. Optionally rename the port member to \`resetDice\` in a later unit.
   - **Disposition:** non-blocking.

4. **Info / out of scope (pre-existing, reachable post-rewind) — co-op AI dice are seeded, not crypto** (\`CoopOpponentDriver.ts:130-140\`).
   - **What happens:** \`driveOpponent()\` runs right after every rebuild. The AI command decides with \`d6Roller: undefined\` and \`diceSeed = sha256([matchId, branchId, events.length, effectiveGeneration, unitId])\`. The rolls are captured, stamped and replay-faithful, but they are deterministic, and possibly predictable by a client that knows the branch id.
   - **Ruling:** this is a deliberate idempotency design from the co-op unit and is outside this manifest.
   - **Action:** consider registering a carry-forward to decide whether AI dice should use the host crypto capture, with idempotency carried by the receipt.

5. **Info / out of scope (pre-existing) — the divergence-rebuild session has no \`d6Roller\`** (\`ServerMatchHostJournalAuthority.ts:266-274\`).
   - **What happens:** after \`projection-divergence\`, the live session is rebuilt with no \`d6Roller\`.
   - **Impact:** journal hosts decide on capture-backed scratches, so this is mostly latent. If that live session were ever used for legacy-path dice, it would hit the engine default.
   - **Action:** worth a one-line carry-forward to pass \`d6Roller: journal.d6\`.
