## 4. Reading notes (authority / replay / persistence)

- Closure over host before declaration: recover passes () => host.capture.d6() while const host is still in its TDZ. Safe
  because fromHydratedSession/constructor never roll (BotPlayer is constructed, not run; setup builds maps only). If a
  future hydration ever rolled synchronously it would throw ReferenceError, which the per-match try/catch in
  recoverActiveMatches turns into a failed match, not a crash. The code comment documents the ordering. No change needed.
- Capture pointer identity: recover does not call adoptExternalCaptureRef (create does). That is correct here: the
  callback reads host.capture.d6() through the field, and ServerMatchHostCapture.installFresh updates that same field,
  so per-intent swaps stay visible to the engine. Proven by the two-intent rows (second intent's rolls land in the
  second buffer and equal the second batch of crypto calls).
- Rolls stamped before persistence: ServerMatchHostIntent stamps and then persists+broadcasts, so DurableMatchStore
  rows and the wire frames carry the same rolls; the fog filter preserves payload.rolls for AttackResolved; the
  probe saw rolls on the host's live frame and the jest row saw them in store.getEvents.
- Fail-closed behaviour: unchanged from UNITS-1 (UnitContractParseError or a missing custom definition fails only that
  match; legacyBranches row 3 pins the isolation).
- Co-op binding: mission ? bindCampaignPause(mission.sessionId) unchanged; the co-op=true row uses an absent campaign
  session and still recovers, so pause binding tolerates a missing session (pre-existing behaviour).

## 7. Findings and precise in-PR fixes

F1 (Medium, pre-existing since #1593 e870eb36a, OUTSIDE this unit's grant; carry-forward CF-MPRU2-1): the LIVE rewind
rebuild still rolls uncaptured, predictable dice. rebuildHostFromActivatedBranch stamps config.seed =
host.journalRandomSeed (0xc0ffee for every MP host: create never passes randomSeed) and calls
recoverServerInteractiveSession(seeded) with NO d6Roller, so the rebuilt engine's d6Roller is
SeededD6Roller(0xc0ffee).asD6Roller() from position zero; host.reseedDice(journalDiceSeed=0) then replaces the capture
with SeededDiceRoller(SeededRandom(0)), which the legacy engine path never consults (only the journal-authority decide
path reads capture.d6). My probe on a REAL ServerMatchHost (probe-live-rewind-dice.log; recovered: true host with a
legacy-compatible reader, real journal rewind, then rebuildFromActivatedBranch): post-rebuild initiative_rolled
{playerRoll 5, opponentRoll 10}, payload.rolls absent on every fresh event, CryptoDiceRoller.d6 called 0 times. So
after a GM rewind on a live server: (a) events carry no rolls, (b) dice are predictable from a public constant, and
(c) boot-recovered rewound hosts (now crypto via capture) and live-rebuilt hosts (seeded, uncaptured) diverge in dice
provenance. Byte-identical to the pre-PR fromSessionAsync behaviour, so not a regression, but it is the same
authority/fairness class as CF-MPRU-4 and this PR closes CF-MPRU-4 only for the boot path. Fix sketch (needs
ServerMatchHost.rewindRebuildPort, outside the recover-only grant): add d6: () => this.capture.d6() to
IRewindRebuildHost and call recoverServerInteractiveSession(seeded, undefined, host.d6) - or, if post-rewind dice are
meant to be deterministic from journalDiceSeed, route the engine through the reseeded capture so they are at least
recorded. Caveat: the new serverUnits row PINS the current behaviour (rebuilt vs a seed-4242 control over seven
advancePhase steps including an initiative roll), so the fix must re-seal that test; that is a reason to route it as a
unit, not to change bytes under this RED.

F2 (Low, observation, frozen control): recover now rebuilds the session it is handed. registerRecoveredHost and the
rewound arm in MatchRecovery still call recoverServerInteractiveSession(state) first, so every boot-recovered match
derives units three times (MatchRecovery, recover's journal units, recover's session). NodeCanonicalUnitService caches
parsed units, so the cost is adaptUnitFromData + the custom SQLite reader x3 per unit - negligible, and it keeps
MatchRecovery byte-identical as the grant requires. OBS-MPRU2-1: a later owner of MatchRecovery.ts can let recover
take IGameSession (or the derived units) and drop the pre-derivation.

F3 (Low, coverage): M6 survives; see section 6. Not a defect.

F4 (Low, observation): the explicit roller wins over a finite config.seed (test row 3). MP hosts never persist a seed
and SP recovery still goes through the engine's fromSessionAsync, so no conflict today. A debug ?seed=N MP host loses
its seeded dice on restart (recover passes no sourceRoller and diceSeed is not persisted) - it did before too (the
0xc0ffee fallback was not the debug seed either). Note for whoever owns diceSeed persistence, if ever.

F5 (Low, evidence quality): the PR body claims no production-build proof; this review supplies it for 1v1 (section 5).
The red receipt's "three passing controls" are the legacyBranches fixtures; fine, and honest.

No required in-PR product or test change. The optional change (F1) is routed, not requested, because it needs a file
outside the grant and a new RED seal.
