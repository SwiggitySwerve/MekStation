## Judged items

**(a) Ordering (read at matchHeadRoute.ts:29-98).** prepareMatchHistoryGet (405 / db / 400 / 401 scoped bearer) -> store.getMatchMeta (throw -> 404 'unknown match', pre-existing) -> authorizeHumanAction over HostAsGmMembershipSource(MatchSeatMembershipSource) -> host-and-gm check (else 403 'Authorization refused'; AuthorizedViewerError / HumanActionAuthorizationError thrown inside the try also map to that constant via rejectMatchHistoryFailure) -> **noPerViewerRevealProjection(meta.config) -> 403 FOG_REFUSAL, return** -> db.transaction(readEffectiveHead, readEffectiveStreamHead) -> 404 'no head' / 200 body. Membership precedes policy; the refusal precedes the transaction, the branch-store read, the stream-heads SELECT and any serialization; there is no fallback branch. The predicate is the B14-0A one, imported read-only (helper blob unchanged); the reason is the shared constant, not a literal.

**(b) Semantics versus B14-0/B14-0A.** HTTP has no 1008/1011; the unit specifies 403 + fixed reason, the same mapping B14-0A gave the participant metadata route ([id].ts:102-105), so the three HTTP surfaces that refuse by policy (metadata 403, export/private-preview 500 projection-failed via FogAwareMatchProjection, head 403) all carry the identical secret-free string. The B14-0 'unreadable config' distinction (1011) has no new analogue here: an unreadable store already fails at getMatchMeta with 404 'unknown match' before authorization, which is fail-closed (no digest) but conflates not-found with infrastructure failure and precedes membership (F4, pre-existing). A legacy row with config: null (not undefined) would make the B14-0A predicate throw and the route answer 500 via sendCaughtApiError, also fail-closed, with a TypeError message and no secret (F7).

**(c) Disclosure.** The refusal body is exactly {error:'fog-projection-unavailable'} (toStrictEqual in the owned rows); no header is set on that path; the digest, branch id, revision and generation are never computed. Host/GM privilege gives no exemption (my RV3). A seated non-host member gets the generic refusal, not the fog reason (RV5), matching the unit text; this is deliberately stricter than the metadata route, where a seated player does receive the fog reason, and is correct for a host-only surface. Anonymous and wrong-scope bearers keep 401 without the substring 'fog'. Existence of a head under fog is not disclosed by the product (refusal precedes the existence check) but is not pinned by a row (F1).

**(d) Known-off / omitted.** {fogOfWar:false} and the fixture's flag-omitted config both pass the predicate; the 200 body {branchId, revision, effectiveGeneration, digest} and the two 404 'no head' rows are unchanged and still pass (RV8 shows four rows guard the omitted-flag path). ## Five-class analysis

- **Authority.** Method, db, URL id and scoped bearer first (unchanged helper); the host-as-GM brand is resolved from durable seats plus meta.hostPlayerId before the policy; non-host members and strangers receive the same constant 403 they did on Main, anonymous 401; the client supplies nothing the decision reads (config comes from the store). Host privilege is not a fog exemption (RV3). Server authority is unchanged.
- **Privacy.** Fog-on and unknown-config host reads refuse with the fixed secret-free reason before the transaction, the branch-store read, the stream-heads SELECT and serialization; the body is exactly the one key; no header. Residual channels are outside this manifest and already routed: /timeline lineage revision/branchId and audit count (F5 -> FOG chain, CF-B14A-7/9), the 404 existence oracle (F4, pre-existing), config null -> 500 (F7).
- **Replay.** No event, journal, reducer, branch, lease or cursor write; the fog-off transaction and its one-snapshot read are byte-identical; the lease CAS contract (digest/revision/generation) is unchanged for fog-off. Fog-on hosts can no longer obtain the digest the rewind-commit CAS needs, which is consistent with the rewind routes' own pre-existing fog refusal.
- **Idempotency.** The refusal is a pure read of meta already in hand; repeated requests write nothing (no audit, outbox or epoch).
- **Concurrency.** The predicate is synchronous and runs between two already-awaited steps; no new await window after authorization. Match config has no update route, so the authorization-time meta and the policy-time meta are the same object. A seat revocation between the brand and the policy only tightens (the brand was resolved first). The SQLite transaction is unchanged.
