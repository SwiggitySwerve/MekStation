## Behaviour verified

### Bounded recovery (CF-H7 / CF-G4)

- QUIET_RETRIES = 2. The episode key is JSON [campaignId, transport.matchId, transport.playerId].
  - At route level, matchId comes from the route and playerId from the stored token, so the key is stable across replacement transports.
  - The budget therefore spans socket identities, not a socket WeakMap, as the policy requires.
- Only the quiet-window timer calls rejoin(true).
  - Exhaustion closes the transport, does not call setRejoins (so no new effect and no new socket), and sets the fixed text.
  - That text is "Campaign sync could not connect. Reload this campaign to try again.".
  - No loop is possible: after exhaustion live=false, and every listener (quiet timer, onError, onAppliedViewConfirmed) is removed.
- Sockets: the initial one plus 2 replacements, so 3 in total, all closed (readyState 3). This is pinned for both host and guest.
- Backoff: retries are spaced at a fixed APPLICATION_CONFIRMATION_TIMEOUT_MS (= HEARTBEAT_TIMEOUT_MS), with no exponential growth. This matches the owner policy of 2 retries then the inline message (I1).
- Reset paths:
  - A validated server confirmation (transport.onAppliedViewConfirmed, emitted by the transport's confirmation handling) resets the budget.
  - So does a key change.
  - So does a route remount, because the state is hook-local.
- A heartbeat, a frame or a rebind does not reset the budget. This is pinned by "HP heartbeat and rebind do not replenish retry budget".
- Live region: one persistent p element with role="status" aria-live="polite".
  - It is rendered before the surface, empty until exhaustion, and is the same DOM node before and after (pinned with toBe(region)).
  - Identity switch clears it (pinned).

### Release of settled offers (CF-H14 / CF-H15)

- settling is incremented in consume, not when the promise starts, so a same-tick dispose still cuts (CF-H15).
- The per-offer release() is guarded by released, so it is idempotent. It is called synchronously before confirmApplied, and again by the final .then(release), which is a no-op.
- Coverage of each path:
  - On a normal return, release happens before confirm.
  - On an early return (!live) or a throw before release, the final .then releases.
  - In both of those cases live is already false, so cut marking was decided at dispose time and stays correct.
  - If confirm throws, release has already run; the .catch rejoins.
- A confirm that schedules dispose in its next microtask now sees settling=0, so there is no false cut. Pinned: 1 socket, ACKs h14-r0 and h14-r1.
- The CF-H1 held-refresh cut is still caught. My mutants R01 and R07 both fail the three CF-H1 rows.

### Authority

- The client still only folds server offers and sends CampaignAck.
- "Healthy" is derived only from the server's validated applied-view confirmation; a client-side outcome never counts as healthy.
- No intent is resolved client-side, and nothing new is sent.
- Exhaustion only closes the client's own socket. Server seat cleanup runs through the existing close handler; no server product file changed.
- The binder row is widened to {host, member} x {confirmed, held, failed}. Every row shows an installed membership-bound join only offers, and joinMember is never invoked. All 6 rows pass.

### Privacy

- The visible text is a constant. It carries no ids, reasons or server error strings.
- The episode key, which contains playerId, stays in memory: it is never rendered or logged.
- No logger or console calls were added.

### Fog / B14 consistency

- The HP change touches no server, projection or journal reader. B14-0 and B14-HEAD refusals carry the reason fog-projection-unavailable.
  - That reason does not start with campaign-application-, so it never triggers a consumer rejoin.
  - A refused or silent socket now reaches the generic exhaustion text after 2 retries instead of reconnecting forever.
- The generic text is no fog oracle: it is identical for fog-on refusal, an outage, or a legacy server.
- Fog-on matches are still refused by the unchanged B14 paths.

### Replay

- Each replacement binding still starts from EMPTY.
- The G1 heardAt watermark, ordered offers and stale-binding silence all hold; the regression set is green.

### Concurrency between recovery and release

- A quiet timer cannot fire mid-settle, because consuming an offer frame marks it heard and clears the timer.
- A rejoin during a settle sets live=false. The settle returns without confirming, and the later release does no harm: the dispose after the rejoin sees live=false and does not cut, and the replacement starts from EMPTY.
- A dispose immediately after a synchronous confirm sees the release already applied.

## Findings

### Low

- F1 (Low, test gap; recommended in-PR, test-only): nothing pins that a healthy confirmation clears the visible exhaustion notice.
  - Mutant R08 (healthy resets retries but leaves recoveryError) passes all 130 owned tests.
  - The local receipt's accepted residual says "notice persists until healthy confirmation or reload", but nothing asserts the "healthy confirmation" half.
  - The path is reachable. A same-key effect rerun can happen when roomCode, store or applyRefusal identity changes. It binds a new transport against the spent budget, and that transport can become healthy while the stale "could not connect" text stays.
  - Fix: add one row to hostProjection.test.tsx:
    1. Exhaust the budget (3 sockets, text shown).
    2. Force a same-key rebind without remount. For example, rerender with a campaign whose coopSession has a different roomCode but the same matchId, so the host effect deps change but the key does not.
    3. Apply a healthy baseline via applied(connection, baselineOffer(...)).
    4. Assert that screen.getByRole('status') is the same node and is empty.
  - R08 must then fail. No product change is needed.
- F2 (Low, defensive code that is not pinned; no fix required): the current() episode-key guards in quiet() and healthy() cannot be reached through the route.
  - Effect cleanup disposes the old binding, which clears its timer and listener, before a new key binds. R03, R04 and R05 survive for that reason.
  - The guards are correct defence in depth. If H installs a receipt port or keeps bindings across keys, a hook-level test should pin them (CF-HP-3).

### Info

- I1: Retries are not backed off; they are spaced at one fixed quiet window. Total time to the notice is about 3 windows. This is consistent with the adopted policy.
- I2: Non-quiet recovery is still unbounded, with no backoff.
  - Signals: recovery-required, prefix-conflict, application-refused, confirmation-timeout, and INTERNAL_ERROR with a campaign-application-* reason.
  - A server that answers every join with a campaign-application-* error drives an immediate reconnect loop, bounded only by round-trip time.
  - This predates the PR, sits outside the registered quiet-window scope, and is disclosed in the PR body and the local receipt. See CF-HP-1.
- I3: The empty live region (a p element) now renders on every campaign page that mounts the connected surface: campaignPageShell routes, personnel and dashboard, single-player included.
  - It is an empty polite region, so a11y is harmless and the A11y CI job passed.
  - If PageLayout spaces its children with gap or space-y, an empty unstyled p may add one spacing slot. A quick visual check is suggested; this is not a blocker.
- I4: As noted above, the units.json ownershipExceptions edit is a manifest field. It is justified by admissionRequires, and 28 earlier units set the precedent.
- I5: A same-key rebind against a spent budget opens one socket and closes it after a window without a further notice change. This is disclosed. Legacy servers reset only on reload; also disclosed.
