Token scan of every added line in `src/` (`\bas\b`, `<T>` assertions, non-null `!`, `any`, `unknown`, `.slice(`, `new Uint8Array(`, `Buffer.from`, `.subarray`, `.buffer`): the only hits are the two `as const` lines. Findings:

- **No type assertion** (`x as T`, `<T>x`), no non-null `!`, no `any`/`unknown` laundering, no new allocation or copy, no overload, no helper added, no import changed. `as const` is a const assertion, is explicitly the form task 1.2 names, and M7 shows it is erased.
- **Signature changes beyond annotation narrowing** are exactly the accepted widening: six exported parameters (`signData` x2, `verifySignature` x3, `encryptWithPassword` x1) from `Uint8Array` to the lib `BufferSource`. Narrowings of returns (`generateKeyPair`, `signData`, the three `fromBase64`, `getRandomBytes`) and of the non-exported `deriveKey` parameter are strictly safer for consumers.
- **Can the widening change behaviour for a real caller?** No. In all three functions the parameter flows unmodified into `crypto.subtle.importKey` / `sign` / `verify` / `encrypt`, whose runtime contract is `BufferSource` already; there is no `.length`, `.byteLength`, `instanceof`, index access or copy on `data`, `signature`, `privateKeyBytes` or `publicKeyBytes` anywhere in the three bodies (read in full at head). So no guard that assumed `Uint8Array` existed to weaken. On 5.8 the widening admits `ArrayBuffer`/`DataView`, which Web Crypto accepts; on TypeScript 7 `BufferSource` is `ArrayBufferView<ArrayBuffer> | ArrayBuffer`, i.e. narrower than the old `Uint8Array<ArrayBufferLike>`, so no caller gains the ability to pass something the runtime rejects. Every caller in the tree still passes a `Uint8Array`: `campaignGrantToken.ts:90` (`signData`) and `:228` (`verifySignature`) with `fromBase64`/`TextEncoder` bytes; `redeemCampaignGrant.ts:142` (`verifySignature`); `issuePlayerToken.ts:138` and `pages/api/multiplayer/auth/token.ts:159` (`signData` with `TextEncoder().encode` payload and `fromBase64` key); `IdentityService.ts:412` (`encryptWithPassword` with the generated private key), `:488` (`signMessage`), `:505` (`verifyMessage`); tests `auth.test.ts:50`, `socketTokenScope.test.ts:75`, `campaignRedeemRoute.test.ts:134`, `campaignShareAndRedeem.test.ts:113`, `IdentityService.test.ts` (268-381), `securityBoundary.test.ts:46` (mocked). `server.js:26/356` binds a different `verifySignature` (node:crypto `verify`) and is unrelated. No caller passes `ArrayBuffer` or `DataView`.
- `generateKeyPair` narrows via an intersection with `IKeyPair` rather than editing `IKeyPair` (`src/types/vault/VaultCoreTypes.ts:60`, keys typed `Uint8Array`); that file is not a leaf, and `IKeyPair & {...}` resolves to `Uint8Array<ArrayBuffer>` members on 5.8, so the choice is correct for the registered scope (note N3).
