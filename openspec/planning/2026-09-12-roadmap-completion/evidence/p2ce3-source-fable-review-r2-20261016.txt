## 3. B1 - fixed, and the widened window opens nothing new

**Code at head** (`publish`, binder 1884-1918):

```ts
view.inFlight = candidate;
const result = await this.deps.broadcaster.sendConfirmed(socket, candidate.frame, view.abort.signal);
if (!this.current(view)) return false;
if (result.kind !== 'sent') { fail(send-failed); return false; }
if (isRevoked) { fail(membership-revoked); return false; }
await this.processAck(view);          // may run commit(previous latest); candidate still in flight
if (!this.current(view)) return false;
view.latest = candidate;
view.inFlight = null;
await this.processAck(view);
return this.current(view);
```

`inFlight` is read in exactly one place, `acknowledge` (binder 1773: `names(view.inFlight) || names(view.latest)`); it is written at 1749 (open), 1888 and 1915. So the fix changes admission only: during the pre-establishment `processAck` the just-written candidate is now admissible, which is the B1 window. I checked each hazard the brief lists:

- **Stale `inFlight` on a live view.** Every exit of `publish` that does not reach line 1915 either follows `fail()` (view invalidated) or a false `current(view)` (view already dead). An exception inside `processAck`/`commit` propagates to `enqueue`'s catch, which calls `fail`. `refresh` is the only caller of `publish` and awaits it inside the serialized chain. Hence on a live view `inFlight !== null` holds only between lines 1888 and 1915 of one `publish`, i.e. exactly while a write or the previous offer's commit is pending. No stale value can survive on a live view.
- **A second `publish` while `inFlight` is set.** Impossible: `publish` is awaited sequentially inside `refresh`'s loop, `refresh` runs as one chain step, and `wake` enqueues rather than interleaves (PROBE-J has a real third commit land during the first commit; its offer is published only after the delta is established, linked to the delta).
- **Failure / close / supersede with the slot full.** `fail` -> `invalidate` nulls `this.view`, so `acknowledge` on the dead view returns `not-offered`; the enqueued `processAck` is skipped by `enqueue`'s `current` check; `sendConfirmed` with the aborted signal returns `cancelled`. A stale `inFlight` on the dead view object is unreachable (PROBE-I: confirmation write fails during the window; PROBE-K: a second join supersedes the view during the window).
- **Early-ACK slot interplay.** An ACK of the candidate during the window sets `pendingAck` and enqueues a `processAck` behind the running `refresh`; the pre-establishment `processAck` does not match it (latest is still the previous offer); the post-establishment one commits it; the enqueued copy is then a no-op (PROBE-A/G/J). An ACK of the previous latest during the window (duplicate) is admitted, but the slot entry never matches again once the candidate is established, so it receives neither a confirmation nor a refusal and does not block the next ACK (PROBE-H). This is identical to the pre-fix behaviour (that ACK was admissible as `latest` before too) and is covered by the Task 13 "cumulative, at-least-once" wording.
- **ACK naming the just-established offer after `inFlight` cleared.** It is `latest`, so admitted; the post-establishment `processAck` has already run with an empty slot and the ACK's own enqueued `processAck` commits it. Ordinary path; exercised by every sequential test.
- **Head-drift exhaustion of the previous offer during the window.** The refusal for the previous offer is sent, `publish` continues, the candidate is established and its slotted ACK commits cumulatively (reasoned from `commit`'s `continue`/fall-through; PROBE-J covers the single-drift-then-retry variant).

**Conclusion:** the only behavioural change is the intended one. The admitted set during the window grows by exactly the candidate the socket has already received.
