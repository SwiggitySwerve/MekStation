## 4. Fail-closed behaviour on a schema-invalid bundled unit

Before: CanonicalUnitService.getById (fetch) returns the raw JSON without contract validation, so a
contract-violating unit file was adapted silently at launch and at recovery (when the fetch worked).
After: getByIdSync runs parseUnit and throws UnitContractParseError naming the field path; the throw
propagates out of deriveServerAdaptedUnits -> recoverServerInteractiveSession -> the per-match
try/catch in recoverActiveMatches, which logs "[MatchRecovery] failed to rebuild match <id>" and adds the
id to failed. Other matches continue; the server listens.

Is that right? Yes for a packaged image: a bundled unit JSON that violates UnitContract is a build/data
defect, and recovering the match with that unit silently dropped would reproduce exactly the
FINDING-A1-REV-1 symptom (no adapted state, every action refused) with less diagnosis. Fail-loud is the
documented boundary of NodeCanonicalUnitService and is consistent with the engine's custom-unit rule.
Reachability today: I scanned the whole bundled catalog through getByIdSync at this head (4225 indexed,
4225 parse, 0 null, 0 throws, 28.6 s; catalog-scan.ts). So the branch is unreachable on a correct image
and only an image corrupted after build can hit it.

Two consequences worth knowing (neither blocks):
- Asymmetry: launch (getOrCreate -> buildMatchHostBootstrapFromMeta -> adaptUnit over fetch) still does
  not validate, so a hypothetically invalid unit launches but cannot be recovered. Harmless while the
  catalog is clean; worth folding into CF-MPRU-1's owner if the fetch service is ever replaced.
- Pre-existing fall-through: a match that lands in failed (not blocked/quarantined) is not in
  hosts, so the next getOrCreate for a non-co-op match builds a FRESH host from meta
  (MatchHostRegistry.getOrCreate, the "Refused recovery must not fall through to a fresh empty host"
  guard covers quarantine only). That is the existing behaviour for every rebuild throw; this PR adds a
  new (unreachable today) throw class to it. Noted as OBS-MPRU-2, owner MP-HOST-DEDUPE-1 since it is
  already in getOrCreate/recoverActiveMatches.

## 5. Do CF-MPRU-1 / CF-MPRU-3 block the reconnect journey (2 players + GM shared mission)?

CF-MPRU-1 (ServerMatchHost.recover derives co-op mission journal units through
deriveAdaptedUnitsFromSession, fetch catalog, at boot): at packaged boot every canonical unit of a
co-op mission host is skipped with the old engine warning, so journalPlayerUnits/journalOpponentUnits
on that host are empty. I traced every consumer of those two fields: they feed only decideDeps
(ServerMatchHost.ts:1324-1328), i.e. the combat journal-authority decide/apply/divergence-rebuild path
(ServerMatchHostJournalAuthority.ts:159, :258-272) and the shadow comparer. The live engine session
that answers legacy-path intents (Move, Attack, AdvancePhase, the CoopOpponentDriver AI turn) is the
InteractiveSession this PR now builds from disk. COMBAT_JOURNAL_AUTHORITY_MODE is 'off' in production
and a recovered host enables journal authority only when the durable rollback reader is
journal-compatible (a started fact exists), which the 'off' mode never writes. So after this PR a
restarted co-op mission accepts unit actions on the legacy path; CF-MPRU-1 does NOT block the
reconnect journey today. It does become High the day combat journal authority is cut over, and it is
not yet proven on a real image (the probes here are 1v1 combat). Verdict: not blocking for A2's
restart row, but A2's co-op restart case must witness an accepted action, not only a replay.
Note the same empty-journal-units gap exists for NON-co-op recovered hosts (recover passes [] for
them), so the fix should hand the disk-derived units to the host for both kinds (OBS-MPRU-1).

CF-MPRU-3 (ServerMatchHostRewindRebuild live rebuild still uses fromSessionAsync -> fetch): only runs
while the server is listening, so it works; it is the same self-fetch pattern, so it is fragile under
NEXT_PUBLIC_BASE_URL/PORT mismatch or a saturated listener. Not blocking for reconnect/restart; the
rewound-at-boot arm (the one that matters at restart) is already on disk in this PR.

Owner recommendation: a new narrow unit (suggested id MP-RECOVERY-UNITS-2, R2.authority-live,
predecessor MP-RECOVERY-UNITS-1, before L1-SMOKE-A2) owning ServerMatchHost.ts and
ServerMatchHostRewindRebuild.ts: (a) ServerMatchHost.recover takes units from deriveServerAdaptedUnits
for both co-op and non-co-op hosts, (b) rebuildHostFromActivatedBranch calls
recoverServerInteractiveSession, (c) one unmocked rewound-at-boot fixture so M8 is caught (CF-MPRU-2),
(d) the recovered-host dice wiring in CF-MPRU-4. Folding (a)-(d) into MP-HOST-DEDUPE-1 is possible
(it owns the server directory and is next in the lane) but mixes a concurrency RED with a unit-source
swap; I would keep DEDUPE-1 narrow. Either way, L1-SMOKE-A2's co-op restart row should cite the owner.
