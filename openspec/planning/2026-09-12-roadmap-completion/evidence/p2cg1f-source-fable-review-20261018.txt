The catch resolves the chain, so later steps run, hit `if (!live) return` at the top of `settle`, and neither fold nor ACK on the dead binding (pinned: `oldAcks: ['v1-r0']`, old socket readyState 3, one reconnect, the new view adopts `v2-r0`). A rejoin inside `settle` followed by the catch's rejoin is a no-op by `live`. ## 5. Per-class findings

- **Authority.** The consumer resolves no canonical action and F adds no write: a thrown step and a silent socket both end in `rejoin`, which only flips `live`, clears the window, unsubscribes, closes the transport and signals the hook; the next binding re-reads the authority's baseline from EMPTY. A settle in flight when the binding dies returns before `confirm`, so a dead binding cannot certify an offer it did not finish (pinned: held successor not ACKed; RM-F7 caught). The store change does not alter what is adopted (version and digest proofs unchanged, FM6/RM-F5 caught); it only decides who wins when a proven adoption and an older guarded read interleave, and the proven adoption wins. Residual (CF-G6): the mirror ordering (guarded refresh adopts a newer row first, then an older proven adoption resets the token) is pre-existing, requires a co-op/non-co-op crossing within one GET latency, and ends in the 409 conflict path, not a silent overwrite (`applySavedRecord` writes the token, metadata and cache key, never the live campaign).
- **Privacy.** Nothing new reaches the wire. The window and the catch send no frame; a rejoin's new `CampaignJoin` carries what E already defined (host: the fold is reset to EMPTY before connecting, so `lastSeq` is -1 and omitted; guest: the mirror's `lastSequence`, which the receipt-mode server ignores). The error text matched on the fixed prefix is never rendered by the consumer. The store serialises nothing new.
- **Replay.** The queue stays ordered: after a throw at step k, steps k+1..n run on the dead binding and neither fold nor ACK (RM-F3 caught). The window fires at most once per binding (cleared and never re-armed), and only one `rejoin` reaches the hook across the timer, the `onError` prefix, the catch and the Error-frame path (pinned: error frame then close -> two connects, not three). The generation is monotonic, so a guarded refresh that captured an older generation can never write later, whichever await it is parked on (both CF14 cases).
- **Idempotency.** `rejoin` is once-only by `live`; `heard()` is idempotent (`clearTimeout` on a cleared or undefined handle); `dispose` after `rejoin` is a no-op for the timer; a second `rejoin` from the catch after `settle`'s own is a no-op. RM-F1 survived because the leaked handle has no observable effect through `rejoin`'s guard; CF-G8 offers the timer-count pin.
- **Concurrency.** `consume` runs synchronously inside the transport's listener dispatch, so `heard()` on the first campaign frame always precedes a timer that could fire in the same tick; the T-1/T boundary is pinned. The chain's catch keeps later steps from waiting on a rejected predecessor. In the store the bump and `applySavedRecord` are one synchronous block, and the guarded refresh's check-and-write pairs are synchronous, so interleaving happens only at await boundaries, each of which re-checks the generation. Liveness judgement: against a server that accepts the socket and sends no campaign frame (the binder's silent `open() === false` return at `bindCampaignSyncConnection.ts:1252` is such a case), each rejoin arms a fresh window, so the client re-joins once per 60 s indefinitely; bounded (one `CampaignJoin` per T, no tight loop) and in the same class as the pre-existing immediate rejoin on a refusal, but worth a cap or a terminal state when the consumer leaf next opens (CF-G4). Against a legacy server the first legacy baseline ends the window, so there is no 60 s cycle in the G2 period, which is what the author's choice set out to avoid.

## 6. Judgments on the open points

1. **CF-F3 and "any campaign frame" (satisfied).** CF-F3 asked F to own a pre-receipt timeout because E's close signal is silent before receipt mode latches, and not to loop on `socket-closed` without the consumer's say. The implementation covers the gap E left: a bound connection that is closed, hung or never answered before its first offer rejoins once after one confirmation window. Clearing on any campaign frame rather than only on an offer is the right choice today for two reasons. (a) Against a legacy server (the G2 period, when creators bind before H installs the port) the first frame is a legacy baseline; an offer-only clear would rejoin every 60 s against a healthy legacy server, resetting the fold each time. (b) Against a receipt-mode server the binder hydrates a bound, membership-admitted connection exclusively through the application view (`bindCampaignSyncConnection.ts:1244-1249`, `:1276`, `:1412`; `joinMember` is never called when `application` is set), so the first campaign frame it sends is an offer, which latches receipt mode in the transport (`parseServerMessage` sets `receiptIntent` on any `appliedView`) and hands the close signal to E's CF12 from that moment. The window therefore never clears on a frame that leaves the connection unprotected. The dependency on (b) is a server invariant F does not pin; it belongs to the binder's next owner or H (CF-G5). Authority and privacy are untouched: the window only reconnects, and a reconnect sends only the join E already defined. The not-a-loop promise holds per binding; the 60 s cycle against a silent-but-open server is recorded as CF-G4.
2. **CF14, bump versus refuse (sound; the bump is the better of the two).** CF14 (my P2CF2 wording) offered either the generation bump in `adoptFlushedRevision` or a `migrated.version < get().baseVersion` refusal in the guarded path. The bump is a temporal fence consistent with how `loadCampaign` and `reset` already supersede a guarded refresh, independent of version arithmetic, and it is placed after both proofs, so an unproved adoption disturbs nothing (pinned). It is conservative: it also stops a guarded refresh whose row is newer than the adopted one; the consumer then reports `adjunct-failed`, the transport recovers and the view rejoins from EMPTY, which re-reads everything. That is correct for authority (nothing stale is written) and costs a reconnect in a case that requires a co-op host to race a non-co-op discard flush, which the live campaign's co-op flag makes nearly impossible. The refusal alternative would have let the newer row land but would not have covered a refresh held between its version check and a later await; the bump covers every boundary. The pre-existing mirror race (section 5, authority) is outside CF14's wording and is carried as CF-G6.
3. **RED shape for the CF-F3 quiet case (acceptable).** The case fails at RED with `TypeError: Cannot read properties of undefined (reading 'sentRaw')` because `connection.acks(1)` indexes a second socket that the baseline product never creates. The failure is behavioural, not a missing API: the test imports nothing that does not exist at the baseline, it typechecks against the baseline product (section 1 item 4), the TypeError is the direct consequence of the missing rejoin, and the same test's `withinWindow/afterWindow` assertion would have failed as `1 !== 2` had the index been guarded; its companion case ("starts nothing once disposed") fails on a plain `toBe`. The ledger's requirement that RED fail for the behaviour the unit delivers is met. A plain assertion would read better in the log; that is a test-only edit that cannot land post-RED and is carried as CF-G7.
4. **CF-F6 (lint and cycles).** 87 warnings / 0 errors at the head; the store's max-lines count moved 990 -> 991 (already warned since before F); the consumer does not warn; madge from F's two leaves 1100 files / 173 chains, as the author measured before and after.
