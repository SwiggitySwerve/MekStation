## C. Incremental reveal effects and replay

The owner's direction fits a server-derived knowledge stream. Keep canonical events/state authoritative and complete on the server. For each committed transition, fold the authoritative state and compare each viewer's prior knowledge with permitted knowledge now. Emit ordered reveal, permitted-field update, and visibility-loss effects. Movement of either observer or target, terrain/LOS, sensor changes and audited GM overrides can trigger them. Reveal must establish the permitted entity before dependent events reference it. Hidden movement updates no player position; visibility loss retains only allowed last-known fields, with stale time. Clients fold a dedicated view model, never an incomplete authoritative game reducer pretending to have full state.

Bootstrap contains own/revealed units and explicitly public facts only; unknown units must not become placeholders with identifiable metadata. Audit every supposedly public payload, including GameCreated, initiative/order and reveal batches. Apply existing open/rough/hidden intel tiers and sealed-choice rules separately. GM authority is an authenticated audience, not an exemption inferred from a host identifier.

Make projection deterministic from canonical prefixes plus historical membership, ownership, policy and GM reveal facts. Use versioned viewer checkpoints and delivery cursors scoped to match, viewer and branch/generation; persist explicit GM grants canonically and make automatic effects reproducible across restart. Live, replay, rejoin, HTTP history/export and digests must consume the same projector. Replay must not recompute past visibility using today's final state. Rewind builds a new candidate knowledge history, validates it, then activates atomically; old-generation cursors cannot resume it. Expose viewer-derived digests, never canonical hidden-dependent hashes. Hidden-only changes should not alter observable payloads/cursors.
