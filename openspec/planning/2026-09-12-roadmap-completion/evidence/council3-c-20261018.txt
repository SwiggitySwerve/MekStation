## B. Co-op lobby discoverability (PRIV-1)

`joinableLobbies.ts` returns any `lobby`-status match with an open human seat. Co-op sessions are created 1v1 with open human seats, and campaign join never fills `meta.seats`. They therefore stay listed with `roomCode` and `matchId` for any authenticated user. "List without code" still leaks that the session exists, the host's display name, and `matchId`. The G2A `campaignIdentity=1` invite read can then link that `matchId` to `campaignId` without a campaign seat. A campaign session is a private group, not a pickup game. The invite is the intended entry, and the browser has no product reason to show these sessions.

Risk for v2.2.0 is small. On loopback, the only authenticated users are the three seats. The fix is still cheap and well bounded: exclude campaign-session matches in `joinableLobbies` (and spectatable listing), using co-op metadata rather than layout guessing. Regression rows: an authenticated stranger sees no co-op row, code, or matchId; ordinary versus lobbies are unchanged; and an invite-link join by a campaign member still works.

B15-6 is a docs/honesty unit. Putting a sensitive product fix inside it mixes review classes and breaks the cadence rule that routine units skip the owner ruling. Split it out.

Recommendation: Hide co-op sessions from the lobby and spectate listings entirely (invite-only). Register **B15-PRIV1** as its own small sensitive (privacy) product unit in the B15 group (L2), ordered before B15-6. B15-6 keeps only the documentation and cites B15-PRIV1's exact-main PASS before any remote-procedure text. Also add one sentence to the v2.2.0 notes: co-op sessions are visible in the lobby list to other users of the same server.
Owner question (if any): Should campaign members ever see their own campaign's session in the browser (a "my sessions" view), or is the invite link the only entry?

## C. Fog design: incremental reveal effects

Architecture that implements the owner's direction:
- **Authority:** the server/GM `IGameState` remains the only full state. Each viewer has a *knowledge state*: own and allied units, plus revealed units at a reveal tier, plus last-known markers.
- **Reveal effects are derived, not commanded.** After every committed event, the server computes a `VisibilityDelta` per viewer from the existing `visibility.ts` rules (ownership/sensors/LOS) and emits viewer-scoped `UnitRevealed{unit, tier, fields}` / `UnitConcealed{unitId, lastKnownHex, staleAt}` effects. They follow the triggering event through the existing publication boundary, so delivery numbering stays per viewer. A GM manual reveal (spec "GM Intel Override", "Mid-match reveal emits audit event") uses the same effect with `source=gm`.
- **Opening:** `GameCreated` is projected per viewer. Hidden units are **absent**, not stripped. The client reducer must accept a unit introduced by a reveal. This is the real client change.
- **Determinism:** reveal streams are a pure function of journal + fog config + viewer. Live, join/rejoin from zero, HTTP history/export and rewind (U26) all re-derive the *same* viewer stream. Any digest a viewer receives is a viewer-stream digest, never the canonical one (consistent with B14-HEAD).
- **Co-op:** team-shared versus per-player knowledge must use the per-unit owner map. Today's `.find(side)` helpers recognise only one player per side.

Draft unit chain (15 files / 500 lines each):

| Unit | Scope | Fit |
| --- | --- | --- |
| F0 | spec/design: knowledge model, reveal/conceal effects, tiers, co-op policy (routine) | ~4 files / 200 |
| F1 | pure `computeVisibilityDelta` + tiered reveal payload in `src/utils/gameplay/` | ~6 / 350 |
| F2 | per-viewer `GameCreated` projection + client reducer unit introduction / last-known | ~8 / 400 |
| F3 | live emission in `ServerMatchHostEvents` / `fogOfWar.ts`; spectator = public-only knowledge | ~8 / 400 |
| F4 | replay/rejoin + `FogAwareMatchProjection` + metadata GET projection; live = replay = export parity | ~10 / 450 |
| F5 | lift B14-0/B14-HEAD refusal per surface; real-server probe; U2 fog rows E2E-2x | ~10 / 350 |
| F6 | co-op team visibility via owner map (if the owner chooses team-shared) | ~6 / 300 |

U26 (fogged rewind) and P5 34-40 then depend on F4 and do not redesign fog.

B14-0 does not conflict, with one wording point. Its spec delta should phrase the rule as "fog-on private reads SHALL be served only through a per-viewer projection; when none is available, refuse with `fog-projection-unavailable`". F5 can then MODIFY one requirement instead of removing a permanent refusal. Keep the policy as the single `fogMatchAdmission` predicate (already the prototype shape). Do not add tests that pin `GameCreated` as a public, full-roster event.

Placement: the owner accepted the refusal for v2.2.0, and fog-on is not in the L1 gate. Adding six or seven sensitive units before v2.2.0 would delay the first shared mission by roughly 15–20 hours for a feature L1 does not claim. Adding them to L2 would stretch the P3 exit contract, which does not include fog.
