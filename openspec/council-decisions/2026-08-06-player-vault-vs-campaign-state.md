# OMO Council — Player Vault vs Campaign State (and the MekHQ Comparison)

**Headline:** The architecture the question asks for was already decided when the CAMP-01 designs froze — copy-on-write with vault provenance (D1's reference + `unitSource` model) — and the real work is finishing it and retiring the contradictory `campaign-instances` spec, not choosing a model.

**Brief:** Decide how account-level player state (custom mech designs, pilots, player-card progression) relates to campaign state, settling the live-reference vs versioned-snapshot contradiction, with MekHQ as comparator.

## Synthesis

**Decision:** Adopt the three-layer model the code has already grown, and finish it:
1. **Vault (account)** — the design/pilot library plus lifetime records (`IPilotCareer` already does this for pilots). Vault entities are versioned templates: editing publishes a new version; nothing in a campaign mutates retroactively.
2. **Campaign instance (copy-on-write with provenance)** — roster entries reference vault identity (`unitRef`/`pilotId` + `unitSource`) and own ALL campaign-local divergence (damage in `unitCombatStates`, refits, campaign XP/wounds/death). Add the two missing unit-side fields (`unitSource`, `sourceVersion`), delete the fuzzy template match in favor of ID membership, and take the one-rung migration.
3. **Session/combat** — already separated (`IUnitCombatState`, event log); replays resolve stats by pinned version, never live vault reads.
Reconcile `openspec/specs/campaign-instances/spec.md` TO this model (rename its pilot half onto `ICampaignRosterEntry`; drop `CampaignUnitInstance` construction snapshots per D1) rather than implementing it. Sequence all of it AFTER CAMP-01F/G/H land — the frozen contracts assert today's roster shape.

**MekHQ's answer, for the record:** it dodges the question — no personal layer exists; everything lives in the campaign save; cross-save transfer is template-stamping (customs files, `.prsx` export). MekStation's cross-campaign vault is a deliberate improvement over MekHQ, and the genre-consistent way to keep it honest is exactly C: template-stamp semantics at campaign boundaries (like everyone), live identity within a campaign (like MekHQ's refit), plus provenance links nobody else has.

**Why:** Every seat independently converged on C from different evidence: it is the declared D1 architecture, it is the already-shipped pilot model, it is the only option satisfying replay determinism and coop-sync payload discipline, and it matches the only healthy cross-save patterns in the genre.
**Survival Score:** Modified — Oracle's mechanism (build the spec's instance types) was killed by the D1 verification; the strategic core survived intact into the D1-mechanism form.
**Trade-offs accepted:** Vault edits never auto-propagate into running campaigns (a "refit available" prompt is the UX instead); the dead spec is rewritten rather than honored; model work waits behind CAMP-01F/G/H.
**Second-order consequences:** Version-pinned instances make the future economy loop safe (refit costs bind to concrete version diffs); player-card meta-progression gets a clean home (vault lifetime records) without touching campaign simulation; coop stays light (ref + version diffs).
**Open risks / revisit triggers:** if the user wants MECHANICAL cross-campaign progression (vault pilots growing stronger for future campaigns), the vault needs its own state machine and coop-fairness rules — revisit then; the `sourceVersion` producer (vault version counter) must be designed when the post-CAMP wave is planned.
**Dissent on record:** None live after the D1 resolution; Oracle's phasing preference for building instance types per the spec is recorded as superseded by the D1 constraint.
