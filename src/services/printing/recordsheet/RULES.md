# Record-sheet figures

Construction and equipment owners decide numerical values. The customizer builders project their results into RecordSheetService; preview and export must use the same builder.

Explicit Mech crew rosters reuse the native MechCrewType owner and existing pilot schema. Extraction rejects incomplete, reordered or mislabelled slots; an absent pilot stays unassigned. No person is inferred, and no crew type is inferred for a Quad or Biped. A Tripod and a QuadVee are the exceptions, from one default in `extractMechData`: TripodMek.java:115-117 (MM 48fcb2f64) gives a Tripod TRIPOD, or SUPERHEAVY_TRIPOD when `isSuperHeavy()` (Mek.java:7167, weight > 100), QuadVee.java:164-166 always gives a QuadVee QUADVEE, and MML 62bf193 PrintMek.java:343-348 prints the single, dual or triple Warrior Data panel by slot count, named or not. So a Tripod or QuadVee without an explicit roster extracts the blank native roster (`blankMechCrew` over `getMechCrewType`); a QuadVee also gets the `quadvee` mech type (PrintMek.java:112-131; `getMechType` tests QuadVee before Quad). An editor-authored or explicit roster replaces the blank one. The `quadvee` type uses the quad armor and structure pip groups, which the QuadVee template carries. Existing specialAbilities stays crew-global; multi-slot rendering and authoring remain separate required work.

- ProtoMech extraction forwards the supplied pilot-SPA block built by spaSection, including designated headlines, to the existing fallback SVG renderer; canonical template/PDF SPA rendering is a separate concern.

- Vehicle BV uses computeVehicleBVFromState, including structure type and chassis protection. Its inferred structure layout reuses the shared support size owner for six-side large-support hulls; explicit installed location lists and VTOL layouts take precedence. Aerospace BV uses calculateBattleValueForUnit with the original subtype, support marker, thrust, heat sinks, armor total and mounts. Neither path reads a saved BV estimate. Aerospace source BAR ratings survive editor load, persistence and custom serialization, and both preview/export callers pass them to the dispatcher. The status bar uses that same dispatcher rather than rebuilding its own incomplete BV input.
- Small-unit preview/export callers pass the full typed source snapshot. All three sheet BV paths call calculateBattleValueForUnit; typed editor snapshots reuse the existing pure state BV owners, retaining native source protection, mount facts and field-gun ammo guards. Missing source is only the legacy partial-input compatibility path.
- BA header tonnage follows canonical default transport weight (squad size), not suit mass. Infantry transport tonnage uses calculateInfantryTransportWeight. ProtoMech topology comes from explicit chassis/main-gun facts.
- Ares loader configuration reuses deriveEffectiveConfiguration so the superheavy tripod cockpit retains its center-leg armor, structure and asset; other mech projections stay unchanged.
- The aerospace subtype selects the conventional fighter flag before sheet dispatch. Small craft retain motionType through both preview/export callers, builder, extractor and schema, selecting the pinned aerodyne/spheroid sheets. Craft side armor uses LS/RS anchors. The aerospace arc owner interprets editor wing aliases as sides only with SmallCraft context; native inputs and fighter behavior remain unchanged. SI and heat-sink markers use owner counts; double-sink text displays owner capacity. Bare rect pip regions are wrapped in valid SVG groups.
- Non-mech equipment keeps its mount id and catalog equipmentId separate. Resolve exact catalog identity/name through the equipment service; reuse the mech equipment formatter for damage, range and ammo figures. Unknown/partial names retain dashes. Explicit caller values (including zero) take precedence.
- Aerospace heat capacity calls calculateHeatDissipation through the shared heat-sink type mapper. Mech extraction remains unchanged.
- Vehicle motion labels preserve Hydrofoil, Submarine and Rail. The shared motion tuple owns both the TypeScript and Zod contracts. PrintTank template selection uses naval for Hydrofoil, submarine for Submarine, wige for standard WiGE, and vehicle for Rail and superheavy WiGE. Preview/export, extraction and the schema preserve the construction owner's isSuperheavy flag; printing never recomputes weight limits. The loader uses getSupportVehicleSizeIndex for support chassis and isSuperHeavyTank for combat chassis. VTOL always uses standard assets and still refuses the absent dual-turret template. Both paper manifests register every selected asset.

Enforcement: recordSheetFigures.test.ts covers the repaired boundaries; catalogRecordSheets.test.ts traverses all six committed indexes through production builders/extractors/selectors/bindings. It rejects repaired mismatch classes and snapshots the complete named residual digest/counts. Review snapshot changes against the emitted per-unit audit (RECORD_SHEET_AUDIT directory); never update snapshots to approve a new mismatch without investigation.

The model harness does not certify template equipment rows, pixels, PDF output, or MegaMek parity. Capital sheets (73c), auxiliary rule sheets and complete pixel/PDF fidelity remain follow-up work.

- Canonical vehicle/aerospace inventory bindings carry the already-resolved record-sheet equipment list to the shared equipment renderer before mounting. Complete-row mode preserves names, explicit zero ammo and every row within the template region; legacy mech table rendering keeps its existing behavior. Unresolved catalog tokens remain unresolved, without sheet-local aliases. Six-side vehicle armor preserves all four hull side locations and targets the pinned superheavy dual-turret RT anchor, while standard dual turrets keep TU.

- equipmentLocations owns native inventory abbreviations. Vehicle builders pass installed dual-turret identity; aerospace builders reuse aerospaceContractArc so small-craft sides/hull retain their native labels. These inventory abbreviations intentionally differ from SVG anchor suffixes (standard dual RT inventory versus TU armor). Legacy callers without an explicit abbreviation retain their compatibility projection.

- Vehicle mounted-equipment construction retains the resolved ammunition kind because ammunition and launchers can share a canonical ID. Loader and editor additions reuse that constructor; state and native-unit BV reuse one mount classifier. The vehicle serialization schema owns saved mount facts for loader, serializer and contract-to-BV projection, with aligned mount counts enforced at the boundary. The sheet builder passes the explicit kind to the existing equipment formatter. Legacy untagged mounts retain their ID-based compatibility classification. No catalog aliases or saved-BV substitutions are introduced.

Capital sheets use extractCapitalData, the frozen capital-view owner for armor/crew/transport/BV, the shared heat-sink owner, and the large-aerospace mount owner for source bay boundaries and per-arc heat. Any unresolved arc heat prints unavailable; a partial sum is never presented as complete. Complete BV and defensive-only BV retain their explicit scopes. Unknown hull shapes refuse. MML 62bf193 ships both DropShips, JumpShip, WarShip and Space Station templates in both paper formats. capitalRecordSheets.test.ts traverses all 394 capital definitions and counts unresolved catalog identities separately from projection differences. This model gate does not certify rendered pages.

Capital rendering uses the canonical front template plus advaero_reverse pages for overflowing inventories. Preview, browser printing and PDF export share RecordSheetService.getSVGPages; missing assets report an error. The read-only capital shell resolves a validated source definition without creating an editor store. Every page preserves source equipment names, bay/arc boundaries, crew/transport and scoped BV.
