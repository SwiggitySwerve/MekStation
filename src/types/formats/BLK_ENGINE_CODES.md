# BLK engine serialization facts

`blk-engine-codes.json` owns the serialized BLK number/name mapping. Keys are
decimal source codes and values are source-format identities, not construction
engine enums or Java runtime ordinals. Engine technology flags are independent.

The authority is MegaMek commit
[`48fcb2f64a1b3f2d575707ce5653dad64927b587`](https://github.com/MegaMek/megamek/blob/48fcb2f64a1b3f2d575707ce5653dad64927b587/megamek/src/megamek/common/loaders/BLKFile.java#L80):
`BLKFile` declares the codes at lines 80–93 and translates them to runtime engine
types at lines 538–568.

The Python conversion package reads this table relative to
`enum_mapping_tables.py`; running a converter from another working directory
does not change its meaning. `blk_vehicle_converter.map_engine_code` remains
the Python decoding boundary. Generic MTF aliases retain their separate
compatibility contract.

Family loaders decide whether to read an engine tag. The pinned ProtoMek loader
always creates fusion; the SmallCraft loader retains its ICE runtime placeholder.
The table itself does not select defaults, validate construction legality,
calculate engine mass or add those families to discovery.

`src/services/conversion/blkEngineIdentity.ts` adapts the same facts to existing
TypeScript model identities. Conventional fighter hydration uses this owner,
keeps the source code and independent Clan-engine context, and rejects known
identities its model cannot represent. SmallCraft hydration uses the ICE runtime
placeholder and warns with the ignored raw tag; this does not prove construction
validity. The handlers' public parse tests cover these boundaries.

The parser validates explicit engine tags for families whose loaders read them;
the fighter handler also validates typed documents containing raw tags. Only
omitted tags use the family default. This is deliberately stricter than upstream:
empty, malformed, comma-containing and multi-value tags are rejected, whereas
MegaMek logs errors and uses fusion for unparseable single values, strips commas,
and reads the first value of multi-value blocks. Typed documents without raw
tags retain numeric-code validation. These syntax differences remain source
fidelity gaps; passing corpus tests does not prove syntax parity.

TypeScript export and combat-vehicle hydration use the shared adapter. Export
writes ICE as 1, fuel cell as 6 and either XL variant as 2, with an explicit
`clan_engine` flag for XL. Vehicle entities retain the raw code and independent
Clan context; installed mass goes through the existing construction owner.
Known NONE alone becomes explicit absence (`null`) and has exactly zero engine
mass. Unknown or unrepresentable identities fail instead of becoming fusion or
absence. Engine-less editor stores, non-XL mixed-engine export flags, other
family hydration and complete persistence remain open work under tasks
2.1/3.2/3.3 of `establish-all-unit-data-parity`. Engine mass and legality remain
construction concerns.

Existing Python regression coverage is in
`scripts/__tests__/test_blk_engine_codes.py`: all known codes, omitted and invalid
tags, ignored-family behavior, MTF compatibility and batch no-write failure.
The extraction is additionally checked by complete before/after converter
outputs from fixtures and pinned original source bytes. Catalogs are not
regenerated by these checks.
