# BLK engine serialization facts

`blk-engine-codes.json` owns the serialized BLK number/name mapping. Keys are
decimal source codes and values are source-format identities, not construction
engine enums or Java runtime ordinals. Engine technology flags are independent.

The authority is MegaMek commit
[`48fcb2f64a1b3f2d575707ce5653dad64927b587`](https://github.com/MegaMek/megamek/blob/48fcb2f64a1b3f2d575707ce5653dad64927b587/megamek/src/megamek/common/loaders/BLKFile.java#L80):
`BLKFile` declares the codes at lines 80–93 and translates them to runtime engine
types at lines 538–568.

The Python conversion package reads this table relative to
`enum_mapping_tables.py`; running a converter from another working directory
does not change its meaning. `blk_vehicle_converter.map_engine_code` remains
the Python decoding boundary. Generic MTF aliases retain their separate
compatibility contract.

Family loaders decide whether to read an engine tag. The pinned ProtoMek loader
always creates fusion; the SmallCraft loader retains its ICE runtime placeholder.
The table itself does not select defaults, validate construction legality,
calculate engine mass or add those families to discovery.

TypeScript export and hydration still contain conflicting definitions in
`BlkExportServiceCore.formatters.ts`, `VehicleUnitHandler.ts` and
`ConventionalFighterUnitHandler.ts`. Their replacement is a separate behavior
change under tasks 2.1/3.2 of `establish-all-unit-data-parity`. No consumer should
add another source-code table while that work proceeds.

Existing Python regression coverage is in
`scripts/__tests__/test_blk_engine_codes.py`: all known codes, omitted and invalid
tags, ignored-family behavior, MTF compatibility and batch no-write failure.
The extraction is additionally checked by complete before/after converter
outputs from fixtures and pinned original source bytes. Catalogs are not
regenerated by these checks.
