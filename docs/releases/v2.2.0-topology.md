# v2.2.0 supported campaign topology

Release-note text prepared for the v2.2.0 release; this file is not a claim that the release has been published or its acceptance playtest has passed.

Publication handoff to Root: include both the supported-topology boundary and the Docker HOSTNAME-refusal/unsupported-hosting statement below in the actual v2.2.0 release notes. This disclosure must ship with v2.2.0; do not defer it until B15-6 updates README/compose after L1.

Campaign play in v2.2.0 is supported on **one machine**, using the Electron application or browsers connected to the local development server at `http://localhost:3600`. The server enforces loopback binding. Room codes identify sessions on that server; they do not connect another computer to it.

Fog of war is unavailable in multiplayer in this release.

**Campaign REST has no per-participant authorization. Do not expose the port through a reverse proxy or tunnel. Remote play is not a supported configuration in this release.**

Same-host play in a shared OS session has no inter-participant isolation: participants can access other windows, browser storage or local files. B15 does not change that property. Its purpose is to protect remote participant access in a future supported single-operator hosting configuration.

The acceptance playtest must record its actual same-host topology and the two players plus non-playing GM completing and reloading one shared mission. Multiple browser contexts alone do not prove remote play.

Current Docker production and uncorrected development-compose configurations fail the server's HOSTNAME admission check. Published ports and proxy labels are not evidence of a working hosted deployment. Docker hosting is unsupported; do not disable the loopback guard to make those configurations start.

B15 is scheduled in L2/P3 exit before any remote/tunnel support claim. It is not a v2.2.0 L1 prerequisite. The separate per-campaign owner-column requirement for multiple mutually untrusted operators remains open.

## Release publication

Releases are tagged manually. Only a repository admin can bypass the active
`release-tags` ruleset for `v*` tags. From the intended release commit, run:

```sh
git tag -a vX.Y.Z -m "Release vX.Y.Z"
git push origin vX.Y.Z
```

Auto Version and Release still computes and reports the next version, including
through `workflow_dispatch`, but never creates or pushes a tag. A push without
a version marker leaves the version unchanged.

The installer `release` job requires approval in the GitHub `release` environment
from SwiggitySwerve before publication. v2.2.x also requires the qualification
evidence for the tagged commit and a successful `--gate-check`; provide the
`qualification_run_id` through the Build and Release workflow's manual dispatch.
See the [v2.2 evidence contract](../../openspec/planning/2026-09-12-roadmap-completion/V220-EVIDENCE.md).
Docker publication remains separate and is disabled for v2.2.x.
