## Findings

### 1. [P2, recommended pre-merge, single-line fix] CLI --x64 is overridden by explicit per-target arch lists in electron-builder.yml

Reference: release.yml:281-282; electron-builder.yml win.target (nsis arch [x64, ia32], portable arch [x64]).

Mechanism (app-builder-lib 26.15.7, the version locked in desktop/package-lock.json; fetched from unpkg and
compared with the locally installed 25.1.8, identical logic):

- electron-builder/out/builder.js normalizeOptions: "--win --x64" with no target types yields
  archToType = { x64: [] } (no explicit targets).
- app-builder-lib/out/targets/targetFactory.js computeArchToTargetNamesMap: because no entry has
  target names, it does NOT return early; it iterates the config targets and, when a target declares
  its own arch list, uses THAT list rather than the CLI arch. Result: { x64: [nsis, portable], ia32: [nsis] }.

Empirical confirmation (the real function executed against a mock of the repo config; output verbatim):

    --win --x64                 => [["x64",["nsis","portable"]],["ia32",["nsis"]]]
    --win nsis:x64 portable:x64 => [["x64",["nsis","portable"]]]
    --win (no arch)             => [["x64",["nsis","portable"]],["ia32",["nsis"]]]

Consequences:

- NsisTarget.finishBuild with two archs and an artifactName containing arch builds the combined
  MekStation-2.1.0-win.exe AND per-arch MekStation-2.1.0-win-x64.exe / -win-ia32.exe (this is why
  v1.4.225 has 22 assets including win-x64, win-ia32 and win). The ia32 installer and the ia32 half of
  the combined installer embed the x64-rebuilt next-standalone native payload, i.e. they are not usable.
- Electron 43.2.0 does publish win32-ia32 (checked the release asset list), so the extra build does not
  fail; it only adds runner time and publishes defective 32-bit artifacts.
- The new inventory check (lines 340-343) still passes because MekStation-2.1.0-win-x64.exe exists
  (verified with a synthetic release-upload containing x64, ia32, combined and portable). The manifest
  check also passes because latest.yml references files that are present.
- PR statements "Windows x64 packaging", "The standalone native payload is rebuilt for this x64 runner
  only" (line 281 comment) and "Windows is x64 only" are therefore not achieved by this diff.

Fix (release.yml:282), either form restricts the build to x64 because explicit target types make
computeArchToTargetNamesMap return the CLI map unchanged:

    run: npx electron-builder --win nsis portable --x64 --config.extraMetadata.version="$APP_VERSION" --publish never

or

    run: npx electron-builder --win nsis:x64 portable:x64 --config.extraMetadata.version="$APP_VERSION" --publish never

With a single arch, NsisTarget uses primaryArch = x64 and the user artifactName pattern, so the
installer is still named MekStation-2.1.0-win-x64.exe; portable remains MekStation-2.1.0-portable.exe;
latest.yml then references only the x64 installer. Lines 340-343 need no change. (The macOS command at
line 289 already passes explicit types "dmg zip", which is why --arm64/--x64 DO take effect there.)
If the fix is deferred, update the PR text and the publish checklist to expect 22 Windows+other assets
rather than 18, and treat the ia32 and combined EXEs as known-defective.

### 2. [P3, informational] No concurrency group

release.yml defines no concurrency. For the first run this is harmless: an ordinary merge to main during
the release triggers auto-version (bump none) -> workflow_run -> release-context resolves no tag at that
head and exits 0 (lines 54-58), so only one cheap job runs. Two overlapping real tag releases would run
concurrently; a later tag mints a separate GitHub release, so there is no corruption, only runner cost.
Optional follow-up: concurrency group keyed on the resolved tag, cancel-in-progress false.

"release" job and the resulting release assets. At the head, desktop/electron/securityPolicy.ts exists
and .dockerignore un-ignores it, so the July missing-module failure is addressed in source; no container
build was run here.

### 4. [Informational] Two latent defects that the PR fixes are now independently corroborated

- Release notes size. A read-only call to POST /releases/generate-notes with tag_name=v2.1.0,
  target_commitish=main, previous_tag_name=v2.0.0 returned a body of 174,421 characters (1,332 commits
  since v2.0.0). The pre-PR step passed that body untruncated to softprops v1, which would have failed the
  Create Release call against the 125,000-character limit. The head slices the body to 50,000 characters
  (line 557) and appends at most 100 commits (lines 528/532; the latest 100 subjects on main total 8,205
  characters), so the final body is about 59k. softprops v3 additionally truncates to the API limit.
- Hidden Next.js output. actions/upload-artifact v7 defaults include-hidden-files to false and its
  globber skips any path whose basename starts with a dot and does not descend into it
  (@actions/glob internal-globber.ts). The standalone payload lives at .next/standalone/.next/\*\*, so
  without line 169 the web-build artifact silently loses the Next server build. The May and July green
  runs used upload-artifact@v7 without include-hidden-files; whether their packaged apps were runnable was
  not verified here (no asset was downloaded). Line 169 is required with the referenced action.

### Permissions

Repository default workflow permissions are read. Jobs without an explicit permissions block
(release-context, prepare-build, build) only check out, cache, and upload/download same-run artifacts,
which do not need write scopes. docker-build: contents read. docker-push: contents read + packages write.
release: contents write, sufficient for generate-notes, release creation and asset upload. No job
depends on a scope it lacks. VERIFIED.
