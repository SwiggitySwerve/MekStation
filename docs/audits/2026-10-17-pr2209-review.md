### 3. Weight-class derivation

`resolveWeightClass` reuses `getWeightClass` from `@/types/enums/WeightClass` (not duplicated). The repo helper's ranges are canonical: ULTRALIGHT 10–15, **LIGHT 20–35, MEDIUM 40–55, HEAVY 60–75, ASSAULT 80–100**, SUPERHEAVY 105–200. The `??` fallback is correct in practice: `ICustomUnitRecord` (what the API spreads into the response) has `tonnage: number` and **no** `weightClass` field, so `stored` is always `undefined` and derivation always runs. **Pass.**

_Note (pre-existing, not this PR):_ `getWeightClass` falls through to `SUPERHEAVY` for any tonnage not on a 5-ton step (e.g. 37, 62.5) because the ranges are inclusive-integer gaps rather than thresholds. Custom 'Mechs are always 5-ton multiples so this is not reachable from the detail page today, but vehicles/ProtoMechs with odd tonnage would mislabel. Worth a threshold-based rewrite in a follow-up.

### 4. `extractWeapons` does not drop real weapons

Pattern: `/(^|[-_\s])ammo($|[-_\s])|heat[-_\s]?sink/i`, applied to the _source_ id/name string (`equipmentId` → `weaponId` → `id` → `name`, first that resolves in the catalog, else first present).

- `ammo` is word-bounded by `^ $ - _ space`, so `ac-10-ammo`, `ammo-lrm-20`, `LRM 20 Ammo` match; `mammoth`/`ammonia`-style substrings would not. `heat[-_\s]?sink` matches `heat-sink`, `heatsink`, `Heat Sink`, `double-heat-sink`.
- **Exhaustive scan** (throwaway test in the worktree, since deleted): walked every entry in `WEAPON_CATALOG_FILES` (all catalog JSON modules) plus `WEAPON_DATABASE` keys/names plus `WEAPON_ID_ALIASES` keys — **485 weapon entries, 0 matches** on either `id` or `name`. No official weapon, legacy DB entry, or alias is skipped by this pattern.
- The skip is placed _after_ the "no id" warning and _before_ the catalog lookup, so ammo/heat-sink mounts no longer produce the spurious "has no official weapon catalog entry" warning. `ammoFromWeapons` reads `ammoState`, not the equipment array, so ammo accounting is unaffected.

**Pass.**

### 5. Event-log name resolution vs fog/hidden units

- The formatter is a **client-side presentation** step. In server-authoritative multiplayer, events are filtered per recipient _before_ broadcast (`ServerMatchHostEvents.ts` → `filterEventForPlayer` / `filterEventForSpectator` in `server/fogOfWar.ts`); fog-withheld events are omitted and e.g. `attack_resolved` is collapsed to a redacted payload. The client formatter therefore only ever sees ids the server already chose to disclose.
- `actorLookup` is built from `session.units` — the roster the client already holds. The PR changes the lookup _value_ from `unitRef` (catalog id such as `shadow-hawk-shd-2h`, which already discloses chassis/variant) to `unit.name`; it does not add any id → anything mapping the client did not already have. Ids absent from the lookup fall back to the raw id, as before.
- Net: no new disclosure surface. The PR neither widens which ids reach the client nor resolves ids from any source other than the client's own roster.
- _Caveat (pre-existing, out of scope):_ P2P/mesh fallback has no server redaction (`server/TRANSPORT.md`), and I did not re-audit `fogOfWar.ts` for completeness across every event type carrying `spotterId`/`targetId`. Neither is changed by this PR.

**Pass.**
