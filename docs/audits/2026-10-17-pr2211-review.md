## Blocking item (concrete fix)

### B1. Fog-of-war now leaks a non-owned custom unit's critical layout through `GameCreated`

- The PR seeds `criticalSlotManifest` onto every `IGameUnit` inside the `GameCreated` payload (`InteractiveSession.setup.ts` `adaptedCombatSeedPatch`). That is the right event-sourced design (see R1 below), but `src/lib/multiplayer/server/fogOfWar.ts:123-137` only redacts `customUnitDefinition` from units the viewer does not own. The manifest is left in place and carries, per slot, `componentName` (e.g. `AC/20`, `AC/20 Ammo`, `Medium Laser`), `componentType`, `weaponId`, `ammoBinId`, `linkedCriticalWeaponId` — i.e. the hidden saved-design layout the existing `customConstructionVisibility.test.ts` invariant ("reveals only owner construction") is meant to protect.
- Proven with a throwaway probe at head: fogged `filterEventForPlayer(event, 'owner', state, { fogOfWar: true, canSeeUnit: () => true })` strips `opp-construction` from the opponent's `customUnitDefinition` but the opponent unit still carries `criticalSlotManifest.right_torso[0] = {slotIndex:0, componentType:'weapon', componentName:'SECRET-AC/20', ...}`.
- Scope: only matches with `config.fogOfWar === true` (default `false`, see `coopMissionCreate.ts:76`, `joinableLobbies.ts`) and only meaningful for custom units (canonical layouts are public via `unitRef`). Still a regression of an explicit secrecy invariant introduced by this PR, and AGENTS.md lists fogged-event leakage as an anti-pattern.
- Fix (small, testable): in the `GameCreated` branch of `filterEventForPlayer` (and the spectator path) drop `criticalSlotManifest` alongside `customUnitDefinition` for units the viewer does not own — at minimum when the unit carries a `customUnitDefinition`, preferably for every non-owned unit since the manifest is server-authoritative state the client never resolves. Add a case to `customConstructionVisibility.test.ts` asserting `criticalSlotManifest` is absent on the other side's unit and present on the viewer's own. The field is optional in the strict `gameUnitSchema`, so per-audience `GameCreated` divergence (already the case for `customUnitDefinition`) stays gate-clean for `mirrorMatchSession`.

## Verified (approve)

### R1. Replay compatibility

- `criticalSlotManifest` was already an optional field on `IGameUnit` (`GameSessionUnitTypes.ts:292`) and `IUnitGameState` (`GameSessionStateTypes.ts:554`); the reducer already copies it from the `GameCreated` unit (`gameState/initialization.ts:198`) and damage resolution already falls back to `buildDefaultCriticalSlotManifest()` when it is absent (`gameSessionAttackResolution.damageEvents.ts:172`). No reducer, event type, or payload shape changed. Pre-PR logs therefore replay byte-for-byte to the same state as before (deterministic legacy fallback), and new logs carry the layout in the event so recovery/replay/multiplayer derive the same manifest. Probe: live session with HBK-4G / BMB-12D / Behemoth 4 -> `hydrateGameSessionFromEvents` reproduces identical manifests; stripping the field from `GameCreated` reproduces the old (`undefined` -> default) path.
- Contracts: `src/types/contracts/generated/*.zod.ts` are unit-data contracts, untouched and not applicable. The replay gate schema `gameUnitSchema` (`CombatLifecycleSharedSchemas.ts:548`) is `.strict()` and already declares `criticalSlotManifest: criticalSlotManifestSchema.optional()` with a strict entry schema; `buildStructuralCriticalSlotManifest` emits only `{slotIndex, componentType, componentName, destroyed}`. Probe: `gateReplaySurfaceHistory(..., {formatId:'match-log-idb', formatVersion:2})` -> `accepted` for the new `GameCreated`; injecting one unknown key into an entry -> `blocked: invalid-payload ... combat.game_created.v1.custom-construction-1`, so the acceptance is a real strict pass.
- Recovery paths reduce events (`hydrateGameSessionFromEvents`, `foldMatchSession` from checkpoint JSON which stores the full `events`), so the new emit-time dedupe guard cannot alter replay of stored logs; the kill-count change for old logs is confined to `derivePostBattleReport` as claimed.
- Multiplayer authority: `matchUnitBootstrap.ts` -> `adaptUnit` -> `adaptUnitFromData` (now hydrates the manifest) -> `InteractiveSession` ctor -> `gameUnitsWithAdaptedCombatSeeds` -> `GameCreated`. Server resolves, clients mirror the broadcast; no client-side resolution added. `GameCreated` grows ~7 KB per mech (23,350 bytes for three mechs); `ws` server uses default `maxPayload`, no custom limit.
- Custom-unit recovery: `customCombatSnapshotSchema` includes `engine`, `gyro`, `techBase`, `unitType`, `criticalSlots`, so re-adapting from a recorded snapshot yields the same engine-aware base; and since the manifest is now in `GameCreated`, re-adaptation is not even on the replay path.

## Non-blocking notes (follow-ups)

- N1. The idempotence guard covers `appendUnitDestroyedEvent` in `gameSessionAttackResolutionHelpers.ts` (weapon damage, ammo explosions, vehicle attacks, DFA miss, AirMek landing, heat ammo explosion). Two session-path emitters still call `createUnitDestroyedEvent` directly: `gameSessionHeat.criticalEvents.ts:170` (no guard) and `gameSessionPhysicalResolution.ts:268` (guards on `currentState.destroyed`, which the PR's own comment identifies as insufficient after a fatal PilotHit). The simulation runner's separate `appendUnitDestroyedEvent` (`simulation/runner/phases/utils.ts:137`) has no guard. Route these through the log-based guard for the "exactly once per unit" claim to hold everywhere.
- N2. "Old logs replay to kills: 1" holds for `derivePostBattleReport` only. `combatStatistics.projectKillCredits` / `projectUnitPerformance` and `morale/moraleShift.computeMoraleShifts` still count every `UnitDestroyed` event. `combat-analytics` literally specifies one credit per event, so this is spec-consistent, but views disagree for pre-PR logs; decide whether those projections should dedupe by `unitId` too.
- N3. `EngineType.XXL` carries `sideTorsoSlots: 3`; TechManual XXL is 6 per side torso (IS) / 4 (Clan). Pre-existing data issue, but the new `it.each` row now enshrines `[0,1,2]` for XXL. Suggest fixing `EngineType` (and adding an XXL Clan variant) in a follow-up and updating that row; the derivation code itself needs no change.
- N4. `tactical-movement-intent` is silent on an empty composition; the PR adds behaviour ("Lock-In with nothing composed commits Stationary") without a spec delta. Add a scenario under "Budget Resolver and Explicit Lock-In" (and the `@spec` annotation already points there). UX: Lock-In is now enabled with nothing composed, so a stray click ends the activation as Stationary; the hint text makes this explicit, which is probably sufficient for a patch release.
- N5. `intentToMovementDeclaration` can no longer return `null`; the nullable signature is kept "for defensive callers" — fine, but the dead `if (!declaration)` branch in `commitComposedMovement` could be removed later.
