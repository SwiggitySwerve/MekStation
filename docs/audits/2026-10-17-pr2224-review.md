1. Principal is server-derived; client-named identity has no path in

The GET branch calls authenticateRequest(req) (src/lib/multiplayer/server/auth.ts:368-375) which extracts the wire token from the Authorization: Bearer header (query ?token= fallback), then verifyPlayerToken enforces expiry, issuedAt drift, playerId === derivePlayerId(publicKey) (pid-mismatch otherwise), and an Ed25519 signature over canonicalTokenPayload under the embedded key. The handler compares only auth.playerId against meta; req.query.playerId, req.body, and x-player-id headers are never read. A scoped (socket) token fails closed as scope-unchecked -> 401 because the route passes no expectedScope; that is pre-existing and unchanged. The test "uses the verified bearer identity despite client-named principal claims" sets query playerId/role, a body, and an x-player-id header to the host's id while bearing an outsider token and expects the 404 body; mutant m5 (host check reads req.query.playerId) is killed only by that test, which shows the test discriminates.

2. Membership source matches the WS host's durable record, deliberately narrower

The WebSocket admission path is ServerMatchHost -> MatchSeatMembershipSource (src/lib/multiplayer/server/authorization/MatchSeatMembershipSource.ts), which reads store.getMatchMeta(matchId) and derives membership from (a) meta.seats when present: seats of kind human OR spectator whose occupant.playerId is the principal, plus a lobby-phase invitee grant while status === 'lobby' and an open human seat exists or the principal is on playerIds; or (b) meta.playerIds when seats is absent (Wave-1 / co-op mission matches). AI seats never confer membership.

The route reads the identical IMatchMeta row from getDefaultMatchStore() and applies: hostPlayerId === principal, OR (seats undefined ? playerIds.includes(principal) : some seat with kind === 'human' and occupant.playerId === principal). Differences from the WS source are the three the PR comment names, and each is correct for this surface:

- Spectator seats excluded. openspec/specs/multiplayer-server/spec.md:870-926 says a spectator "SHALL NOT be recorded as a match participant" and in fog-on matches "SHALL receive only the most-redacted view - never more information than the least-informed participant". IMatchMeta.unitBootstrap carries startHex, pilotRef, gunnery, piloting for every unit (IMatchStore.ts IMatchUnitBootstrapEntry) and coopCampaign.state carries the full authoritative campaign state; handing that to a spectator would defeat the fog scope the spec mandates. The spectator registration route (matches/[id]/spectate.ts) returns only slotId/matchId/wsUrl, so spectators have no precedent for reading meta. Exclusion is spec-consistent.
- Lobby-phase invitees excluded. The WS grant exists so a room-code joiner can open the socket before OccupySeat; it is not a data-read grant. The invite route (invites/[roomCode].ts) returns only matchId/status/layout and the lobby list returns summaries; the test "keeps public discovery and room-code resolution available" pins both and asserts no unitBootstrap/coopCampaign/SECRET material in either body.
- Host/GM admitted without a playing seat. Co-op creation seats the host on a spectator seat (matches/index.ts:178 hostSeatKind = 'spectator' when coopCampaign is present, defaultSeatsWithSpectatorHost). The hostPlayerId clause covers the GM; test "returns full metadata to the GM/host without a playing seat" pins it and kills m1. GM identity in MatchSeatMembershipSource is derived from the durable campaign_session_participant gm row for role purposes only; the host identity (hostPlayerId) is what DELETE on the same route already trusts, so GET and DELETE now agree on who the host is.

Co-op mission matches (coopMissionCreate.ts:260-290) are created with playerIds and no seats key; DurableMatchStore.getMatchMeta is JSON.parse(meta_json) (DurableMatchStore.ts:1649-1652) and JSON.stringify drops undefined, so seats stays absent on read and those players fall into the playerIds branch, matching ServerMatchHostReconnectLifecycle.ts:44-51 which uses the same seat-then-roster fallback. Tests "preserves pre-seat membership from the stored player roster" / "does not grant outsiders pre-seat roster access" cover that branch. Current seats override a stale roster (test "uses current seats rather than a stale playerIds roster", kills m3), which is the right precedence because playerIds is a creation-time roster while seats is live lobby state.

3. 404 vs 403 against sibling routes

Siblings refuse authorization with 403: the match-history chain uses a constant 403 (src/pages-modules/api/matchHistoryViewerChain.ts:268-279, matchHeadRoute.ts:57) and DELETE in this same file answers 403 "Only the host may close the match" for a non-host. This PR chooses 404 with the exact MatchNotFoundError body for non-participants so that an unknown match and a forbidden match are indistinguishable (test "makes an unknown match indistinguishable from a forbidden one"). For a read of privacy-sensitive data that is the better choice and is what the task brief asked for; it is a documented divergence, not an accident. F1 below notes the remaining existence oracle.

8. Non-blocking follow-ups (not defects introduced by this PR)

- F1 Existence oracle via DELETE on the same path. A non-host outsider issuing DELETE /api/multiplayer/matches/:id receives 403 for an existing match and 404 for an unknown one, so the indistinguishability this GET now provides is not route-wide. Lobby-status matches are discoverable by design through /lobbies anyway; for active/completed matches the DELETE 403 is the residual signal. Low severity (existence only, no payload); a one-line change to return 404 on the non-host DELETE branch would close it if desired.
- F2 Intra-match disclosure to seated opponents. The full IMatchMeta returned to any seated human includes unitBootstrap for both sides (opponent startHex, pilotRef, gunnery, piloting) even when config.fogOfWar is true, and the whole coopCampaign.state. B9's scope is strangers, and no product client reads this GET today, so this is not a regression and the surface is currently unused; but if a client is ever pointed at this route, a per-viewer redaction (or dropping unitBootstrap/coopCampaign from the GET body) should land first. Suggest registering this as its own B-item.
- The route still loads meta before the membership check and the 404 message echoes the requested id; both are fine (the id came from the caller) and match the pre-existing not-found body.
