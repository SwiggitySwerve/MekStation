## 1. Loading, equipment and customization

**Shared Java pipeline.** `M:src/megamek/common/loaders/MekFileParser.java:203` dispatches MTF to MtfFile and BLK by UnitType: Tank/Naval/Hydrofoil, VTOL, infantry, BA, ProtoMek, support/large-support/VTOL support, aerospace/conventional/fixed-wing support, small craft, dropship/jumpship/warship/station and handheld weapons (:209–228). MTF retains backward-compatible version/chassis/model handling (`M:src/megamek/common/loaders/MtfFile.java:605`). MML loads through that parser and saves MTF or BLK (`L:src/megameklab/ui/util/TabUtil.java:106,114,199`). MekHQ resolves a summary's source file plus ZIP entry through the same parser (`H:src/mekhq/campaign/Campaign.java:1187`); its export also writes MTF/BLK and refreshes the cache (`H:src/mekhq/gui/adapter/UnitTableMouseAdapter.java:1407,1413,1421`). These are shared engine entities, not three independent format implementations.

**Cache and user units.** `M:src/megamek/common/loaders/MekSummaryCache.java:83,237,250` initializes equipment and reads Java-serialized `units.cache`; source existence and file/ZIP timestamps control reuse (:262,828,911). It scans data/mekfiles, internal userdata, configured external user directory and story arcs (:293–313), suppressing unofficial directories when requested (:806). Canon status is separately stored from `Entity.isCanon()` (:500). `name_changes.txt` provides unit lookup aliases (:84). Thus cache contents are derived, environment-dependent data, not a published BV oracle or content-addressed catalog.

**Equipment.** `M:src/megamek/common/equipment/EquipmentType.java:729,737,751,762` registers internal names and lowercase lookup aliases, then initializes weapon/ammo/misc/bomb/armor types. Display names are not automatically valid keys. BLK loading parses equipment options, resolves names with tech-prefix fallback and records failures (`M:src/megamek/common/loaders/BLKFile.java:226,276,280,337`). MekStation instead has JSON equipment catalogs, explicit alias maps and lookup normalization (`S:src/services/equipment/EquipmentRegistry.ts:148,191,227`). Python conversion merely normalizes strings (`S:scripts/megameklab-conversion/enum_mappings.py:346`); that is not equivalent to Java registry resolution. Unresolved BV equipment becomes zero with `resolved:false` (`S:src/utils/construction/equipmentBV/resolution.ts:74`), so validators must assert resolution rather than merely obtain a number.

**Data layout/versioning.** mm-data holds mekfiles, universe, RATs, boards, images, sourcebooks and campaign/scenario data (`D:README.md:3`; `D:build.gradle.kts:15,25,33,53`). Packaging creates `unit_files.zip` and excludes cache files (:14,71). MekHQ separately loads planetary YAML (`H:src/mekhq/campaign/universe/Systems.java:239`). Suite settings use the sibling mm-data Gradle build (`E:/Projects/Personal/megamek/settings.gradle:2`). MekStation's `scripts/mm-data` currently fetches record-sheet assets, not unit/universe catalogs: `S:config/mm-data-assets.json:2–4` pins v0.3.1 and images/recordsheets; `S:scripts/mm-data/fetch-assets.ts:39,98,265` chooses output, downloads and writes a version manifest. Python uses MM_DATA_ROOT or an obsolete machine default (`S:scripts/megameklab-conversion/enum_mappings.py:30`). Pass the explicit local data path.

MekStation preconverts MTF into era/rules JSON plus index (`S:scripts/megameklab-conversion/mtf_converter.py:151,175`). Its canonical browser service loads only battlemechs (`S:src/services/units/CanonicalUnitService.ts:80,152`). Current inventory: 4,225 indexed mechs, 4,226 mech JSON files including index; three BA and three infantry JSON fixtures; no vehicle, aerospace or ProtoMek directories. Custom units use separate persistence/version endpoints (`S:src/services/units/CustomUnitApiService.ts:313,438`), not Java user-directory overlays. The import dialog accepts JSON only (`S:src/components/customizer/dialogs/ImportUnitDialog.parts.tsx:192`); direct MTF import explicitly returns unimplemented (`S:src/services/conversion/MTFImportService.ts:87`). BLK parser/handler code exists, but its existence does not demonstrate a complete custom-import UI.

## 3. Ranked correctness/customization gaps and ownership

1. **Critical: wrong BLK engine enums.** In-memory Scorpion Light Tank (LRM) conversion maps source engine_type=1 to XL, although BLK 1 means ICE; Sabre SB-27b-EC maps 2 to Light rather than XL. Evidence: `D:data/mekfiles/vehicles/3039u/Scorpion Light Tank (LRM).blk:70`, `D:data/mekfiles/fighters/Golden Century/Sabre SB-27b-EC.blk:87`; `M:src/megamek/common/loaders/BLKFile.java:71–84` versus `S:scripts/megameklab-conversion/enum_mapping_tables.py:91` and `blk_vehicle_tables.py:42`. Fix BLK-specific numeric tables, retain textual MTF mappings, cover every engine code and roundtrip representative inputs. **New nonmech-conversion backlog**, coordinate shared converter paths with U79.

2. **Critical: converter/consumer mismatch.** Python vehicle output has nested armor and equipment.id (`S:scripts/megameklab-conversion/blk_vehicle_converter.py:248`; `blk_unit_fields.py:60`); adapter reads top-level armor and equipmentId (`S:src/utils/construction/vehicle/vehicleBVAdapter.ts:272,291`), dropping armor type (:326). Aerospace similarly emits armor.byArc (:291) while its adapter reads totalArmorPoints (`S:src/utils/construction/aerospace/aerospaceBVUnitAdapter.ts:117`). Java initializes armor and mounts explicitly (`M:src/megamek/common/loaders/BLKAeroSpaceFighterFile.java:184,201`). Add one validated conversion boundary preserving armor/turrets/mount options/BAR before parity. **New backlog**, with fixture lane dependent on this repair.

3. **High: registry and semantic loss.** Java alias/prefix/options handling versus slug-only conversion above can lose tech identity, rear mounts, sizes and ammo quantities. Mixed Clan chassis provenance is already acknowledged lost (`S:scripts/validate-bv.ts:45–49`). Export an attributed registry alias manifest; preserve original names/options/chassis tech and reject unresolved gameplay equipment. **U79 owns mech reproducibility; new nonmech semantic-parity successor**, not a wider U79 scope by assumption.

4. **High: missing discovery/type coverage.** Python skips LargeSupportTank and capital classes (`S:scripts/megameklab-conversion/blk_vehicle_tables.py:7`; `blk_aerospace_tables.py:14`) while Java supports them. Canonical service remains mech-only. Add per-type catalog/index contracts and honest supported-type diagnostics before exposure. **New backlog**, defer automatic catalog expansion; P7 expressly excludes it.

5. **Medium/high: reproducibility and custom import.** Pin units/equipment/converter hashes separately from record sheets; U79→U80→U81→U82 already owns reproducibility, publication, build consumption and untracking (`S:openspec/planning/2026-09-12-roadmap-completion/units.json:15799,15835,15878,15922`; planned/blocked). Raw MTF/BLK import UI is a **new backlog**; published revision authority, provenance migration, minted instances and refit divergence remain **P7 tasks 88–93**, not ledger units U88–U93. Evidence: `E:/Projects/Personal/MekStation/.omo/plans/mekstation-phased-delivery-20261015/PLAN.md:125–133`; entry is 87+68→88. Do not bypass those dependencies through an importer.
