## Verdict in one paragraph

The STOP is correct. Claim 1 is true for the socket door and only partly true for the HTTP door; claim 2 is true; claim 3 is true for both real commit doors and false for the launch-authority preflight; the proposed order is sound in shape but needs three corrections (the activation predicate must be installed on the campaign host registry, not handed to the binder or session alone; C must precede K because binding creators today changes the join frame; legacy deletion fits neither C nor S and needs its own unit after activation). The honest shape is nine ordinary-cap successors registered by one three-file registration PR that supersedes P2CG1 exactly as P2CE and P2CF were superseded, with the activation predicate frozen in the successors' contracts. Every intermediate main keeps today's legacy behaviour until the one activation merge (S), and S's proof must include the real two-browser journey.

## 1. Verdicts on the implementer's claims

### Claim 1 - "production never connects the receipt path; removing MAX(acked_sequence) and the in-memory credit refuses every co-op AdvanceDay and every session-bearing launch-authority POST; the e2e fails at advance-day"

**Socket door: TRUE.** **HTTP door: PARTLY TRUE** (true in code, unreachable by today's production clients).

What happens today, traced:

- `server.js:656-665` composes `bindCampaignSyncConnection({socket, matchId, verifiedPlayerId, logger, membership, forceClaims})`. No `applicationReceipts`. `bindCampaignSyncConnection.ts:332-343` builds `application` only when `membership && applicationReceipts`, so in production `application` is `null` on every connection. No offer is ever sent, no receipt ACK is admissible (`:710-727`), and no `campaign_public_applied_view` row is written. `grep applicationReceipts src server.js` outside tests hits only the binder (the P2CE2 and P2CF2 reviews recorded the same).
- Socket door today: `refuseUnconvergedProgression` (`bindCampaignSyncConnection.ts:811-828`) is called before the host commit at the three AdvanceDay sites (`:860-867` host intent, `:1372-1381` auto-approve proposal, `:1436-1444` GM approve). It calls `entry.syncSession.evaluateScenarioLaunch()` (`CampaignSyncSession.ts:844-868`), which runs the three durable clauses and then compares the in-memory `retained` map. Guests are seeded converged at hydration (`:578-592`, "Never the GM"), and the legacy numeric `CampaignAck` advances the map through `noteParticipantAcknowledged` (`bindCampaignSyncConnection.ts:727-734` -> `CampaignSyncSession.ts:753-762`). The client sends that numeric ACK on every `CampaignEvent` while not in receipt mode (`campaignSyncTransport.ts:453-473`). This is the only credit the socket door has, and it works: the e2e `advance-day-btn` step (`e2e/coop-campaign-two-browser-journey.spec.ts:365-377`) passes on it.
- P2CB evaluator: `deriveLaunchView` (`campaignPublicAppliedView.ts:398-449`) refuses `gm-required` when no retained roster member has `seat === 'gm'` (`:412-413`), and marks a seat behind when `row === null` (`:433-444`). The roster is `listActiveCampaignSessionParticipants` (`campaignProgressionReaders.durable.ts:95`), which includes the GM seat the host arm binds (`bindCampaignSyncConnection.ts:1101-1106`). With no rows anywhere, every retained seat including the GM is behind.
- Therefore: switch the socket door to the P2CB evaluator and delete the retained-map credit, and every production AdvanceDay on every path is refused `CAMPAIGN_NOT_CONVERGED`; the e2e fails at line 366-370. **Confirmed.**
- HTTP door today: `campaignLaunchProgressionGate.ts:194-218` iterates the session roster and reads `MAX(acked_sequence)` from `campaign_participant_cursor` (`:226-245`). That table is written only by the grant-channel ACK (`handleCampaignGrantAck.ts`, dispatched at `bindCampaignSyncConnection.ts:624-631`), whose only client is `CampaignReplicaSyncClient.ts` behind `pages/api/campaigns/[id]/replica-sync.ts`; the legacy socket numeric ACK never writes a cursor row. So for any session-bearing POST after revision 0 the legacy HTTP door already refuses (`acked === null -> 0 < requiredRevision`). But no production caller sends `sessionId`: `requestLaunchAuthority.ts:114` includes it only when supplied, and neither `CampaignDashboardPage.launch.ts`, `fastForwardCampaign.ts` nor `inProcessApiRouter.ts` contains the string `sessionId`. With `sessionId` undefined the gate returns `[]` (`:195`) and the head-only verdict is returned (`campaignLaunchAuthorityRoute.ts:272-291`). The e2e has no launch step (spec header line 12 says mission launch proof is "intentionally bounded"). **So removing MAX(acked_sequence) regresses only session-bearing POSTs, which today come from tests (`campaignLaunchAuthorityRoute.test.ts` seeds cursor rows at 237-253, 541, 794 per the preparation doc) and not from any shipped client.** The implementer's sentence "every session-bearing launch-authority POST returns 409" is true; "production regression" for HTTP is not observable today.

### Claim 3 - "inside P2CG1's leaves the socket door's in-transaction revalidation is impossible without A1/B/A2"

**TRUE for both real commit doors; FALSE for the launch-authority preflight.**

- `CampaignLaunchView.revalidate` (`campaignPublicAppliedView.ts:525-552`) refuses `context-mismatch` unless `db === this.db`, `this.ports.currentDb() === db` and `db.inTransaction`. It must run synchronously inside the transaction that commits the guarded write.
- Socket commit: `applyHostIntentLocked` (`CampaignMatchHost.doors.ts:156-179`) -> `commitValidated` -> `host.commitEvents` -> `commitCampaignEventBatch` (`campaignHostBatchCommit.ts:378-418`) -> `appendCommandBatch` (`JournalCampaignEventStore.ts:434-466`) -> `appendCampaignCommandBatch` -> `journal.appendWithExtension` (`SQLiteEventJournalWriter.ts:60-82`), whose only in-transaction hook is the after-append `rewriteRecordAfterCommand` (`JournalCampaignEventStore.ts:430-432`: "Called inside the append's transaction, after the batch rows are written"). Neither `CampaignSyncSession`, `CampaignProgressionGate`, the readers, the API gate, the route nor the transport is on that path. A `revalidate` from the session would have to open its own throwaway `db.transaction`, which proves nothing about the later append. The implementer's "sham" characterisation is correct.
- One thing the census under-states: the writer already has the synchronous pre-append seam A1 needs. `appendPreparedWithExtension` (`SQLiteEventJournalWriter.ts:85-137`) runs a synchronous `prepare(db)` inside the immediate transaction and short-circuits on `{kind: 'refused'}`; it is already used by `campaignAcceptContractCommand.ts:457` and `campaignRecordJournalSave.ts:86`. A1 therefore reduces to threading an optional synchronous guard from the locked doors through `ICampaignEventStore`/`JournalCampaignEventStore` into that seam and mapping the refusal into `CampaignCommitOutcome`; the writer leaf may not need to change at all.
- Mission-create commit: `createCoopMissionMatch` (`coopMissionCreate.ts:49-130`) runs `entry.host.runBatchExclusive` and writes the match row through `getDefaultMatchStore()`; it performs **no** progression check today (no `evaluate`, `Converged` or `progression` symbol in the file) and the only route caller is `pages/api/multiplayer/matches/index.ts:313-315`. The real HTTP commit door is therefore B, and it is not a P2CG1 leaf.
- Launch-authority preflight: `campaignLaunchAuthorityRoute.ts:244-247` already wraps every read in `getSQLiteService().getDatabase().transaction(() => {...})()`. `prepare` is async (it awaits `materializeBranchPath`), so the handler must become async and prepare before entering that transaction, then `revalidate` inside it. That is feasible inside the route and API-gate leaves. It is a preflight, not a commit, which is exactly what the accepted decision says cannot satisfy readiness on its own.

### Claim 4 - the proposed order and ruling

**Sound in shape, with three corrections and one placement change.** Evaluated against production safety at every intermediate main, privacy/authority/replay/idempotency/concurrency, plan conformance, and minimality.

1. **The activation predicate must be installed on `CampaignHostRegistry`, not handed to the binder or the session.** The implementer's ruling text says "the binder or session receives the port from server composition". The binder already has the dep; the session is constructed only by the registry (`CampaignHostRegistry.ts:294-297`), and the HTTP route lives in Next's API module graph, which cannot see a module-level install made in the tsx socket graph (the two-graph split is documented at `server.js:452-463` and `campaignProgressionReaders.durable.ts:398-405`). The one object all three doors already share across graphs is the registry singleton in the `Symbol.for('mekstation.multiplayer.campaignHostRegistry')` slot (`CampaignHostRegistry.ts:418-444`): the binder defaults to it (`:284`), the route reads it (`campaignLaunchAuthorityRoute.ts:158`), mission create uses it (`coopMissionCreate.ts:55`). So the predicate is: **a typed `ICampaignApplicationReceiptPort` installed once on the registry at server boot inside `loadMultiplayerRuntime` (`server.js:446-481`), before the server listens.** The binder composes `application` from `applicationReceipts ?? registry.applicationReceipts`; each entry exposes a graph-local `launch: CampaignLaunchView | null` built only when the port is installed; the HTTP doors test the installed port for presence and build their own graph-bound view through `createDurableCampaignLaunchView()` (`campaignProgressionReaders.durable.ts:92-100`; a foreign-graph handle must never be adopted, `:85-88`). This is the "concrete installed composition condition ... through existing server/session public ports" the preparation doc demands, it is not a flag (it is the port the binder needs anyway, typed, set once, no uninstall outside `_resetCampaignHostRegistry`), and it closes the C1 gap by construction: the same install that makes the binder offer views makes every door read rows. There is no interval in which receipts flow and a door still reads legacy credit.
2. **C must land before K, not after.** Binding `expectedCampaignId` at the creators is not inert on today's server: the transport omits `lastSeq` from the join when bound (`campaignSyncTransport.ts:390`), and the legacy binder uses `lastSeq` to choose tail resync over a full re-join (`bindCampaignSyncConnection.ts:1223-1262`); the guest surface quotes `lastSeq: useCampaignMirrorStore.getState().lastSequence` (`CampaignCoopRouteSurfaceConnected.tsx:294-299`). A bound guest reconnecting in-page would get a fresh baseline, which the legacy mirror path adopts at 0 (`:330-354`, `applySnapshot(event, event.sequence < 0 ? 0 : undefined)`) against a held cursor. The P2CF2 review's N5 only showed that numeric ACKs still fire on a bound transport; it did not cover the join frame. Fix in the transport leaf (C): keep quoting `lastSeq` on a bound join. The server ignores it in receipt mode anyway (`:1223` `&& !application`), so the "client-claimed cursor never selects the cut" property is server-enforced and unchanged. Then K is byte-identical on the wire against the legacy binder, and K's test must say so.
3. **Legacy deletion fits neither C nor S; it is its own unit after S.** With deletion in C, main between C and S has no credit (claim 1). With deletion in S, S needs `server.js`, the port factory and its test, the N4 backfill, plus the session, API gate, transport and binder and their four tests: 13 code/test leaves plus 5 lifecycle, over 15. After S every connection is in receipt mode (the server composes `application` whenever `membership` is present, which production always supplies), the transport latches `receiptMode` on the first `appliedView` frame and stops generating numeric ACKs (`campaignSyncTransport.ts:400, 454`), and the binder refuses numeric ACKs on a receipt connection (`:719-727`). The legacy credit is unreachable from S onward, so deleting it afterwards is pure deletion with no behaviour change. That is the correct reading of "Remove MAX(acked_sequence) and public-memory ACK readiness credit": removal at activation, as the plan's "At activation" list says.
4. **Placement change: the socket switch is A2's, not C's.** A2 precedes C and owns the binder, registry, gate and readers; C owns the session. A guard inside the append needs a prepared P2CB preparation from something A2 can reach, which is the entry (`entry.launch`), not a session method that does not exist yet. So the three AdvanceDay paths move to `entry.launch ? prepare + guarded commit : legacy session gate` in A2, and `evaluateScenarioLaunch`'s legacy convergence branch is simply left in place until S2 deletes it. The preparation doc allows exactly this: "If an A1/A2-owned file no longer changes in C, report the actual smaller delta". C then shrinks to the two HTTP doors plus the transport hardening.

Alternatives considered and rejected:

- **S before C with a compatibility shim.** The only shim that keeps the legacy doors honest once receipts flow is one that writes cursor rows or seeds the retained map from receipts. That is "numeric/cursor translation" (plan 2924) and "must not write/seed P2CA ... compare them to journal revisions" (preparation doc 210) verbatim, and it reproduces C1 blindness in the meantime (receipt-mode participants are never retained, `bindCampaignSyncConnection.ts:1138-1145`). Rejected on plan text.
- **One activation unit that flips `server.js`, the creators and deletes legacy together, everything else pre-landed dormant.** Counted: `server.js`, port factory + test, three creators + their three tests, session + API gate + transport + binder + four tests = 16 code/test leaves before lifecycle. Does not fit 15 even without the deletions (12 + 5 = 17). Splitting creators out is K; splitting deletion out is S2; what remains is S. So this alternative collapses into the recommended plan.
- **Amend P2CG1 in place** (the implementer's literal request). Rejected for three reasons: the 10-leaf restriction still cannot hold the socket switch, which must live in the binder; P2CG1's text would keep claiming the removal while the unit no longer performs it; and the packet's established procedure for "measured scope cannot fit" is supersession by narrower successors (`admissionRequires` of every P2C unit; precedents P2CE -> P2CE1/2/3 PR #2146, P2CF -> P2CF1/2 PR #2158), not text amendment of a planned unit.
- **Dual-evaluator doors gated on the installed port** (the implementer's core idea). Accepted, with the registry as the install point (correction 1).

## 3. Activation mechanics at each step

- **Before P2CG1H:** `getCampaignHostRegistry().applicationReceipts` is `null` in every process. Binder: `application = membership && (applicationReceipts ?? registry.applicationReceipts) ? new CampaignApplicationConnection(...) : null` -> null in production -> legacy frames, legacy numeric ACKs, `noteParticipantAcknowledged`. - **At P2CG1H (one merge):** `loadMultiplayerRuntime` installs the port on the registry before `app.prepare().then(...)` starts listening; the Next API graph sees the same registry through the `Symbol.for` slot. Binder composes `application` on every membership connection -> offers. Bound clients (P2CG1G) latch receipt mode on the first offer, apply through the P2CF2 consumer, ACK, and P2CA writes rows. `entry.launch` is built from the installed port per entry; the three AdvanceDay paths prepare the P2CB view, pass the A1 guard into the append, and translate a late refusal into `CAMPAIGN_NOT_CONVERGED`. - **Tests at every step** install the port explicitly on a reset registry (`_resetCampaignHostRegistry`, `CampaignHostRegistry.ts:450-454`) exactly as they pass `applicationReceipts` today; the binder dep stays for test composition. No test may set a boolean; the only switch is the typed port.

## 6. Risks

1. **P2CG1A fit.** Measured, not estimated, before registration; two slices if over 500. Waiver is available but shifts review cost into D and I.
2. **P2CG1H's journey proof can race.** At `e2e/coop-campaign-two-browser-journey.spec.ts:365` the host clicks AdvanceDay right after `expectGuestDashboardSynced`; with receipts the gate needs the guest's AND the GM's first receipt committed (P2CA row) before the click, and the spec has no retry on `CAMPAIGN_NOT_CONVERGED`. The spec is a P2CH leaf. Options: (a) P2CG1H is granted a narrow exception on the spec limited to strengthening the pre-click wait (poll on the guest's and host's confirmation signal), with P2CH keeping the scenario extensions; (b) the host surface's existing refusal posture is accepted and the spec is only run, in which case a red run blocks S until P2CH. **Recommend (a)**; it is one more file in S (9-10 of 15).
3. **Two-graph port identity.** The port installed by the tsx graph carries that graph's SQLite handle. Every door must use the port only as a predicate and build its own graph-bound `CampaignLaunchView` (`createDurableCampaignLaunchView` in the door's graph); the crossGraph test in P2CG1D must pin that a foreign-graph handle is refused `context-mismatch`, which `revalidate` already does (`campaignPublicAppliedView.ts:531-539`).
4. **Session-bearing launch-authority stays client-unreached.** No shipped client sends `sessionId`; activation makes the P2CB preflight correct but nothing exercises it until a client does (P2CH's "actual launch-authority POST" or a later client unit). Not a regression; a coverage gap to record in P2CG1E's text.
5. **`preparePublicCut` cost at S** (O(views x history) per commit, P2CE2 C3). Measured in S; if over budget the fix is a post-S tail-read unit, not a blocker to activation unless the journey times out.
6. **`CampaignSyncSession.retained` is also delivery bookkeeping** (`delivered` watermark, `noteDelivered`). P2CG1I deletes the `acknowledged` credit and the convergence compare, not the map; its test must keep the delivery assertions.
7. **Order is nine serial merges.** P2CG1F is file-disjoint from B/C/D and could run in parallel on its own worktree if the parent allows a second lane; everything else is serial by dependency.
