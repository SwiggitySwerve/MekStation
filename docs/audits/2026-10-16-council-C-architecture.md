# Council C: architecture and layering - what is load-bearing, and the order to add layers

Owner question (verbatim): "what should be our current path to get to something that builds and then we can add onto in layers".

Lens: technical architecture. Council A (`docs/audits/2026-10-16-council-A-product-path.md`) covered the owner artifact and product layers; Council B (`docs/audits/2026-10-16-council-B-process.md`) covered process cost and how to park the P2CG1 and TS7 tracks in the ledger. This report does not repeat those. It maps the code into layers, identifies what each layer actually depends on, decides where the dormant co-op receipt path sits, names the structural risks that will bite when layers are added, and gives a layer-by-layer entry/acceptance/exit plan.

**Verdict.** The runnable baseline (L0 rules + L1 single-player engine/UI + L2 persistence, wrapped by L5) is architecturally clean and does not depend on anything in the dormant receipt chain or on TS7. Lower layers essentially never import upper layers (3 hits across engine/gameplay/simulation/construction/validation). The dormant receipt path is **(b) required only for co-op campaign readiness**, and it is **(c) parkable at its current A2 state but not cheaply removable**: the live legacy binder imports its frame helpers from the new module (38 `send(` and 28 `errorFrame(` call sites), the receipt code is threaded through six live modules, and it has already shipped an applied SQLite migration. The things that will actually hurt when layers are added are not in the receipt chain: (1) the WebSocket runtime is a second module graph loaded by `tsx` whose load failure is swallowed at startup and which no PR CI job exercises; (2) the only CI lanes that run the co-op/campaign browser specs (nightly) abort at collection because of one module-scope throw, and CAMP-01 is red purely because the Windows runner's Git (2.56.0.windows.2) is not on a hard-coded allowlist; (3) a 1,676-line campaign binder is the hub every co-op change passes through; (4) layer boundaries are guarded only by "the build still bundles", with `fs`/`path` aliased to an empty module in browser builds; (5) the determinism audit covers only `src/utils/gameplay` and `src/simulation`. Each has a cheap guard (section 3). Fix the CI blind spots first: they are small, orthogonal to the TS7 paths, and they turn "add a layer" from an act of faith into a measured step.

### 1.2 What the baseline actually depends on

- **Production transpilers are not `tsc`.** Next uses SWC, the socket graph uses `tsx`/esbuild at runtime, root and desktop Jest use `@swc/jest` (`jest.config.js:22-28`; #2180). TypeScript is a type gate with two exceptions that reach runtime: (a) `tsconfig.json` is read by `tsx` in the production socket graph (shipped by the hydrate script, `:178`), so `paths`/`target` edits are runtime inputs; TS7S1B already changed `baseUrl`, `paths` and `target` (commit 07e61c704); (b) the desktop main process is emitted by `tsc` (`desktop/package.json:26`).
- **The socket runtime loads at startup, but its failure is non-fatal.** `server.js:524-540` calls `loadMultiplayerRuntime()` and `bootstrapMultiplayerServer()` inside a `try` whose `catch` only logs `[mp-boot] runtime load failed` and continues serving HTTP. A broken socket graph therefore passes every PR CI job that only renders pages.
- **Two SQLite connections to one file, by design.** `server.js:455-464` explains that the `tsx` graph has its own `SQLiteService` singleton and calls `initialize()` again; WAL makes the two connections safe. Both run on one Node thread with the synchronous `better-sqlite3` API, so transactions cannot interleave mid-statement; contention would surface as `SQLITE_BUSY` after the library's default busy timeout (no explicit `busy_timeout` in `src/services/persistence` or `DurableMatchStore.ts`; the 5 s default is from library documentation, **unverified here**). Only one test targets the cross-graph property: `src/lib/multiplayer/server/__tests__/campaignProgressionReaders.durable.crossGraph.test.ts`.

## 2. The critical path and the dormant receipt path

### 2.1 True critical path to a demonstrable baseline

L0 + L1 + L2 (+ the L5 wrapper). None of it imports from the receipt chain: the receipt modules' production importers are confined to the co-op route surface, the campaign binder and the durable readers (section 2.3). Council A showed main builds and REL-03 proved the loop on ba8007f2. Through the architecture lens, the only gaps on this path are _signals_, not features: (a) PR CI does not prove the socket runtime boots, and because the custom server always loads it at startup, a broken socket graph is a latent risk to every shipped build (L1 does not need it, but L5 ships it); (b) the nightly full browser suite, which would catch regressions outside the five specs PR CI runs, has been producing zero test results.

### 2.2 What L3 and L4 need from existing plumbing

- **L3 standalone skirmish** needs `bindMultiplayerSocketConnection.ts`, `MatchHostRegistry`, `ServerMatchHost*`, `DurableMatchStore` and the engine. Nothing from the campaign receipt path. Acceptance tooling exists: `npm run verify:qc:multiplayer-reliability` (`package.json:203-205`).

P2CG1H's own text makes the port's `database()` "the composing graph's `getSQLiteService().getDatabase()`", and P2CG1E handles "a foreign-graph handle": activation is fundamentally a two-graph wiring problem (risk 1).

## 3. Structural risks when adding layers, and the cheapest guard for each

1. **Two module graphs with a silent boot failure (L3, L4, L5; latent for all).** The Next API bundle and the `tsx` socket graph are separate module instances (`server.js:440-475`), each with its own SQLite connection and module-level state; registries survive only because they deliberately use `globalThis` slots. New process-wide state (a cache, a port slot, a pause signal) silently forks unless it follows that pattern, and P2CG1D/H must install a port that the _other_ graph's HTTP route can see. If the socket graph fails to load, `server.js:536-540` logs and keeps serving. **Cheapest guard:** add `npm run validate:multiplayer:packaged-socket` (existing, `package.json:72`) as a step in the Customizer Regressions job, which already builds and starts the standalone server (`pr-checks.yml:683-742`), and make the E2E readiness probe fail if `[mp-boot] runtime load failed` was logged. When a layer adds process state: one cross-graph test in the style of `campaignProgressionReaders.durable.crossGraph.test.ts`.

2. **The campaign binder is the single hub for co-op (L4).** `bindCampaignSyncConnection.ts` is 1,676 physical lines (larger than the ~1,300 in the brief): `handleInbound` at `:369`, grant join/ack, room-code join, heal passes, timeout outcome broadcast, and the dormant application handling; it shares helpers with the dormant module, and its lifecycle/broadcaster pair is keyed per entry (`:212-245`). Every co-op feature and every remaining P2CG1 unit edits it or its collaborators. **Cheapest guard:** before more co-op work, establish a green legacy baseline with the existing `npm run verify:qc:coop-campaign-journey` (`package.json:206`) and make it the acceptance for any change under `src/lib/multiplayer/server/*Campaign*`, `src/lib/campaign/coop/*` or `src/components/campaign/coop/*`. Continue the AST-proved A1/A2 move-only extraction pattern only while a co-op milestone is active.

3. **Browser CI is blind outside five specs (every layer above L1).** Nightly aborts at collection and CAMP-01 is red for a Git pin (section 2.4), so nobody gets a usable browser signal for campaign, co-op or multiplayer. **Cheapest guard:** (a) add the missing `/compendium/chassis` entry to `routeProofs` in `e2e/app-shell-route-proof.spec.ts` and move the manifest cross-checks from module scope into a `test()`, so a future mismatch fails one test instead of every lane; (b) add `2.56.0.windows.2` to `CAMP01_GIT_VERSIONS` with its test expectation. Both are QC/test-only files outside TS7's reserved paths.

4. **Layer boundaries are guarded only by "it still bundles" (L3/L4 especially).** Browser builds alias `fs`/`path` to an empty module (`next.config.ts:96-100`, `:169-174`), so an accidental Node import on a browser path compiles and fails at runtime; only native `better-sqlite3` breaks the build. `src/lib/campaign/` mixes server-only modules (`authority/*` with `getSQLiteService`) with browser modules; `src/engine` imports UI (`InteractiveSession.persistence.ts:1`); browser `coopRuntimeSession.ts` instantiates server authority classes. There is no import-boundary lint (the madge `analyze:dependencies` script, `package.json:79`, checks circularity and is not in CI). **Cheapest guard:** a ~30-line `scripts/qc/audit-layer-imports.mjs` (new) modelled on `audit-combat-determinism.mjs` (`git grep` + explicit allowlist), run beside the Determinism Audit job: forbid `@/components`/`@/stores` value imports from `src/engine`, `src/utils/gameplay`, `src/simulation`; forbid value imports of `better-sqlite3`, `@/services/persistence/SQLiteService` and `@/lib/multiplayer/server/*` from `src/components`, `src/stores`, `src/hooks`, non-API `src/pages` and the browser half of `src/lib/campaign`. Seed the allowlist with today's hits so it starts green and blocks only new leaks.
