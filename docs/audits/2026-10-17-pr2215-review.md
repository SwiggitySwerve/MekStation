## Claims verified

### V211-01a — interactive AI movement plans/validates on an occupied grid

`src/engine/InteractiveSession.ai.ts` `runInteractiveSessionMovementAI` now builds
`occupiedGrid = gridWithUnitOccupants(context.grid, session.currentState.units)` per AI unit, after
`emitRetreatIfNeeded` and after re-reading the session, and passes it to all three consumers:
`botPlayer.playMovementPhase`, `validateMovement`, and `buildMovementEventPath`.

- "Rebuilt per AI unit incl. moves declared/locked this turn" — CONFIRMED. `declareMovement` appends a
  `MovementDeclared` event and `appendEvent` re-derives `currentState`; `applyMovementDeclared`
  (`src/utils/gameplay/gameState/actionLocking.ts:71`) sets `position: payload.to` immediately, so the
  next AI unit's `gridWithUnitOccupants` call sees the declared destination, not the origin.
- Same helper as the player commit path (`InteractiveSession.actions.movement.ts:79`) and the UI
  reachability projection (`GameSessionPage.movement.helpers.ts:95`). The AI is now exactly as strict as
  the player path — no stricter.
- Own-hex handling is safe everywhere the grid is consumed: `getValidMoveCandidates` skips the
  occupancy check at distance 0; `findPath` never re-enters the start (closed set) and allows an
  occupied `end` only when a caller asks for it; `AITerrainPathfinder` settles the origin first;
  `validateMovement` compares `occupantId !== position.unitId` for the start hex.
- Stale occupant markers: `gridWithUnitOccupants` clears every `occupantId` before placing live units,
  so the comment "static context grid only carries terrain" is harmless even if false.

### V211-01b — weapon panel blocks all weapons at range 0 with the engine's reason

`deriveWeaponLegalityForTarget` maps every option to `available: false, blockedReason:
SAME_HEX_ATTACK_DETAILS` when `hexDistance === 0`. The string matches the engine verbatim
(`InteractiveSession.actions.attack.ts:99-100`: `'SameHex'`, `'Attacker and target occupy the same hex'`),
and the engine applies that rejection before the per-weapon loop, so blocking _all_ weapons is the correct
mirror.

- Physical attacks are unaffected — CONFIRMED. `deriveWeaponLegalityForTarget` has exactly two product
  callers (`AttackIntentComposer.model.ts`, `GameplayLayout.tsx` attack-infeasible reasons), both in the
  weapon-attack composer. Physical attacks use the `PhysicalAttack` phase and their own validators
  (`TargetNotSameHex` etc.); BA leg/vibro-claw/swarm attacks use dedicated dispatchers
  (`InteractiveSession.actions.battleArmor.ts`, `declareVibroClawAttack`). None route through the mutated
  function.
- Legit range-0 weapon attacks: none exist in this engine today; the engine already rejects every
  ranged attack at range 0 regardless of unit type. If infantry same-hex fire is added later it must be
  added engine-side first, and this UI gate should then be relaxed in lockstep.

## Stacking rule assessment

The movement-system spec names an "occupancy/stacking gate" but defines no friendly-vs-enemy or
Mek-vs-infantry exceptions; the engine's hex model is a single `occupantId` and `validateMovement`
rejects any occupied destination (`'Destination hex is occupied'`). Blocking every occupied hex is
therefore the correct behaviour _for this engine_ and identical to what the player is allowed. It is
stricter than tabletop (which permits limited friendly stacking and infantry entering enemy hexes), but
that gap is engine-level and pre-existing; because the AI now uses the same validator and the same
occupancy helper, any future relaxation is inherited automatically.
