## 2. M1 rationale (pre-state vs post-state)

- The live replay (`getReplayEventsForPlayer`) folds `deriveState(gameId, prefix)` with the current event **included**, i.e. post-state; the PR does the same. So M1 surviving is a test-coverage question, not a parity question.
- The implementer's claim "no filtered event can change its own visibility today since movement declarations skip the filter" is **approximately, not literally, true.** `applyEvent` writes a unit `position` in exactly two non-`GameCreated` places: `applyMovementDeclared` (sealed, skips the filter) and `PhysicalAttackResolved` (`applyPhysicalDisplacements` for push/charge/DFA and `applyGrappleResolution`, which moves the attacker onto the target's hex). `PhysicalAttackResolved` is `target-visible` and does go through `filterEventForPlayer`, where visibility of the actor/target depends on `hexDistance <= sensorRange && LOS`. A 1-hex displacement cannot cross a normal sensor range, but it can cross a `sensorRangeBrackets` `'none'`/0 range or an LOS-blocking hex edge, so there is an engine-reachable case where pre and post differ. Since post-state is what live uses, the fix is a test, not code: a direct `fogMatchHistoryProjection` unit case with a synthetic `PhysicalAttackResolved` carrying a `displacements` entry that moves a unit across a 0-range sensor boundary (or any `target-visible` event with a stubbed `canSeeUnit`), asserting the post-state decision. Non-blocking.
