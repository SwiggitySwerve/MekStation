## 3. Review classes

### Authority

- **Binding.** The view is constructed per socket in `bindCampaignSyncConnection` from the server-verified `verifiedPlayerId`, the registry `entry` (campaign) and `matchId` (session); `preparePublicCut` looks the seat up for that principal only (`activeCampaignSessionMembership(campaignId, sessionId, participantId)`) and the authority triple (`branchId`, `effectiveGeneration`, `viewerAuthorityFingerprint` over seat, `boundAt`, viewer identity) is captured on the first cut and compared on every later one; drift ends the view with `campaign-application-replaced`. Lineage is the `appliedView` chain (`viewId`, fresh `receiptId`, `previousReceiptId` = the latest established receipt).
- **Seat before cut.** GM: `membership.bind(gm)` precedes `application.open()`; `gm-seat-taken` returns before any hydration. Returning member: `isActive` gate precedes `hydrateApplication`. Room-code newcomer (both the grant-adapter path and the no-adapter fallback): room code is verified and `bind(player)` claims the seat before `publicHydration` / `hydrateApplication`; `tactical-seats-full` refuses first. `isRevoked` is checked at the top of every join.
- **Rejoin mints a new view id.** `open()` always calls `invalidate()` then `randomUUID()`; pinned by the test (`views.has(rebaseline.viewId)` false) and by my S2a/S2b.
- **Removal / revocation / authority change end the view.** `cut === null` (no active seat), `cut.removed` (a committed `ParticipantRemoved` anywhere in the verified history), post-write `isRevoked`, and the authority triple comparison all route to `fail` -> `closeWithTypedError` (1008). Pinned by the committed-removal, authority-change and unsettled-revocation tests.
- **No client-resolved actions.** The `lastSeq` resync arm is skipped in receipt mode (`envelope.lastSeq !== undefined && !application`), so a client-claimed cursor never selects the cut; pinned by "newcomer quoting lastSeq ... still gets the public bundle". No new inbound frame kind is parsed in this slice.

### Privacy

- **Same cut, one transaction.** `db.transaction(() => ({ head, generation, path, membership }))()` on `receipts.database()`; the path is materialized outside SQL by `materializeBranchPath` and `reached` (last stored digest, or the first segment's base digest for an empty path) must equal `captured.head.digest`, otherwise `campaign-application-history-integrity` throws into the chain and the connection closes `campaign-application-unavailable` with nothing sent (pinned by the digest-mismatch test, which also asserts the secret never leaves). See note N3 on the seat read's connection.
- **Projection.** `projectCampaignForViewer(campaignId, events, campaignScopeAdmits(scope, {participantId, isGm}))`; `isGm` comes from the durable seat, not the registry. The snapshot payload is `cut.state` (the fold of the visible set only) and carries no journal position (`payload` has no `revision`, asserted). `hydrationFacts` = `selectCampaignMissionLaunches(visible, Infinity, admits)`, launch facts only, already bounded by the cut.
- **Hidden events produce no frame and no offer.** Deltas iterate `cut.visible` only, so a `gm`-scoped event never becomes a frame; the watermark only advances on sent frames. Pinned by "withholds hidden progress" and by my S5 (a hidden-only commit writes zero bytes to the guest and the next visible delta links straight to the baseline).
- **Grant replica stays internal.** In receipt mode `handleRoomCodeGuestJoin` still runs `hydrateFirstJoin` (grant-scoped snapshot into the replica) and `attachRoomCodeGuestLiveSession` (replica catch-up), but `sendGuestSnapshot`, `sendReplicaSnapshot`, `releaseSnapshot` and the legacy launch replay are never reached; the test asserts `sent` is empty and the replica cursor exists at hydration time. The grant channel has not carried client frames since delivery unification, so nothing else can leak through it.
- **Sequence gaps.** Delta frames carry the event's own campaign `sequence`, exactly as the legacy member arm does; a restricted viewer can infer that something was withheld from a gap, as before. Not new to this slice and not a receipt leak. No new log line prints frame content.

### Replay

- **Deltas.** After the baseline (`cut` = head revision), each refresh re-reads the verified journal and sends every visible event with `streamRevision > latest.cut`, in path order, each linked to the receipt of the frame established just before it (`view.latest` is updated inside `publish`, so the loop links correctly within one refresh). Checkpoints (`CampaignSnapshotPublished` that `campaignBaselineReachesViewer` admits) ride the `CampaignSnapshot` kind via `campaignEventWireFrame` with `sequence >= 0` and a non-null `previousReceiptId`, which `CampaignSnapshotMessageSchema` accepts (my S6).
- **Nothing durable.** `latest` lives on the in-memory view; no map keyed by socket survives the view, no timer, no queue beyond the per-view promise chain, no `setInterval`/`setTimeout` in the diff.
- **P2CE1 note 1 honored.** The sole `sendConfirmed` caller is `publish` and its argument is typed `ICampaignApplicationOffer` (`CampaignSnapshot | CampaignEvent` with `appliedView`), so a sequenced match `Event` cannot reach it and `deliveredSeq` semantics are untouched.

### Idempotency

- An offer is **established only** when `sendConfirmed` returns `sent` and the post-write `isRevoked` check passes; `failed`, `backpressure`, `not-open` and `cancelled` all leave `latest` unchanged and (when the view is still current) close 1008 `campaign-application-send-failed`. Pinned by the `it.each(['failed','backpressured','closing'])` test (a failed write hands the frame over but establishes nothing; refused writes hand nothing over) and by my S4 (backpressure on the first delta after an established baseline).
- A superseded view's `fail` is a no-op (`current(view)` false), so a rejoin never closes the socket it just replaced.

### Concurrency

- **Serialized per view.** `enqueue` chains every step on `view.chain`; `wake` coalesces commits with `refreshQueued`; the subscription is taken **before** the first cut is prepared, so a commit landing between the read transaction and the write is picked up by the queued refresh (pinned by "a commit meanwhile follows it, linked to it" and my S1 for the delta-held case: 'b' is sent exactly once, after 'a' settles, linked to 'a').
- **Abort is the release.** `invalidate()` aborts the signal; the `abort` listener unsubscribes from the host (pinned by the subscription-count test); `sendConfirmed` receives the same signal, so a rejoin cancels an unsettled write instead of waiting on it.
- **Healthy recipients unaffected.** Each socket has its own view and chain; a bad socket's failure closes only that socket. Pinned by the `it.each` test's GM delta assertion and my S4.
- **Errors.** `enqueue`'s `catch` logs and fails the view, so the chain never rejects unhandled. The only path that could throw inside the `catch` is `deps.close` itself (`socket.close` on a dead handle); `ws` tolerates that, and the mock does too.

## 7. Findings

### N1. [NOTE] A committed removal that lands while a write is unsettled is caught one chain step after the write, not at the write (S3)

`publish` establishes on `sent` and then checks `membership.isRevoked`. Durable revocation for a committed `ParticipantRemoved` is applied by `applyCommittedParticipantRemovals` (binder line ~983) after the host returns, i.e. after the host has already fanned the event out and `wake` has queued the next refresh. So in S3 the baseline is established, `open()` returns true, `hydrateApplication` runs `addSocketToMatch` + `acknowledge()`, and the queued refresh then closes the view with `membership-revoked`. No offer or campaign frame reaches the removed participant (my assertion), and the window is a few microtasks on one chain. The only thing that could reach them in that window is the legacy `broadcast(matchId, ...)` fan-out of `CampaignDecision`/timeout frames, because the socket was momentarily in `socketsByMatch`. This is consistent with the contract clause "removal ... also end[s] the view" and is not a leak of the public bundle. **Carry to P2CE3:** the ACK/commit path must not rely on `isRevoked` alone; it must re-prepare the cut (the preserved patch's `commit` does: it calls `prepare()` and P2CA's context carries `participantRemoved`). Suggested wording: _"P2CE3 ACK admission MUST re-prepare the verified cut (head, generation, path, seat, committed removal) before P2CA `accept`, and MUST refuse an ACK naming a `viewId` other than the live view's."_

### N2. [NOTE] GM double-join sends a spurious `campaign-session-unavailable` Error frame (S2b)

The host arm maps `application.open()` returning false onto the legacy `joinMember` failure. `open()` also returns false when a later join superseded the view, so a GM that sends two `CampaignJoin` frames quickly receives one misleading Error frame on a socket whose second view is live and continues correctly. Guest arms are clean because `hydrateApplication` returns silently. Root cause is pre-existing: `socket.on('message', () => void handleInbound(...))` does not serialize joins per socket. Harmless to authority and privacy; the client should ignore it. A one-line fix in P2CE3 (return without the Error when `application` is set, since `fail` has already closed on a real failure) fits P2CE3's binder leaf; not required here.

### N3. [NOTE] Same-cut atomicity rests on the seat read sharing the transaction's connection

See C2. Wording for Task 14 given there.

### N4. [NOTE] Receipt mode requires an effective-head branch backfill

`readEffectiveStreamHead` returns a genesis placeholder for an un-backfilled stream, but the very next line `branches.requireEffectiveHead(stream)` throws, so a campaign without `event_history_branches` rows closes every receipt-mode join with `campaign-application-unavailable`. The legacy path has no such requirement. Correct fail-closed behavior for a verified cut, and disclosed by the author ("requireEffectiveHead throw on ... missing branch"). **Carry to Task 14:** _"Every campaign served in receipt mode MUST have its effective-head branch backfilled before `applicationReceipts` is composed; otherwise joins fail closed."_

### N5. [NOTE] `removed` is computed over the whole verified history

`cut.removed` is true if any `ParticipantRemoved` for this participant exists on the path, regardless of order. Today that is exactly right: `bind` refuses a revoked row (`{ kind: 'revoked' }`) and no readmission path exists, so a removed participant can never hold an active seat again. If a readmission flow is ever added, this must become "removed after the current seat's `boundAt`". Record it with that flow, not here.

### N6. [INFO] Written-but-cancelled frames can reach the client on a rapid rejoin

P2CE1's abort-then-late-callback path settles `cancelled`, but the bytes may already be on the wire, so a client that rejoins fast can see two baselines with different `viewId`s (S2a/S2b show exactly that). The server holds only the second. P2CE3's ACK admission must refuse the first view's receipt (the preserved patch's `acknowledge` only names `latest`/`inFlight` of the live view, so it will).
