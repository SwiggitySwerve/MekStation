## 2. Fold owner (`campaignAuthoritativeFold.ts`)

Read in full at head. Verified against the P2CF1 behaviour text:

- `foldCampaignHydration(fold, snapshot, hydrationFacts, replacement=false, resumeSequence?)` filters the bundle through `isLaunchFact` (type, `campaignId === snapshot.campaignId`, non-negative integer sequence, strict `CAMPAIGN_BASELINE_SCHEMA_PACK` v1 `CampaignMissionLaunched` payload parse via `schemas[0].parse`) plus strict ascending order, and refuses when `!hydrationFacts` or any element was filtered out (`facts.length !== hydrationFacts.length`) or any held fact is absent byte-for-byte from the new bundle. The client check is stricter than the wire `superRefine` in Protocol.ts 1007-1030 (which checks type, campaign and order but not payload shape); the strict parse also acts as a privacy guard, since a fact carrying an extra field is refused rather than held.
- Explicit `[]` is accepted as a complete set (test "accepts an explicit empty bundle"); `[]` is truthy, so `foldCampaignSnapshot` and `foldCampaignEvent` carry it (`fold.launchFacts ? {...} : next`) rather than dropping it.
- Replacement starts from `EMPTY_CAMPAIGN_AUTHORITATIVE_FOLD` (held lineage, cursor and facts discarded); the test "starts an authorized replacement from EMPTY" shows a reconnect at cursor 0 refused without `replacement` and installed with it. Non-replacement keeps the P2CD ordering guard (`adopted < fold.lastSequence` -> null), so "reconnect cannot adopt at 0 against stale held proof" holds at the owner level.
- Historic facts are kept as given: never passed to `applyCampaignEvent`, never move `lastSequence` (fold.lastSequence stays -1 after hydration with facts at 3 and 7). Live launches are appended by `foldCampaignEvent` only on a fact-holding fold, and refused when malformed, foreign (`fold.state?.campaignId`) or already held by sequence. Legacy folds (no bundle) keep the exact `{ state, lastSequence }` shape and the old launch handling (tests pin `Object.keys`).
- Privacy: the fold holds only what the server's viewer-scoped cut sends (`preparePublicCut` -> `selectCampaignMissionLaunches(visible, Infinity, admits)` at bindCampaignSyncConnection.ts 1684; `visible` is the viewer projection). No grant replica, no hidden field can be introduced client-side, and the strict parse rejects unexpected keys.

Observations (minors below): the held-fact equality is `JSON.stringify` byte equality, so a semantically identical fact with a different payload key order is refused (probe F1); the fold does not check the snapshot's `campaignId` on a non-replacement adoption (probe F3; pre-existing P2CD behaviour, guarded by the mirror store and by `registerOffer`'s `frame.event.campaignId !== options.expectedCampaignId` check).

Does a later confirmation confirm an earlier ACK? Only one ACK is ever outstanding (`sent`), so the flag has nothing earlier to confirm; a confirmation naming an earlier receipt is dropped and cannot flip `confirmed` for the newer ACK. Out-of-order or duplicate confirmations cannot corrupt the flag: it is set only on an exact `appliedView` match with `sent`, and reset only when `drain` sends a new ACK.

### M1 (major, contract-level): an ACK of a superseded offer is refused as `unknown-receipt`, and P2CF1 ends the view on it

Server half (code at head, plus a registered test): `acknowledge` (bindCampaignSyncConnection.ts 1768-1781) admits an ACK only if it names `view.inFlight` or `view.latest`; `publish` (1900-1917) writes the next candidate, runs `processAck` once while the previous offer is still `latest`, then sets `view.latest = candidate` (1914). After that, an ACK of the previous offer is `campaign-application-unknown-receipt`. `coopMissionAnnouncement.reconnect.test.ts` 1300-1312 asserts exactly this on one connection: after `[baseline, delta] = offers(guest)`, ACKing `baseline.appliedView` is refused `unknown-receipt`.

Client half (P2CF1): the transport sends the ACK for offer X as soon as X is applied and no newer offer has been registered (`drain`). If the server establishes Y while that ACK is in flight, the server refuses it; the refusal arrives after Y (same socket, in order), and `handleApplicationRefusal` calls `recover('application-refused')`: the view is torn down even though Y is registered and would have been ACKed cumulatively moments later (probe P2, 13/13 passing). The head-drift re-send (probe P1) is the same race one step later: the re-sent ACK for X is refused `unknown-receipt` whenever the drift was caused by a visible event that `refresh` publishes right after the refusal, which is the common cause of head drift.

When it bites: offers X and Y published with a gap between the client's application time for X and that time plus one round trip (back-to-back offers are already covered, because the transport only ACKs `latest` once the whole prefix is applied; offers seconds apart are covered because X's ACK lands first). Two participants acting within ~100 ms of each other, or a server-side reaction following a command, fall in the window. Each hit costs a full rejoin (close, fresh baseline + bundle, new view).

Why not a blocker: it is the registered P2CF1 behaviour ("unknown-receipt ... end the view as recovery-required") and the P2CE3 Task 13 wording (item 3, optional item 5); no false applied proof is possible; nothing in production can reach it until Task 14 composes `applicationReceipts` and binds `expectedCampaignId`. My own P2CE3 optional item 5 ("never a server-side timing race") was too strong: it holds for ACKs the client sends after receiving Y, not for an ACK already in flight when Y is established. I correct it here.

Resolution options, owner's call, to be closed before Task 14 activation:

- (a) Client rule in the transport leaf (this PR or P2CF2's transport touch, three lines + one test): _"On `campaign-application-unknown-receipt`, if a newer offer has been registered since the refused ACK was sent (`latest !== sent`), the refusal concerns a superseded ACK: ignore it and let `drain` ACK the latest offer; otherwise end the view as recovery-required. Never re-send on unknown-receipt."_ This keeps "never retried with the same frame" and "rejoin when the refusal concerns the current ACK"; it requires a one-sentence amendment of the P2CF1 behaviour text at closure.
- (b) Server rule in Task 14 (binder leaf): _"Admit an ACK naming any receipt of the live view's established chain; for a receipt older than `latest` return `stale` and send nothing (cumulative commit already covers it). Reserve `unknown-receipt` for receipts the view never issued."_ Or: _"Typed refusal frames carry the refused `appliedView` so the client can discard refusals of superseded ACKs."_
- Either way, P2CF2's consumer must treat every `onError` recovery-required as an automatic, idempotent rejoin (CF2), so the cost of M1 is bounded until it is fixed.

## 7. Judgement on the fail-closed generalisation

The server's full INVALID_INTENT `campaign-application-*` set at head is eleven reasons: binder `not-offered`, `receipt-required`, `head-drift`; P2CA `accept` (`campaignPublicAppliedView.ts` 113-124) `invalid-offer`, `unknown-receipt`, `offer-binding`, `not-admitted`, `current-authority`, `receipt-conflict`, `baseline-required`, `replacement-required`. The contract names four non-retry reasons plus head-drift. Ending the view on the other six is the right reading of "never retried with the same frame ... so the consumer rejoins": every one of them means the view or its authority is not what the client thinks, retrying the same frame could only repeat the refusal, and for `not-admitted` the server follows with `AUTH_REJECTED`/close anyway. No contract clause is violated; the behaviour text should say "every other `campaign-application-*` INVALID_INTENT refusal" at closure (documentary, N1). Subject to M1, which is about the one reason (`unknown-receipt`) that the protocol can produce for a well-behaved client.

## 8. Findings

Blockers: none.

Majors:

- **M1. Superseded-ACK refusal tears down a live view** (section 4). Contract-level, inherited from P2CE3's admission rule plus the Task 13/P2CF1 refusal wording; P2CF1 is conformant. Owner decision required: option (a) in this PR or P2CF2, or option (b) in Task 14; in all cases before `applicationReceipts` is composed. Recorded as a hard Task 14 precondition in CF7.

Minors:

- **m1. No client-side bound on head-drift re-sends** (P8). Each cycle is gated by a server refusal after three commit attempts, so it is not a tight loop, and a visible new offer ends it; but a hidden-only tail under sustained churn re-sends indefinitely. Decide a bound or rely on the Task 14 "bound its wait and rejoin" wording (P2CE3 Task14 item 4).
- **m2. Untested branch: `socket.send` throwing inside the re-send** -> `recover('send-failed')` (author concern 4; probe P5 confirms the behaviour). Worth one registered case the next time the transport leaf is open.
- **m3. Re-send has no `socket.readyState !== 1` guard**, unlike `drain`. On a CLOSING socket browsers discard silently; `onclose` then marks the transport closed, so no incorrect state results. Cosmetic consistency.
- **m4. Held-fact equality is byte equality** (`JSON.stringify`), so a re-sent fact with a different payload key order is refused on a non-replacement bundle (F1). Fail-closed and only reachable on a non-replacement rebaseline, which `registerOffer` does not admit on a live connection; a reconnect uses `replacement`. Record in CF3 so P2CF2 never relies on the non-replacement path for a new view.
- **m5. The fold does not check the snapshot's `campaignId` on non-replacement adoption** (F3; pre-existing P2CD). Guarded by the mirror store and by `registerOffer` (`prefix-conflict` on a foreign `event.campaignId`); the host fold path in the component relies on the transport. No change needed in P2CF1; note for P2CF2's consumer gate (`transport.campaignId === campaignId`).
- **m6. A confirmation of `sent` is dropped when a newer offer is already registered** (P3; pre-existing P2CD filter, now also leaves `confirmed` false). Harmless for the re-send rule (the same condition blocks the re-send), but the consumer never hears that confirmation and must rely on cumulative semantics (CF4).

Notes:

- **N1.** Amend the P2CF1 behaviour text at closure to the eleven-reason wording in section 7 and to mention `foldCampaignHydration`'s signature `(fold, snapshot, hydrationFacts, replacement?, resumeSequence?)` and the mirror's fourth positional argument.
- **N2.** `report.md` concern 2 says "a duplicate ACK is harmless". True for a duplicate of the latest ACK (`stale`, no frame); not true for a duplicate of a superseded ACK (M1). The author's concern 5 (lost refusal, Task 14) is correctly deferred.
- **N3.** The mirror state now always has a `launchFacts` key (value `undefined` for legacy mirrors). The fold return shape is pinned by `Object.keys`; the store state shape is not. Zero impact on callers; mention in CF5 so P2CF2 does not persist the key.
- **N4.** INTERNAL_ERROR `campaign-application-*` frames are not treated as refusals; the server closes right after. P2CF2 must handle `onclose` as a rejoin signal as well (CF2).
- **N5.** Transport `max-lines` warning is pre-existing (636 physical at base, 669 at head). P2CF2 should not touch the transport; if Task 14 does, register an extraction as P2CE2 did for the binder.
