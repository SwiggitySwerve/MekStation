## B1 (fog leak of `criticalSlotManifest`) - CLOSED

What changed (`src/lib/multiplayer/server/fogOfWar.ts:123-150`):

- The `GameCreated` branch now triggers when any unit carries `customUnitDefinition` OR `criticalSlotManifest`, and strips both fields from every unit the viewer does not own. Owned units are returned by reference, unchanged. Input event is not mutated (existing test asserts `JSON.stringify(event)` unchanged).
- `filterEventForSpectator` is unchanged and still routes through `filterEventForPlayer` with the `__spectator__` sentinel, so spectators/unknown viewers get no manifest for any unit.

All paths that deliver `GameCreated` or unit state to a client were enumerated; the match wire has no state-snapshot message kind (server->client kinds are `Event`, `ReplayStart/Chunk/End`, `Heartbeat`, `Error`, `Close`, `LobbyUpdated`, plus campaign kinds), so events are the only transport for unit state:

1. Live broadcast - `ServerMatchHostEvents.ts:316-320` -> `filterEventForSpectator` / `filterEventForPlayer`. Covered.
2. Reconnect / resync replay (`sendReplay`, `handleSessionJoin`) - `ServerMatchHostReplay.ts:getReplayEventsForPlayer` re-derives state per event and calls the same two functions when `meta.config.fogOfWar` is set. Covered.
3. Authority shadow digest - `journalAuthorityShadow.ts:222` calls `filterEventForPlayer` (comparison only, not delivery). Consistent.
4. HTTP history routes (`/api/matches/:id/export`, `/timeline`, `/head`) - see N6: this chain never calls `filterEventForPlayer` (pre-existing, not introduced by this PR).

Proof at head (throwaway probe, deleted): a real `ServerMatchHost` with two custom-adapted Atlases, `fogOfWar: true`, owner/opponent/spectator sockets. The stored authoritative `GameCreated` carries manifests for both units (precondition asserted, so the test discriminates). Live `broadcastEvent`, `sendReplay(socket, 0, viewer)`, and `handleSessionJoin` each delivered the manifest only for the viewer's own unit (`['instance-0']` / `['instance-1']` / `[]`), and the store copy was left intact. A second probe with two canonical units (manifest present, no `customUnitDefinition` anywhere) confirmed the "any unit has a crit layout" trigger: each side keeps its own manifest and loses the other's, spectator gets none, fog-off returns the identical event reference, unit order/ids preserved.

Client handling of a missing manifest for hidden units: the only readers of `criticalSlotManifest` in product code are `gameState/initialization.ts:198` (copies if defined), `gameState/damageResolution.ts:51-72` (`markCriticalSlotManifestEntryDestroyed` returns `undefined` through for `!manifest`, and tolerates a missing location), and `gameSessionAttackResolution.damageEvents.ts:172` (server-side resolution; falls back to the default manifest - never runs on a mirroring client). No component, page, store, or hook reads `criticalSlotManifest` (grep over `src/components`, `src/pages`, `src/pages-modules`, `src/stores`, `src/hooks`: zero hits), so the record sheet / damage / crit UI cannot crash on, or present defaults as "real" from, the stripped field; crit UI continues to render from `componentDamage` and the public `CriticalHitResolved` payload. The PR's new test (`replays a fogged log with no enemy manifest without errors`) and the pre-existing replay-gate strictness (field is `.optional()` in `gameUnitSchema`) cover the reducer path. No client<->server state-digest comparison exists that the per-audience divergence could trip (`expectedPostStateDigest` is server-local).
