## Finding and limits

**Confirmed privacy exposure, but “both sides' state” needs qualification.** In a fog-on match, seated players and spectators receive both sides' initial unit records in `GameCreated`, including an enemy the server considers invisible. The normal reducer reconstructs its deployment location from that payload. An authenticated seated player can also retrieve unprojected match metadata, including both sides' bootstrap entries, over HTTP. These are server-delivered bytes, so hiding tokens in the UI cannot fix the exposure.

**Not confirmed:** a periodic WebSocket snapshot containing the entire current `IGameState`, or wholesale delivery of every hidden event. The combat protocol is event/replay based; ordinary invisible `MovementLocked` events were withheld in both live and replay controls. Private construction snapshots/manifests receive specific filtering. There is no combat `StateDigest`/full-state snapshot message in the server-message union. Do not describe this as “no fog filtering exists.”

There is also a distinct, reproduced spectator sealed-choice defect already assigned to **B10 / P2CG1S**. It must not be confused with B14 or used to claim B14 is already covered.

Evidence levels: the five Jest checks below exercised real host/filter/serialization code with an in-memory match store and recording sockets. HTTP routes, durable recovery, campaign delivery, and roadmap ownership were traced statically. No browser session, listening server, real network handshake, durable restart, or full co-op launch was run. A passing characterization test means the observed leak exists, not that privacy passes.

## Seated-player delivery trace

A valid identity is not automatically an active-match seat: `authorization/MatchSeatMembershipSource.ts:152-180` reads durable metadata/seat membership. Lobby invitees are intentionally a different case.
2. **Build the opening state.** `matchUnitBootstrap.ts:93-120` builds `IGameUnit` records with references, pilot skills, heat sink/movement/gyro/tonnage/C3 fields and, when available, a custom construction snapshot. `ServerMatchHostBootstrap.ts:43-50` passes both forces and game units to the authoritative session. `src/utils/gameplay/gameEvents/lifecycle.ts:75-100` embeds `input.units` in `GameCreated` along with configuration and optional objectives/terrain/C3/ground objects/minefields. `src/utils/gameplay/gameState/lifecycle.ts:19-29` reconstructs every listed unit using `deployPlacementsFor`; `gameState/initialization.ts:35` derives placement from side/list order. Thus a unit list can disclose position without an explicit `position` JSON key.
3. **Live event boundary.** `ServerMatchHostEvents.ts:261-280` reads match metadata and resolves recipients; `:285-325` invokes `filterEventForPlayer` or `filterEventForSpectator` when fog is on. `:328-362` applies the publication boundary and only then assigns a viewer delivery number. `ServerMatchBroadcaster.ts:195-208` serializes and sends the resulting message. There is no need to bypass this boundary to reproduce B14: the boundary's current policy admits the opening payload.
4. **Exact leak.** `fogOfWar.ts:123-150` strips only `customUnitDefinition` and `criticalSlotManifest` from non-owned opening units; it does not remove the unit or its other fields. If neither secret field exists, processing falls through. `src/utils/gameplay/gameEventVisibility.ts:6-17` classifies `GameCreated` as public, and `fogOfWar.ts:163-165` returns public events. `projection/MatchWireAudienceCatalog.ts:54-73` also makes `GameCreated` public. The probe establishes the leak for reference/skill/deployment data; richer bootstrap producers can carry additional construction-derived fields. 5. **Ordinary event streams.** `fogOfWar.ts:163-171` discriminates public/actor/observer/target events; `:186-211` gates observer movement by visibility. `src/utils/gameplay/visibility.ts:58-85` uses ownership, sensor range and LOS. ## Proposed bounded disposition

Do not promise complete playable fog redaction in a single 500-line slice. Simply dropping unknown units from `GameCreated.units` changes list-index deployment placement and leaves later visible events referring to units the client never initialized. A correct solution needs an explicit visible-unit hydration/last-known-state contract, stable placements, shared-team ownership semantics, and parity across live/replay/recovery/HTTP history and metadata. The current `GameCreated` public classification and deliberate sealed reveals also need an explicit information-policy decision. Those are separate restoration slices, not a cosmetic client fix.

**Recommend a new B14-0, “fail closed on unsupported fog delivery,”** under the existing multiplayer authority/privacy area, with review classes **privacy, authority, replay**. This is a proposed temporary containment, not a change made by this audit or a claim that fog is implemented correctly. It would refuse fog-on multiplayer reads for every playing/spectating/host audience before baseline/event serialization, including join, live/rejoin and HTTP history/metadata. Preserve fog-off co-op behavior. Verify membership first, so a stranger learns no extra fog configuration. Unavailable metadata must not cause a raw fallback. Use existing typed refusal vocabulary with a fixed `fog-projection-unavailable` reason and policy close 1008; no new protocol enum is needed. Persisted matches remain intact and the server remains authoritative. Public lobby existence/config summaries are not private battle-state reads.
