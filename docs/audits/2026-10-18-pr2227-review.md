The scope ("the helper seam is the recommended maintainable plan"), the design ("Rebuilding/discarding the fixture in each caller ... would be alternative implementations") and the receipt (`alternative` field) all disclose this alternative rather than hiding it. Registering is the correct call.

### Leaf 2: `coopMissionAnnouncement.harness.ts` - necessity established, on two independent grounds

(a) Threading. The reconnect leaf reaches `openRouteFixture` only through `openAnnouncementFixture` (announcement:54, zero-argument call). Once leaf 1 gains an opt-in seam, this file is the only place on the registered leaf's call path that can forward it. Bypassing it would mean the test re-implements `join`/`create`/`census`/`close` (announcement:56-118) locally; same duplication objection as above.

(b) Confirmed writes. `ObservedSocket.send(data: string)` (announcement:23-29) calls `MockWireSocket.send(data)` (grant-helpers:50-52), which records the frame and never invokes a write callback. With a registry port installed, `bindCampaignSyncConnection` (binder:320 `applicationReceipts ?? registry.applicationReceipts`; the harness `join` passes `membership`, :68) builds a `CampaignApplicationConnection`, and the GM/member join path awaits `application.open()` (binder:1245-1246) -> `refresh` -> `publish` (application:385-419) -> `broadcaster.sendConfirmed` (broadcaster:230-268), which resolves **only** via the `socket.send(payload, cb)` callback (:256-260) or abort. `ObservedSocket` never calls `cb`, so `open()` never settles, `view.inFlight` stays set, and no later ACK or delta can flow; meanwhile `join` returns successfully because `nextFrame(socket, 'CampaignSnapshot')` (:70, :79) resolves on frame _arrival_. The reconnect leaf calls `fixture.join` at :306 and :332. The migration's "real application ACKs" therefore cannot be proved through the shared `join`; the socket must complete writes and the join must await establishment, not arrival. Confirmed from source, and the receipt's distinction (frame arrival is not readiness) is the right one.

The reconnect test does already contain a callback-aware `ReceiptSocket` (:759-773) and `bindReceipts`/`joinReceipts` (:796-846) - but those are scoped inside the P2CE2 `describe`, pass an **explicit** binder override (`applicationReceipts: { database: db }`, :817), and do not use the registry-installed port. They prove the receipt engine, not the registered "installed on a reset registry" behavior, and cannot substitute for the shared `join` the cold-rebuild tests use. The minimal-repair text correctly requires `ReceiptSocket` to keep sole ownership of its callback (its `super.send(data)` at :764 passes no callback), which is the one compatibility hazard of making `ObservedSocket` callback-aware; the receipt names it.
