## Narrative

The branch is, with one exception, a slower draft of work main already finished. Its central idea was to generalize the umbrella's session journal into an entity-scoped authority journal with one owning stream per fact, indexed entity links, explicit branching, and replay-safe schema evolution. That idea reached main, but through a different route: the umbrella spawned focused leaf changes under `event-history-wave-map.md`, those leaves were implemented and archived, and their deltas merged into the canonical capability specs. The canonical `openspec/specs/event-store/spec.md` today opens with `Authority Events Have One Owning Stream and Explicit Entity Links`, which is the branch's `Authority Events Have One Owning Stream and Explicit Entity References` with more identity fields, a stricter provenance rule, and a server-internal read boundary the branch never wrote. Several branch paragraphs appear on main word for word. `a6ffda42e`'s quarantine sentence is the canonical `Corruption Isolated to One Authority Scope` body, and `b6cfad30d`'s canonicalizer paragraph is the canonical `Chain Verification` body.

Where the branch and main disagree, main is later and better informed. The branch's `01d2cebea` required branch activation to wait until every admitted cross-stream delivery was reconciled. Main's `add-authoritative-history-branches` states the opposite in `Branch Activation Is Verified, Compare-and-Swap, and Atomic`: activation "SHALL NOT wait for a replacement receipt that cannot exist before activation", and instead commits the higher-version replacement outbox and `pending` saga inside the activation transaction. That is a deliberate deadlock fix, so the branch wording was not applied.

The one live gap is vocabulary. Main's journal settled on stream-local `streamRevision`, database-wide `commitPosition`, and intra-batch `commandIndex`, present in 55, 31, and 13 source files respectively, and the canonical spec is written in those terms. The umbrella `harden-gm-two-player-campaign-sessions` delta still describes a single "server-only authority sequence", because the branch commit that reconciled it (`ff94ac319`) never merged. Wave-map rule 4 requires exactly this reconciliation before a leaf is synced, so main would otherwise receive two contradictory definitions of the same ordering contract. That commit is the applied work below.

Two adaptations were made rather than taking the branch text verbatim. First, `authoritySequence` is not dead on main: it is the live match-store identity in `src/lib/multiplayer/server/projection/ViewerDeliveryCursors.ts` and `IMatchStore.ts`, mapped onto the journal at `revision = sequence + 1` (`src/lib/multiplayer/server/MatchCheckpointHistory.ts`). D3 therefore names both identities and their mapping instead of deleting one. Second, the branch renamed the umbrella's sketch fields to `baseStreamRevision` and `cutoffStreamRevision`, but the shipped `IEventHistoryBranch` in `src/lib/events/journal/EventHistoryBranchContract.ts` uses `baseRevision`; the applied edit follows the shipped spelling so a third variant is not introduced.

## Encounter force selection decision

The package is not re-created. Its subject, a working `/select-force` recovery route for both encounter force slots, shipped on main as PR #1139, commit `a19555116`, "fix(gameplay): add encounter force selection recovery". The route is `src/pages/gameplay/encounters/[id]/select-force.tsx`, its link builder is `src/pages-modules/gameplay/encounters/encounterRouteIdentity.ts`, and it is registered in `e2e/app-shell-route-manifest.json`.

Every behavioural scenario the branch proposal named has a matching test on main. The unit suite `src/__tests__/unit/pages/encounterSelectForce.test.tsx` covers the empty-force recovery state, side-specific player and opponent assignment actions, save failure without navigation or false success, duplicate-submit prevention while a save is in flight, invalid-side refusal, and the missing-encounter state. The browser journey in `e2e/encounter.spec.ts` follows the real player and opponent links, asserts the side-aware URL with preserved campaign and mission linkage, waits on the per-side validation response, reads `/api/encounters/:id` back to confirm both persisted slot ids, and proceeds to a successful launch.

Creating a fresh package with every task unchecked would assert that this work is in flight when it is merged, and would require a ledger entry claiming the same. Two residuals are recorded here rather than filed: the browser journey proves persistence by API readback rather than by a cold page reload, and the accessibility and narrow-viewport clauses of the branch's third requirement have no dedicated coverage. Neither is a regression, and neither justifies an active change of its own.
