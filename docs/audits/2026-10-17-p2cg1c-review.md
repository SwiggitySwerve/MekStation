**Store (`DurableMatchStore.ts`, +102/-3).** `createMatch` keeps its async signature and behaviour; its body is now the shared private `writeMatchRows(meta, events, transact)` with `transact = this.db.transaction(write)()` (the baseline DEFERRED transaction, duplicate pre-check outside it exactly as before). `holdMatchConnection()` refuses when `this.db.inTransaction` (`Match reservation needs an idle match connection`), issues `BEGIN IMMEDIATE` on `this.db` (M; never `capabilityDatabase()`), returns `commit` (COMMIT, then `held=false`; throws if already released) and `release` (idempotent; `held=false`, ROLLBACK only if still in a transaction), and queues a microtask that releases a hold its synchronous span left open. `createMatchPrepared`: hold -> `guard()` -> `rejectPreparedThenable` -> a non-null refusal releases and returns `refused` with nothing written -> `writeMatchRows(..., write => write())` runs the duplicate check and the inserts inside the hold (so the duplicate check is under the IMMEDIATE lock, stronger than the async path) -> `commit`. A precommit throw releases (an `AggregateError` if the release itself throws) and rethrows the original. A COMMIT that throws is rolled back if still open and classified by owner readback: `getMatchRow(meta.matchId).meta_json === JSON.stringify(meta)` is `committed` (the row is written as `JSON.stringify(meta)`, line 768, so this is exact identity), row absent rethrows the original error, and a throw from the release or the readback is `uncertain {error}`. `reserveMatchProgression()` is `{ release }` of a write-free hold. The one new value import, `rejectPreparedThenable` from `SQLiteEventJournalWriter`, is the helper B exported and adds no cycle (madge 174 -> 174, identical sets). Every other store method, the campaign `capabilityDatabase()` ports and the journal mirror paths are untouched.

## 5. Per-class findings

- **Authority.** No new trust surface. `actorId` comes from the route's authenticated player; `createPreparedCoopMissionMatch` is a server module export with no route, socket or client reach (section 6 item 4). Membership is re-checked at the same three points as the baseline; admission, roster and fingerprint identity rules are shared with the route path through one body rather than copied. The P2CB preparation is opaque (a `WeakMap` capture inside `campaignPublicAppliedView.ts`), is revalidated only by the view that created it, and only on that graph's own handle inside an open transaction; a second module graph's view on the same file is refused `context-mismatch` -> `COOP_MISSION_LAUNCH_REFUSED` with both files unwritten (tested, including a cold reopen). The old route-reached create needs no readiness and still answers 201 (positive control in the first case). No finding.
- **Privacy.** The three new public codes `COOP_MISSION_LAUNCH_UNSUPPORTED`, `COOP_MISSION_NOT_CONVERGED` and `COOP_MISSION_LAUNCH_REFUSED` are `CoopMissionRefusal(409, code)` instances whose only own properties are `status`, `code`, `name` and `message === code`; the verdict's `reason`, `participantIds`, cuts, digests and hydration are dropped at `launchRefusal` (`expectPublicOnly` pins the serialised shape; my RM4 shows the pin discriminates). The route maps `CoopMissionRefusal` to `{error: code, code}` and everything else, including `CoopMissionCommitError` (whose `errors` can carry SQLite messages), to a fixed `500 COOP_MISSION_STORE_FAILURE` after server-side logging. `ICampaignLaunchPreparation` carries no journal position, digest or row fingerprint (its own doc comment and the capture design). No finding.
- **Replay.** Match id, request fingerprint, owner map, side assignments and the opening events are derived by the same code as the route path; the lock-order case proves one deterministic match and opening log through a cold reopen (`GameCreated`, `GameStarted` prefix equal across the owning store and an independent handle). The seed after release is the baseline `seedJournalFromInitialEvents` (idempotent on its receipt). The route then reaches the same stored identity through the old door without a second match or a second launch event. No finding.
- **Idempotency.** Exact retry after a precommit failure creates once; after a known M commit with a failed C release, the retry settles from the stored row (`prepare` not called: no new readiness granted), announces once and appends one launch; after an uncertain outcome the retry's readback finds no row and creates once; after campaign advancement the stored identity is returned with no append and identity/membership still apply (divergent config -> `COOP_MISSION_IDENTITY_CONFLICT`; revoked seat -> 403). `holdMatchConnection.release` and the reservation's `release` are idempotent and inert after the microtask. No finding.
- **Concurrency.** Lock order is C IMMEDIATE then M IMMEDIATE, pinned by the exec trail `C:BEGIN IMMEDIATE, M:BEGIN IMMEDIATE, M:COMMIT, C:ROLLBACK` and by the observation that during the guard both handles are in a transaction and a separate connection cannot take either file's write lock; at M COMMIT the row is visible on the owning connection and not yet on a read-only one, and C is still held. A real second process sees BUSY on both files during the hold and acquires each lock only after the corresponding release (match after M COMMIT, campaign after C ROLLBACK). A competing process that commits first makes the IMMEDIATE acquisition wait and the revalidation refuse `COOP_MISSION_NOT_CONVERGED` with an unchanged census, while a deferred reader on the same file keeps its stale snapshot and cannot upgrade (`SQLITE_BUSY*`). There is no `await` between `BEGIN IMMEDIATE` on C and `ROLLBACK` on C (the write callback is synchronous; `create` is the synchronous store method; `revalidate` is synchronous and thenables are rejected). Nothing holds M across an `await` either: the store's microtask release is proven by the forgotten-hold case (a write made inside a forgotten reservation is rolled back by the next microtask and a stale release is inert). Finding: none on this head; two design hazards for successors are recorded as N2 (stuck transaction after a throwing ROLLBACK) and N3 (deferred read-then-write on M under external writers), with carry-forwards CF-D5 and CF-D7.

## 6. Judgments on the author's decision points

1. **Decision point 1: the test changed after the RED commit.** The diff between 8f0955f8 and ed7fb95b in `coopMissionCreate.test.ts` is +23/-2, all inside the `blocked` branch of the spawned child script and the `blocks writers in other processes ...` case. Red version: after observing BUSY, the child immediately did `BEGIN IMMEDIATE` (busy_timeout 15 s), wrote a probe row and committed, so the saga writer's commit could land on matches.db while the parent's post-release `seedJournalFromInitialEvents` had a DEFERRED read transaction open. Head version: the child proves the lock is free with `BEGIN IMMEDIATE`/`ROLLBACK` (recording `acquiredAt`), waits for a `.done` marker the parent writes after `create()` resolves, then commits its probe; one assertion is added (`committedAt >= acquiredAt`), none removed or loosened. The kept flake log (`green-related-run1-flake.json`, sha256 verified) shows exactly one failure in 1490 tests: `SqliteError: database is locked` thrown at `DurableMatchStore.ts:1260` inside `seedJournalFromInitialEvents`'s `db.transaction` (the INSERT after the receipt SELECT), i.e. `SQLITE_BUSY_SNAPSHOT` on a deferred write upgrade, which `busy_timeout` does not retry. Ruling: (a) this is not a violation of the red/green discipline's purpose. The discipline exists so that the product is proven against tests the author did not tune after seeing it fail; here the product never failed the case in the registered run mode (my 3/3 runs of the RED-byte file against the head product, and the author's two-suite green), the only failure was a timing race between two OS processes in a parallel selection the discipline does not register, the change is to the child harness's scheduling and is assertion-monotone, and it was disclosed with the raw evidence. It is a recorded deviation from byte-identity, not a hidden one, and the author's mutation probes ran against the red bytes. (b) The case still proves what its title says: `busyAt <= guardAt` (both writers were refused during the hold), `saga.acquiredAt >= matchCommit` and `campaign.acquiredAt >= campaignRelease` (each lock became takeable only after the matching release) are unchanged, and the commit now lands after the parent's post-release work rather than concurrently with it. What moved is only that "then lets them commit" is no longer demonstrated to be concurrent with the parent's seed, which was never the claim. (c) The underlying behaviour the flake exposed is real but baseline: every `this.db.transaction(fn)()` on DurableMatchStore is BEGIN DEFERRED and reads before it writes, so under any concurrent writer in another process on matches.db a write upgrade can fail with `SQLITE_BUSY_SNAPSHOT` instead of waiting. Production runs one server process on matches.db and the route path has the same exposure, so this is not C's defect and not in C's leaves to fix; it is recorded as N3 and carried to D as CF-D5 (D must not add a deferred read-then-write on M, and E's route switch must keep seed/recovery/announce after both releases). I would have preferred the stabilisation to be committed as a separate, visibly labelled fourth commit rather than folded into the implementation commit; that is M1, a docs/ledger minor.
2. **C-OPEN-1 / CF-C1 non-applicability.** Confirmed by the code and by the trail: the only SQL C issues on the campaign handle is `BEGIN IMMEDIATE` and `ROLLBACK` (the `traceExec` spy records every `exec`, and `holdCampaign`'s write callback cannot reach `appendInBorrowedTransaction` or any journal writer: the create module imports no campaign sync or journal module, only the type-only `campaignPublicAppliedView`). `revalidate` reads the branch store, effective head, roster and applied-view rows and writes nothing (the only INSERT/UPDATE in `campaignPublicAppliedView.ts` is in `accept`, not on this path). CF-C1 therefore does not arise; no leaf outside the seven is implied.

## 7. Carry-forwards for P2CG1D (exact wording)
